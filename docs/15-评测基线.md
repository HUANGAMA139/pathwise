## 一、本轮学的：`QuestionAnswerAdvisor` 与「LLM 当裁判」

### 1. 教科书版的 RAG 有多短

我们用 迭代 8 以来手写的那套编排，把「检索 → 注入 → 生成」拆成了四五处代码
（路由、取证据、拼材料、带出处渲染、综合）。框架给的标准件是这样一个：

```java
QuestionAnswerAdvisor advisor = QuestionAnswerAdvisor.builder(vectorStore)
        .searchRequest(SearchRequest.builder().topK(5).build())
        .promptTemplate(myTemplate)      // 可选，不传就用它默认的英文模板
        .build();

chatClient.prompt().user(question).advisors(advisor).call();
```

检索和注入都在 advisor 的 `before()` 里完成了。**这就是「基础 RAG」的全部。**

### 2. 两个必须知道的细节

**（1）检索结果不在返回值里，在 `context` 里。**

advisor 把检索到的文档放进 `ChatClientResponse.context()`，键是
`QuestionAnswerAdvisor.RETRIEVED_DOCUMENTS`。所以评测时要用
`.call().chatClientResponse()` 而不是 `.content()`——**否则你只拿到答案文本，
拿不到「它到底检索了什么」，context 类指标就没法算。**

**（2）它会丢掉「出处」。**

advisor 注入提示词时只取 `Document.getText()`，把片段拼成一段纯文本。
我们 `Chunk.render()` 里的「【片段 id｜出处：xxx】」在这里看不见了。
后果很实际：**模型没有东西可引用，用户也就没东西可核实**——
而这正是 迭代 8 定 `source` 字段时最在意的那件事。这个差异值多少分，评测会给答案。

### 3. 关键结论：Spring AI 只覆盖 RAGAS 四个指标里的大约一半

| RAGAS 指标 | 含义 | Spring AI 1.1.0 有吗 |
|---|---|---|
| faithfulness | 答案是否被检索到的上下文支持 | ✅ `FactCheckingEvaluator` |
| answer_relevancy | 答案是否回答了问题 | ⚠️ 只有 `RelevancyEvaluator`，但它的定义是「答案是否与 **context** 一致」 |
| context_recall | 标准答案的要点有多少能从上下文里得到 | ❌ 没有，要自己写 |
| context_precision | 检索到的片段有多少真的有用 | ❌ 没有，要自己写 |

**不是框架不行，是这两个指标本来就需要 ground truth（标准答案），框架无法凭空生成。**
所以 `eval/` 里有一个自己写的 `LlmJudge`，负责这三项：答案准确率、片段级 context 精确率、
RAGAS 式的 context 召回率。

### 4. 框架那两个判分器有个必须知道的脆弱点

我读了 `RelevancyEvaluator` 的源码，它的判分逻辑是：

```java
if ("yes".equalsIgnoreCase(evaluationResponse)) {   // 拿整个响应跟 "yes" 精确比较
    passing = true; score = 1;
}
return new EvaluationResponse(passing, score, "", Collections.emptyMap());   // ← 原始输出被丢掉
```

两个问题叠在一起：

1. **精确匹配**：中文模型回「是」或「YES.」都会被判成不通过；
2. **原始输出被丢弃**：我们**看不到它到底说了什么**——坏了不会报错，只会给出错误的分数。

这正是项目一直在防的那类错误（「最危险的错误都是不报错的」）。所以评测里加了一道守卫：
**某项指标在全部用例上恰好是 0.00 就大声报警**（28 道题全 0 几乎不可能，大概率是判分解析坏了）。

## 二、测试集：8 列，`expected_route` 贯穿全表

`eval/testset.csv`，28 条用例。为什么是这 8 列：

| 列 | 用途 |
|---|---|
| `id` | 定位一道题，结果里能对回来 |
| `question` | 喂给链路 |
| **`expected_route`** | **算路由准确率；`document`/`database`/`both`/`none` 四值** |
| `expected_source` | 算**文档级** context 精确率/召回率（零 LLM 成本） |
| `expected_answer` | 算答案准确率、LLM 版 context 召回率（需要标准答案） |
| `category` | 分组看指标（比如只统计「语义」那一族） |
| `difficulty` | 同上 |
| `note` | 解释这题在考什么 |

**`expected_route` 贯穿全表是这套设计的关键。** 如果只有一个「准确率」数字，
你分不清是**路由选错了**还是**路由对了但检索差**——而这两件事的修法完全不同。

分布：`document` 15 · `database` 4 · `both` 4 · `none` 5。

> **命名说明**：测试集里写 `none`（给人和报表看更直白），代码里叫 `REFUSE`（迭代 8 定的，改它要动一片）。
> 两者的映射收在 `EvalCase.route()` 一处。

## 三、迭代 14 教训的落地：测试集要先量字面重合度

迭代 14 的发现 4 是：**我凭感觉挑的 3 道「同义题」，只有 1 道真的有效**——
另外两道和文档仍有大量 2-gram 重合，字符匹配照样能命中。

所以这次**写完测试集先量一遍**，结果写在 `eval/testset-check.md`（脚本生成，勿手改）：

对照标定（迭代 14 那 5 道题，命中结果已知）：

```
字符匹配命中=是   0.43 / 0.29 / 0.38 / 0.53
字符匹配命中=否   0.20          ← 唯一一个失败样本
```

**分界大致在 0.2 ~ 0.3**（注意：否定样本只有 1 个，这只是粗标定）。

本测试集 15 道 document 题的分布：

- **低重合（<0.30，能量出语义差异）7 道**：D03 D07 D11 D12 D13 D14 D15
- **高重合（>=0.50，两种检索都该命中，用作对照）6 道**：D02 D04 D06 D08 D09 D10

其中 **D13 / D15 是刻意做的对照对**：同一个事实（数据是 T+1 的）、两种问法，
字面重合 0.17 对 0.00。这种对照对是**最省成本地分离出「检索方式」这一个变量**的办法。

## 四、评测脚手架怎么跑

### 三条链路 / 三个 scope

一次实验往 `eval/metrics.csv` 追加 **3 行**：

| pipeline | scope | 说明 |
|---|---|---|
| `agent` | all | 跑全部 28 条。**路由准确率在这一行** |
| `agent` | document | 只统计 15 条 document 用例，**与 basic-rag 可比的那一档** |
| `basic-rag` | document | 教科书版；它没有路由能力，硬跑 database/both 是在评它做不到的事 |

### 指标

| 指标 | 要花模型调用吗 | 怎么算 |
|---|---|---|
| `route_accuracy` | ❌ | 实际路由 vs `expected_route` |
| `ctx_recall_doc` | ❌ | 期望出处文档有没有被召回 |
| `ctx_precision_doc` | ❌ | 召回片段里有多少来自期望出处 |
| `ctx_precision_llm` | ✅ | 逐片段判「有助于回答这个问题」 |
| `ctx_recall_llm` | ✅ | RAGAS 做法：标准答案拆要点，逐条判上下文支不支持 |
| `answer_correct` | ✅ | 实际答案 vs 标准答案（A 完全/B 部分/C 不一致） |
| `faithfulness` | ✅ | 框架 `FactCheckingEvaluator` |
| `answer_relevancy` | ✅ | 框架 `RelevancyEvaluator` |

### 调试时先小跑

```
# 只跑前 3 条，确认链路通、判分没坏
mvn spring-boot:run "-Dspring-boot.run.arguments=--sdaq.exp15.enabled=true --sdaq.eval.limit=3"
```

全量一次约 **215 次模型调用**（43 次问答 + 判分），耗时几分钟。
`metrics.csv` 是**追加**的——历史记录必须留着，否则「比上次好多少」永远答不了。
换实验名用 `--sdaq.eval.experiment=exp16-hybrid`。

## 五、实测结果

### 5.1 判分器实测行为（来自 `limit=3` 的调试跑）

这一节的价值不在数字（n=3 太少），在于**先确认判分器可不可信**。挂上 `JudgeLoggingAdvisor` 后拿到的原始输出：

```
agent      D01: yes / YES    D02: yes / YES    D03: yes / YES
basic-rag  D01: no  / YES    D02: yes / YES    D03: no  / YES
                         ↑        ↑
                   忠实性判分   相关性判分
```

**结论 1：框架那两个判分器没有解析问题。** 它们回的是干干净净的 `yes` / `no` / `YES`——
没有句号、没有中文。事先担心的「`"yes".equalsIgnoreCase` 会被『Yes.』或『是』打挂」**没有发生**。
所以那几个 `no` 是模型真的判的，不是失败。

> 这一条值得记：**一个「可能有问题」的怀疑，只有实测能定死。**
> 我在动手前就把这个脆弱点写进了文档，结果实测证明它这次没有发作——
> 如果只凭怀疑就把框架判分器换掉，就白换了一次。

**结论 2（重要）：`RelevancyEvaluator` 在这个场景里没有区分度。**
六次判分全是 `YES`。不是它坏了——它判的是「答案是否与 **context 一致**」，
而我们的答案都是照着材料写的，必然一致。**RAGAS 的 `answer_relevancy` 问的是
「答案有没有回答这个问题」，那是另一回事。** 这一列现在等于恒真；
真要度量答案相关性，得自己写一个判分器（套 `LlmJudge` 的写法即可）。

**结论 3（这个结论我改过一次，那次改正比结论本身更值得记）：**

我一开始把 `faithfulness=0.00` 解释成「框架判太严、会惩罚正确的改写」——**错了，真因是我传错了参数。**

`FactCheckingEvaluator` 的 `{document}` 来自 `Evaluator.doGetSupportingData(request)`，而它**只读 `getDataList()`**：

```java
default String doGetSupportingData(EvaluationRequest r) {
    List<Document> data = r.getDataList();          // ← 只读 dataList
    return data.stream().map(Document::getText)...;
}
```

我却写成了 `new EvaluationRequest(context, answer)`——它命中 `(String userText, String responseContent)` 重载，
**dataList 是空的，`{document}` 渲染成了空字符串**。模型拿着空材料去核查断言，只能瞎答：
这正是**同一份空材料下 agent 三次 `yes`、basic-rag 两次 `no`** 的原因——它是无依据的随机输出。

现在改成 `new EvaluationRequest(List.of(new Document(context)), answer)`（上下文进 dataList），
并加了守卫：**上下文为空就跳过这个指标并告警——宁可不给分，也不给一个假分。**

**这件事的教训比 bug 本身值钱。** 我当时给的解释（「框架判的是严格支持」）听起来很合理、也很有深度，
但它是错的。真正把它揪出来的，是那行**答案原文**的日志：

```
[分歧] D03 答案判定=1.00 忠实性=0.00 —— 答案原文：华东区管着：上海、江苏、浙江、安徽、福建。
```

看到答案完全正确，我才回头去查参数——而不是去写一段「faithfulness 为什么容易偏低」的漂亮分析。
**「把中间产物打出来」不是洁癖，它是防止把错误结论写进文档的唯一办法。**

**修完之后复跑同一个 `limit=3`：** D03 的忠实性 `0.00 → 1.00`，`[分歧]` 警告消失，
basic-rag 那一列变成整齐的 `1.00 / 1.00 / 1.00`。诊断和更正都成立。

**但这一跑立刻暴露出下一个可见性缺口：** basic-rag 的答案判定是 `0.50 / 0.50 / 1.00`，
agent 是 `1.00 / 1.00 / 1.00`——**我知道它被扣分了，但不知道为什么**，
因为答案原文只在「判分器打架」时才打。于是把日志条件放宽成「打架 **或** 没拿满分」。

> **同一个教训在一小时内出现了两次**：分数本身不构成证据，**能解释的分数才是**。
> 这也是为什么这套脚手架里，「打日志」的代码量和「算指标」的代码量差不多。
> 迭代 4 那句「中间产物是错误放大器」，在评测这一层同样成立——只是这次被放大的是**结论**，不是答案。

### 5.2 第一组数字（两次全量对照）

> **为什么留两次**：第 1 跑之后修了 `both` 的上下文 bug（发现 6），于是重跑了一次。
> 而**重跑本身就产出了本轮第二个重要发现**（发现 8）——所以两次都留着。
> 两次实验名都是 `exp15-baseline`，靠 `metrics.csv` 的 `ts` 列区分（13:46:51 / 13:54:28）。

| 指标 | agent/28 第 1 跑 | agent/28 **第 2 跑** | agent/15doc 第 2 跑 | basic-rag/15doc 第 2 跑 |
|---|---|---|---|---|
| 路由准确率 | 0.89 | **0.86** | - | -（不做路由） |
| 答案准确率 | 0.89 | 0.86 | **0.73** | **0.73** |
| 忠实性 | 0.75（bug） | **0.93** | 0.91 | 1.00 |
| 相关性 | 1.00 | 1.00 | 1.00 | 0.93 |
| 文档召回 | 0.88 | 0.87 | 1.00 | 1.00 |
| 文档精确 | 0.51 | 0.52 | 0.55 | 0.53 |
| 覆盖(LLM) | 0.88 | 1.00 | 1.00 | 1.00 |
| 检索精确(LLM) | 0.64 | 0.64 | 0.64 | 0.61 |
| 平均耗时 | 4456 ms | 4226 ms | 5006 ms | **1471 ms** |

**修 `both` 的效果确认了**：agent 的整体忠实性 `0.75 → 0.93`，X01/X02/X03 的 `[分歧]` 全部消失。

**同时答案准确率从 0.80 掉到 0.73（agent/15doc）——正好和 basic-rag 打平。** 这是发现 8 的直接后果。

### 发现 1（最重要）：三处路由错误是同一个病 —— **路由不知道「我手上有什么」**

28 条里错了 3 条，而三条的理由指向同一件事：

| 用例 | 期望 | 实际 | 模型给的理由 |
|---|---|---|---|
| D10 `XR-2000B 和 XR-2000C 有什么区别` | document | **refuse** | 「属于产品规格对比，**既不在制度文档中定义**，也不在业务数据库中存储」 |
| D14 `福建以前是哪个区的` | document | **refuse** | 「涉及历史行政区划，**属于通用地理历史常识**」 |
| D12 `每个订单平均贡献多少钱` | document | database | 「需从订单表聚合」 |

**前两条的理由是错的**：语料 05 就是《产品线与编码规则》，明确列了这两个型号；语料 02 明确记录了「2025 年起福建由华南划归华东」。

**所以路由是按「这是什么类型的问题」在判断，而不是按「我的语料里有没有」。**
它缺一个「我手上有什么」的信号——**给它一份语料标题/表结构摘要就能修**（迭代 23 路由 v2 的现成切入点）。

> 这也解释了为什么这个错误**看起来不像错误**：模型的理由写得很有条理、很像那么回事。
> 只有拿它和语料的实际内容对一下，才知道它在断言一件假事。

### 发现 2：agent 的优势不在「生成」，而在「能干 basic-rag 干不了的活」

15 道 document 题上：**agent 0.80 vs basic-rag 0.73——基本持平。**

但 basic-rag 只被允许跑这 15 道。**另外 13 道（4 database + 4 both + 5 none）它一道也答不了。**
所以正确的读法是：**在「只查文档」这件事上两者基本相同；agent 的价值是覆盖了全部 28 道题。**

我事先隐含的预期是「手写编排会明显更好」——**这个预期没有成立。** 记下来。

### 发现 3：basic-rag 那一片 0.50 是我造成的，不是它笨

`[未满分]` 打出的原文说明了问题：

```
D06 答「7个工作日。」                       期望还含「从申请提交时间起算，遇法定节假日顺延」
D04 答「福建属于华东销售区域。」              期望还含「2025 年起由华南划归华东」
D05 答「不包含。山东在本公司的销售区域划分中归属华北区。」  期望还含「行政区划上属华东」
```

**这些答案都对，但都少了要点。** 而少要点的原因是我给 `BasicRagPipeline` 的提示词里写了
「**回答简洁**」，而 agent 的提示词要求引用来源、说清口径。**这不是能力差异，是提示词差异。**

结论：**对照组要公平，这条得改**——要么两边都要求完整覆盖，要么把「简洁」从 baseline 的提示词里拿掉。
改之前，0.80 vs 0.73 这个差距**不能算作编排能力的差距**。

### 发现 4：`ctx_precision_llm` 上那点差异是**噪声**，不是信号（这条比数字值钱）

两条链路的检索**完全相同**（同一个向量库、同一个 topK、同一个查询串），
所以它们送给判分器的输入**逐字相同**。但结果是 agent 0.63 / basic-rag 0.60。

逐题看最清楚——**D06 两边输入一样，一个判 0.40、一个判 0.20。**

> **同一输入、同一判分器、两次运行差 0.20 = 一个片段 / 5。**

**这就是这套评测的判分噪声量级。** 直接推论：

- 15 条用例上的平均差异**小于约 0.05 时不可区分**；
- 本轮所有 context 列的对比（1.00 vs 1.00、0.53 vs 0.53、0.63 vs 0.60）**全部落在噪声里**——
  它们说明的是「两条链路检索相同」，**而不是「谁更好」**。

**这条给出了整套评测的分辨力下限，是本轮最有方法论价值的产出。**

### 发现 5：`answer_relevancy` 几乎没有区分度（并更正我上一轮的说法）

我前一节说它「恒为 1.00、没有区分度」——**说过头了**。43 次判分里它否了一次
（basic-rag 的 D14）。但那一次大概率也是误判（答案「福建以前是华南区的。」确实与上下文一致）。

准确的说法是：**它在 43 次里携带的信息量约等于 0**。这一列应该换掉或去掉。

### 发现 6：`faithfulness` 的 0.75 是量测 bug，不是答案的问题

`agent / 全 28 条` 的忠实性 0.75 里，X01/X02/X03 三条是 `0.00`。看它们的答案原文：

```
X01 ...华东区销售额是 **128,450,000 元**，来自数据库查询结果... 销售额 = 订单金额 ? 退货金额...
```

**答案引用了数据库的数字，而我只把「文档片段」当上下文送去判分——数据库结果没进去。**
严格的事实核查当然会说「这个数字不被材料支持」。

**已修**：`both` 用例现在把 `dbResult.render()` 一并并进上下文。**所以 0.75 这个数字作废**，
修完要重跑。这是本轮第三个「指标算错了而不是答案错了」的问题——**同一类错误的第三次出现**。

### 发现 7：延迟是路由的价格标签

同一批题：agent **5456 ms** vs basic-rag **1425 ms**，差约 4 秒。主要来自
路由那次 LLM 调用（约 1.5 s）+ 更长的提示词与答案。**这是「四值路由」的成本，要记账。**

### 发现 8：路由是**非确定性**的 —— 第二类噪声

两次全量之间只有一道题的路由变了，但那一变就够了：

| 用例 | 第 1 跑 | 第 2 跑 |
|---|---|---|
| D15 `能不能一小时前下的单马上查出来` | DOCUMENT [OK] | **REFUSE [X]** |

同一道题、同一份提示词、同一个模型，**两次跑出了不同路由**。而第 2 跑拒绝它的理由
（「**既不在制度文档（未涉及查询时效规则）中定义**」）**和 D10/D14 是同一个病**——
而且这次它给的还是 `置信度 0.95`。

**推论：`route_accuracy` 这个数字本身有噪声，28 条上 ±1 条 ≈ 0.036。** 所以：

- **迭代 23 做路由 v2 之前，必须先测这个噪声底**——否则「从 0.86 提到 0.93」可能只是运气；
- **任何小于 2 条（0.07）的路由提升都不可声称**；
- 这条和发现 4（判分噪声 0.20/条）合起来，就是本轮量出的**两个噪声源**，
  它们共同定义了这套评测的分辨力下限。

> 这一条只有靠「同一实验跑两次」才看得见。
> **`metrics.csv` 追加而不是覆盖的设计，本轮第一次真正派上用场。**

### 发现 9：分类表把矛头指向了**路由**，不是检索 —— 这改了 迭代 16 的计划

| 分类 | 条数 | 答案 | 忠实 | 检索精确LLM |
|---|---|---|---|---|
| **语义** | **7** | **0.57** | 0.75 | 0.65 |
| 口径 / 口径状态 / 事实 / 纠偏 / 流程 / 跨源 | 各 1~2 | **全 1.00** | 1.00 | 0.40~0.80 |
| 精确编号 | 1 | 0.00 | - | - |

**「语义」那一族 7 条只有 0.57，其余各族全是 1.00。** 看起来像是「语义检索不行」——
**但拆开看，失败的 3 条全是路由错**：

```
D12 每个订单平均贡献多少钱        → 判成 database（正解在语料 06）
D14 福建以前是哪个区的            → 判成 refuse（语料 02 明确写了）
D15 能不能一小时前下的单马上查出来  → 判成 refuse（语料 04 明确写了）
```

**检索根本没跑。** 所以：

> **迭代 16 的混合检索救不了这 3 条。** 想改善「语义族」，**得先修路由**——
> 也就是发现 1 那条：给它一份「我手上有什么」的摘要。

**这对我的测试设计是个反讽。** D14（字面重合 0.12）和 D15（0.00）是我特意设计的低重合题，
目的是**隔离出「语义检索 vs 字面匹配」的差异**——结果它们在**路由**这一层就折了，
**检索压根没机会上场**。低字面重合这件事同时压到了路由和检索两处，而路由在更前面。

**所以 迭代 16 的合理顺序是：先修路由 → 再比检索。** 否则会得出「混合检索没用」的错结论。

## 六、局限

1. **`database` / `both` 的标准答案依赖 mock 数据库的夹具**（mock 只认两个关键词分支）。
   迭代 18 接真实库后，这两个路由下的 `expected_answer` 必须重新标注——`note` 列里标了 `[注意]`。
2. **B04 的标准答案是「查不到」**，考的是防编造而不是查得对。接真实库后这题性质会变。
3. **没有一道题是「文档明确说它答不了」**（比如「退款多久到账」，语料 03 明确写了本文件不规定）。
   这类题路由上算 document、答案上算「承认不知道」，价值很高，但标注规则要先定清楚。
4. **只有 28 道题**。够看出方向，不够做统计推断。
5. **框架那两个判分器的精确匹配问题**（见第一节第 4 点）还没解决，只加了报警。
   如果实测发现它们恒为 0，就换自己写的判分器。
6. **判分本身有噪声**：同一个答案两次判分可能不一样。所以指标只该看趋势，不该抠小数点后两位。
