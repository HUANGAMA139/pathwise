# 迭代 14 · 把 ETL 的第三段补上：pgvector 向量检索

> 目标：把 迭代 13 切好的块灌进 pgvector，用真实向量检索替换掉 `DocumentTool` 的 mock
> 新增代码：`CorpusIngestor`（入库）· `VectorDocumentTool`（检索）· `VectorSearchDemo`（对比实验）
> 开启方式：
> ```
> mvn spring-boot:run "-Dspring-boot.run.arguments=--sdaq.exp14.enabled=true"
> ```

**⚠️ 从本轮起，应用启动需要 pgvector 在跑**（`docker compose up -d pgvector`）。
因为 `PgVectorStore` 这个 bean 在创建时就要连库、建表。没有 Docker 起不来——
这一点我在开工前跟你说反了（当时说「保留 mock 就能不开 Docker 跑旧 demo」），特此更正。

## 一、本轮是什么、不是什么

**不是**「RAG 从零开始」——ETL 的前两段（读、切）迭代 12/13 就做完了。

**是**把 ETL 三段里一直空着的那段补上：

```
迭代 12：CorpusLoader（读）
迭代 13：DocumentChunker（切）
迭代 14：入库 → 向量库（写）   ← 本轮
```

迭代 13 结束时的状态是：片段切好了，但只是**在内存里过了一遍检索工具就丢了**，进程一退全没了。
本轮它真正落进数据库，下次启动还在。**这才是 RAG 里的「R」有本钱可查的前提。**

「不是」的另一半同样重要：**接口一个字没改。** `DocumentTool` 还是 迭代 8 定下的那个形状
（`List<Chunk> search(String query, int topK)`），Agent 主干、四值路由、MCP 对外暴露的代码
全都没动。这是 迭代 8 把契约抽出来的第一次真正兑现。换掉的只是 `MockDocumentTool` 里
那段 2-gram 字符匹配。

## 二、本轮学的：`VectorStore` 接口

Spring AI 用一层接口把「哪个向量库」这件事隔开了。1.1.0 里的形状是：

```java
public interface VectorStore extends DocumentWriter, VectorStoreRetriever {
    void add(List<Document> documents);          // 写
    void delete(List<String> idList);            // 删
    List<Document> similaritySearch(SearchRequest request);   // 查（在 VectorStoreRetriever 上）
}
```

四件事值得记住：

| 观察 | 含义 |
|---|---|
| `add` 收的是 `List<Document>` | 说明**向量库这一层的货币是 Document，不是 Chunk**——我们的 `Chunk` 是项目自己的契约，进出这一层都要翻译 |
| `similaritySearch` 收的是 `SearchRequest` | `topK` / `similarityThreshold` / 元数据过滤都走 builder。**1.x 没有 `similaritySearch(query, k)` 这种重载**，那是 0.x 的写法 |
| 它继承 `DocumentWriter` | 所以 ETL 的第三段不是「另写一个类」，而是**实现框架给的 writer 接口**——pgvector 在框架眼里就是一个 Writer 实现 |
| 有个 `getNativeClient()` | 接口抽象不够用时的出口。我们没用它（`JdbcTemplate` 更直接），但知道它在 |

配套的两个注解式依赖，各管一件事：

- **`spring-ai-starter-vector-store-pgvector`** → 负责把 `PgVectorStore` 装配好
- **`spring-ai-alibaba-starter-dashscope`**（本来就有）→ 顺带提供了 `EmbeddingModel` 的自动配置

**不需要为 embedding 加任何依赖**，这是本轮的第一个好消息。

## 三、三个必须处理的现实问题

这三个都是「不看源码/文档就会踩」的，也是本轮最值钱的部分。

### 1. `initialize-schema` 默认是 `false` —— 不显式打开就不建表

Spring AI 1.0 之后改的，官方文档里管这叫 **breaking change**（早期版本默认会建表）。
打开之后由它负责 `CREATE EXTENSION vector` 和建 `vector_store` 表。

所以 `docker/init-rag-db.sql` 里那句 `CREATE EXTENSION vector` **其实成了冗余保险**——
Podman/Docker 首次初始化时会执行，但它只建扩展、不建表。真正的建表在应用启动时。

### 2. DashScope embedding 接口单次最多 10 条文本

官方 FAQ 原话：

> **支持多大的批量？** 单次 API 调用最多接受 10 条文本。数据量更大时，将输入拆分为每批 10 条，分多次调用。

我们 迭代 13 切出 **19 个块**——一次全送去就是 `InvalidParameter`。

处理方式写在 `CorpusIngestor` 里：**自己控批大小**，每批 ≤10 条调一次 `vectorStore.add()`。

> **为什么不信框架代劳：** `spring.ai.vectorstore.pgvector.max-document-batch-size`
> 默认是 10000，那个数字管的是「一次插入多少行」，和「一次送给 embedding 接口几条文本」
> 不是一回事。**这类「看起来该自动、实际不会自动」的地方，是要自己去确认的**——
> 不确认就得靠实跑报错才发现。

### 3. `vector_store.id` 是 `uuid`，我们的块 id 插不进去

表结构是框架建的：

```sql
CREATE TABLE IF NOT EXISTS vector_store (
    id uuid DEFAULT uuid_generate_v4() PRIMARY KEY,
    content text,
    metadata json,
    embedding vector(1024)
);
```

而 迭代 13 的块 id 长这样：`01-销售数据统计口径说明#0`——**当主键插会直接报
`invalid input syntax for type uuid`**。

解法（见 `CorpusIngestor.toDocument`）：

```java
// 不传 id → 让 Spring AI 生成一个 uuid 当主键
// 业务 id 进元数据 → 检索出来再取回
new Document(chunk.content(), Map.of("chunk_id", chunk.id(), "source", chunk.source()));
```

然后 `VectorDocumentTool` 从元数据里把 `chunk_id` 取回来还原成 `Chunk`。

**这是个很典型的「存储层的主键约束反过来改你的数据模型」**：你以为 id 只是个标识，
直到某一天底层说「我要 uuid」。注意元数据的键名 `chunk_id` 是**读写双方约定的契约**，
所以它定义在写的那一侧（`CorpusIngestor.META_CHUNK_ID`），读的那一侧引用它。

## 四、一个容易忽略但很重要的变化：得分语义变了

`Chunk` 契约里有个 `score` 字段（迭代 8 定下时预留的）。本轮它第一次有值，但**含义完全变了**：

| | `MockDocumentTool` | `VectorDocumentTool` |
|---|---|---|
| 算的是什么 | 查询的 2-gram 有多少出现在片段里 | 1 − 余弦距离 |
| 值域 | 0 ~ 1 | 0 ~ 1（余弦距离可能略大于 1，故实际可能微负） |
| 分布 | **拉得很开**，0.0 到 0.9 都有 | **挤在一起**，大多落在 0.6 ~ 0.8 |

**所以「最高分 0.83」在两种实现下完全不是一回事，跨实现比较分数没有意义。**

这条的后果直接落在 迭代 25：原计划的「低置信度兜底」已经在 迭代 9 被排除过一轮了，
现在**相似度阈值也必须在新实现上重新标定**——不能拿 迭代 12/13 记录里的分数当标尺。

## 五、装配上的一个决定：容器里现在有两个 `DocumentTool`

主链路要换成真检索，但 迭代 8/9/12 三个历史 demo 的结论是关于**字符匹配**的
（迭代 12 那个 demo 通篇在讲「字符匹配的局限」，而那正好是 迭代 14 和 迭代 16 存在的理由）。
让它们改用向量检索，等于**拿新实现去污染历史记录**。

所以 `AgentConfig` 里现在是：

```java
@Bean @Primary
public DocumentTool documentTool(VectorStore vectorStore)          // 主链路：向量检索
@Bean
public DocumentTool mockDocumentTool(int chunkSize)                // 历史 demo：字符匹配
```

三个历史 demo 用 `@Qualifier("mockDocumentTool")` 显式指名。这也是个可复用的判断：
**契约不变时，只有装配处要改；但那些「专门演示旧实现行为」的地方，得显式点名。**
不点名就等于悄悄改了它们的语义，而这种改动不报错。

## 七、实测结果（实跑）

入库正常：19 个片段、分 2 批、耗时 1420 ms。

> 顺带一句：`PgVectorStore` 启动时会打一行 `Using the vector table name: vector_store. Is empty: false`。
> **这行容易误读**——它说的「Is empty」指的是**表名**是不是空的，不是表里有没有数据。
> 证据是我们自己的入库日志：那一刻 `count(*)` 返回 0，库确实是空的。

### 汇总

| 检索方式 | 命中期望出处 | **平均精确率** |
|---|---|---|
| 向量（pgvector） | **5/5** | 0.48 |
| 字符匹配 | 4/5 | **0.52** |

逐题明细（精确率 = 返回的片段里来自期望文档的比例）：

| 问题 | 向量 命中 / 精确率 | 字符 命中 / 精确率 |
|---|---|---|
| 销售额是怎么算的？ | 是 / 0.40 | 是 / 0.40 |
| 这个东西是怎么算出来的 | 是 / 0.20 | **否 / 0.00** |
| 华东区都包括哪儿 | 是 / 0.60 | 是 / **1.00** |
| 退款的钱什么时候扣 | 是 / 0.60 | 是 / 0.60 |
| XR-2000B 和 XR-2000C 有什么区别 | 是 / 0.60 | 是 / 0.60 |

### 发现 1（最重要）：近似编码的预言完全命中 —— 迭代 16 是必需的

```
[向量检索]  查 XR-2000B → 05-产品线与编码规则#1 （0.685307）
            查 XR-2000C → 05-产品线与编码规则#1 （0.684646）
            首个片段是否不同：相同 [X] 区分不开
            两个得分的差距：0.000662      ← 十万分之七
[字符匹配]  查 XR-2000B → 05-产品线与编码规则#0 （0.833333）
            查 XR-2000C → 05-产品线与编码规则#1 （0.833333）
            首个片段是否不同：不同 [OK] 能区分
```

**两个编码落进了同一个片段，而且得分只差 0.000662。** 对嵌入模型来说这两个串几乎就是同一个东西——
这正是 迭代 12 预言的「语义相近 ≠ 需要区分」：它们语义上确实近（都是 XR 线、都是第 2 代、都是产品编码），
而业务上必须精确区分。**迭代 16 的混合检索（保留关键词通道）不是优化，是必需的。**

这里有个**微妙但重要的细节**，值得单独记一笔：

> 字符匹配那两个得分是**完全相同**的（都是 0.833333）。
> 它能把两个编码区分开，靠的不是「分数更高」，而是**命中的是哪个片段**。
>
> 原因：它的查询串里含 `XR-2000B` 这个字面序列，2-gram 里有个 `0B`；
> 换一个字母，`0B` 变成 `0C`，能命中这个 gram 的片段就换了。
> **所以「关键词能精确区分编码」的机制是「字面串决定了命中哪一块」，不是「分数拉开了」。**
>
> 这一点 迭代 16 做融合（RRF）时必须注意：**关键词通道的价值在"排序位置"，不在"分数高低"。**
> 拿分数去加权融合会把它的优势抹掉。

### 发现 2（预判之外）：召回变好了，精确率反而略降

命中率 4/5 → 5/5 是意料之中的。**但平均精确率从 0.52 掉到了 0.48，方向是反的。**

看 `销售额是怎么算的？` 就清楚了。向量返回的 top5 是：

```
01#0 (0.7694)  06#0 (0.6979)  06#1 (0.6972)  01#1 (0.6814)  06#2 (0.6410)
      ↑ 正确          ↑ 相关但不回答问题（销售指标定义手册）
```

**第 2、3 名是 06 文档，分数还排在 01#1 前面。** 06 是「销售指标定义手册」，
讲的是各种指标的定义——和「销售额怎么算」语义高度相关，但**它不回答这个问题**。
（迭代 11 见过这件事在答案层的版本：「路由全对但答案只有六成有用」。本轮它在检索层重演了一遍。）

另一半证据在 `华东区都包括哪儿`：**字符匹配精确率 1.00，向量 0.60。**

```
字符：02#0  02#1                                    ← 只召回 2 个，都是对的
向量：02#0  02#1  02#2  06#0  04#1                  ← topK=5 填满了，后两个是噪声
```

**结论要说准：** 换向量解决的是「该找的没找到」（召回），**没解决「找到的不该要」（排序/精确率）**。
后者是 **迭代 17（rerank）** 的事，不是 迭代 16。

### 发现 3：向量的分数挤在一起，阈值这条路走不通

| 问题 | 向量第 1 名 | 向量第 5 名 | 跨度 |
|---|---|---|---|
| 销售额是怎么算的？ | 0.7694 | 0.6410 | 0.1284 |
| **这个东西是怎么算出来的** | **0.5638** | **0.5260** | **0.0378** |
| 华东区都包括哪儿 | 0.6491 | 0.3835 | 0.2656 |
| 退款的钱什么时候扣 | 0.7378 | 0.5926 | 0.1452 |
| XR-2000B 和 XR-2000C 有什么区别 | 0.7525 | 0.3647 | 0.3878 |

第 2 题最典型：**top5 全部落在 0.526 ~ 0.564 之间，跨度只有 0.0378。**
第 1 名和第 5 名的分数差 0.0378——**在这个区间设任何阈值都没有意义**，
因为「排第一的正确片段」和「排在最后的噪声片段」在分数上几乎不可分。

这条比预想的更极端。它给 迭代 25 的结论是：

> **「低置信度就不返回」这种兜底，在向量检索上比在 LLM 路由上更难做。**
> 迭代 9 已经用实测排除过「模型自评置信度」那条路；本轮是第二次——
> 相似度分数同样不能当兜底依据。**兜底得靠别的东西**（比如 rerank 之后的差距、或者干脆在生成层做）。

### 发现 4（我预判错了）：同义问法只错 1 个，不是 3 个

我在设计这个 demo 时说「字符匹配在 3 个同义问法上都会命错」。**实际只错了 1 个。**

| 问题 | 我在问句里以为的「语义鸿沟」 | 字符匹配实际表现 |
|---|---|---|
| 这个东西是怎么算出来的 | 完全不含文档用词 | **确实命不中** [OK] 预判成立 |
| 华东区都包括哪儿 | 「包括哪儿」vs「包含哪些省」 | **命中了**，还拿了 1.00 精确率 |
| 退款的钱什么时候扣 | 「扣」vs「扣减」 | **命中了** |

原因很直白：这三句里**仍然有大量的 2-gram 和文档重合**——
`华东`、`退款`、`什么` 这些词都在文档里出现过。字符匹配只要有一半的 2-gram 命中就能排上来。

**这对 迭代 15 是个直接的、可操作的启示：**

> 想真正隔离「语义 vs 字面」的差异，评测集里的问题必须做到**与文档近乎零 2-gram 重合**。
> 我这次是凭感觉挑的问句，结果只做出 1 道有效的题。
> **一道好的对照题，本身就要先量过「它和文档的字面重合度」。**

否则会得到一个虚假的结论（「向量只比字符匹配强一点点」），
而真相是**我的题目不够狠**，不是向量的优势不够大。

---

**一个必须写清的边界**：这个规模（6 份文档、19 个片段、5 个问题）**只够看出方向，不够下结论**。
上面所有数字都带这个前提。真正的量化是 迭代 15 的事。

## 八、局限

1. **语料只有 6 份、111 个块。** 这个规模下向量检索和字符匹配的差距**可能不明显**——
   字符匹配在「字面重合」上本来就不差，而向量检索的优势要在**同义改写、口语化、跨表述**
   这类查询上才显现。5 个问题也太少。
2. **`text-type` 用的是一个模型走两边。** DashScope 建议查询侧用 `query`、文档侧用 `document`
   以优化质量，但 `PgVectorStore` 内部对「存」和「查」用的是同一个 `EmbeddingModel` 实例，
   所以两边拿到的都是默认的 `document`。要做区分得自己包一层——记为 迭代 22 的候选优化项。
3. **相似度阈值还没设。** 现在是「不管多低都返回 top-K」。等 迭代 15 有了评测集，
   才谈得上「低于多少分就不该进材料」。
4. **元数据过滤还没用上。** `SearchRequest` 支持 `filterExpression`（比如只在某几份文档里搜），
   迭代 17 做重排/MMR 时可能会用到。
