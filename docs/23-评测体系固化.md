## 二、六类指标，一张表

| 指标 | 问的是 | 谁负责 |
|---|---|---|
| **路由准确率** | 四值分类对不对（原创指标） | `expected_route` vs 实际 |
| **路由混淆矩阵** | **谁被错分成了谁** | 见下 |
| 检索指标 | context 精确率 / 召回率 | `LlmJudge` + 文档层 |
| 生成指标 | faithfulness / answer_relevancy | 框架两个 Evaluator |
| **执行准确率** | 数据库支路：查出来的数据对不对 | `util/Amounts` 数值比对 |
| **端到端正确率** | 用户视角：最终答案对不对 | `LlmJudge.gradeAnswer` |

### 为什么「混淆矩阵」比「准确率」值钱

一个 `0.89` 不告诉你错在哪。矩阵会：迭代 15 那 3 处错**全都掉进同一个方向**，
而按 迭代 25 的代价分析，**那恰恰是最坏的那个方向**（`document → database` 会产生用户察觉不到的假数字）。

所以报告里除了矩阵，还单独点出一格：

```
★ 最该盯的一格：document→database = N 条（会产生用户察觉不到的假数字）
```

**准确率是一维的，失败模式不是。**

## 三、一条命令做了什么

```
28 条用例
  ├─ 链路 1：agent        → 跑全部 28 条（要算路由准确率与混淆矩阵）
  └─ 链路 2：basic-rag    → 只跑 document 用例（它没有路由能力，硬跑是在评它做不到的事）
```

产出三样：

- **控制台大表**：六类指标 + 混淆矩阵 + 按 category 分组 + agent vs basic-rag 对照；
- **`eval/report.md`**：同一份内容，Markdown，**可直接贴进 README**（每次覆盖，是「当前状态」）；
- **`eval/report.csv`**：一行一次报告（含矩阵的紧凑串），**留历史做对比**。

两处刻意的设计，都是 迭代 15 教训的延续：

- **拒答不花模型调用**：`refuse` 用例上期望路由与实际路由都是 `refuse` 时，直接判对，
  不再问一次模型「这个答案对不对」。
- **答案原文只在两种情况打**：两个判分器打架，或答案未满分。没有这行日志，
  迭代 15 那个「参数传错」就会被误解释成「框架判得太严」并写进文档。

## 四、顺手做的去重：量具只能有一份

写报告时发现两样东西会被用到第二次，于是收成一处：

### 1. `util/Amounts` —— 数值量具

「执行准确率 = 期望答案里的大额数字能否在结果里找到」这条判据，迭代 22 写在
`Text2SqlEvalDemo` 里，本轮的报告要用同一套。**两份各留一份，迟早漂移——
而它是量具，漂移了不会报错，只会给出一个错的准确率。**
（同 `DocumentChunks`（迭代 17）、`Vectors`（迭代 19）的理由。顺带把 迭代 22 那批调用点也指了过来，
并带上那次「小数位被当成大数字」的边界 bug 的修复说明。）

### 2. `eval/JudgeLoggingAdvisor` —— 框架判分器的日志口

```java
// 为什么非要有它：两个框架 Evaluator 内部都是拿模型回答跟 "yes" 做精确比较，
// 然后把原始输出【丢掉】。它们坏了不报错，只会给出一个错误的分数。
```

迭代 15 就靠它才看出「自写判分 1.00、框架忠实性 0.00」是**参数传错**而不是「框架判得严」。
现在报告也用它，于是从 `EvalRunner` 的内部类抽成了独立类。

> **`EvalRunner` 保留着没删**——它产出的是 `metrics.csv` 的 `exp15-baseline` 历史行。
> 报告是它的接任者，但旧基线要能复现这条纪律不破。**两个不要同时开。**

→ **证明第 4 节的量具抽取没有改变行为**（这正是「量具只能有一份」要防的事）。

**② 端到端正确率 0.71 里混着两个来源，不能都算在系统头上。**
掉分的用例：D10/D14（**路由错**）、B02/B03/X04（**题面缺时间范围**，迭代 22 发现 2 的测试集缺陷）、X02/X03。

**③ 可疑值报警按设计触发了两条，而且都对上了已知结论。**
```
[可疑] 指标 faithfulness 在 28 条用例上都是 1.00
[可疑] 指标 answer_relevancy 在 28 条用例上都是 1.00
```

**④ 一个离群点**：basic-rag 在 D12（「每个订单平均贡献多少钱」）**跑了 37 秒、答案 2939 字**，

## 六、路由修正：让它读「我手上有什么」（已实施，待重跑对比）

### 6.1 为什么修它 —— 基线的混淆矩阵把它指得很清楚

基线跑出 3 处路由错，**全部从 document 掉出去，且和 迭代 15 是同样那三道**。逐条看模型给的理由，
病根是同一个：

| 题 | 期望 | 实际 | 模型给的理由 | 真相 |
|---|---|---|---|---|
| **D10** | document | refuse | 「超出两个数据源覆盖范围」 | 在语料 **05 产品线与编码规则** |
| **D12** | document | database | 「属于具体数值计算，答案在业务数据中」 | 在语料 **06 销售指标定义手册**（客单价定义） |
| **D14** | document | refuse | 「属于通用地理常识，不在范围内」 | 在语料 **02 销售区域划分规则** |

**三条都是「模型断言手上没有，而其实有」。** 它为什么会这么断言？因为提示词里那份
「数据源能力」清单是**手写的、而且早就过期了**：

- 文档库只列了 **4 份**（实际 **6 份**）——漏掉的两份正好是 D10/D14 的出处；
- 业务库写着「**订单表**，含区域、订单金额、退款金额、状态、完成时间等字段」——
  **那是 5 张表时代的描述**，现在有 20 张。

> **手写的清单会悄悄过期，而它一过期，路由就开始凭印象判「我手上没有」。**
> 这是「不响的错」在提示词里的一种形态——没有任何一处会报错。

### 6.2 改法：清单从真实来源读

`LlmQueryRouter` 现在接一个 `Supplier<String>`（懒加载），由 `AgentConfig.describeDataSources` 提供：

```
- 文档库，共 6 份：
    · 销售数据统计口径说明 / 销售区域划分规则 / 售后与退货管理流程 /
      数据仓库使用说明 / 产品线与编码规则 / 销售指标定义手册
- 业务数据库，共 20 张表：
    · channels / customers / employees / ...（真实表名）
（以上两份清单都是完整的。清单里没有的资料，才算「我手上没有」。）
```

语料清单来自 `CorpusLoader`、表清单来自 `SchemaRenderer`——**两边都是运行时读的，不会过期**。
提示词里另加了一条判断要点：

> 3.【判 refuse 之前，务必先逐条对照上面的清单】——清单里有的资料，就不该判 refuse。

### 6.3 两处降级（都不影响路由能不能工作）

1. **读不到清单**（业务库没起）→ 退回一句静态描述 + **打日志**；
   **只缓存成功**，所以业务库晚点起来还能自愈。
2. **LLM 调用失败** → 照旧降级到关键词路由。

### 6.5 对比结果：**预判被推翻 —— 修好一条、弄坏一条，净效果 0**

重跑一次（`eval/report.csv` 现在有两行）：

| 指标 | 基线 | 改后 | |
|---|---|---|---|
| **路由准确率** | **0.89 (25/28)** | **0.89 (25/28)** | **没动** |
| 端到端正确率 | 0.71 | 0.71 | 没动 |
| 执行准确率 | 0.38 (3/8) | 0.38 (3/8) | 没动 |
| 检索精确(LLM) | 0.70 | 0.69 | 噪声内 |
| 平均耗时 | 5379 ms | 5956 ms | 提示词变长了一点 |

**我预判「0.89 → 1.00」，`document→database` 归零 —— 两条都错了。**
逐题看才知道为什么：

| 题 | 基线 | 改后 | 说明 |
|---|---|---|---|
| **D10** | refuse | **document** ✅ | **修好了**：理由改成「文档库中《产品线与编码规则》是权威来源」 |
| D12 | database | database | 没变（它考的是「定义 vs 数字」的语义判断，清单帮不上） |
| D14 | refuse | refuse | 没变（理由变成「《销售区域划分规则》未包含历史沿革信息」—— **更"有理"了，但结论没变**） |
| **D15** | document ✅ | **refuse** ❌ | **新坏的**：理由「清单中无直接对应的技术 SLA 或实时性说明文档」 |

净 +1 −1 = 0。

#### ★ 为什么 D10 修好了而 D15 反而坏了 —— 一个比「修没修好」更值钱的结论

**清单给的是「标题」，不是「覆盖范围」。**

- **D10 的答案**在《产品线与编码规则》里——**标题恰好提示了内容** → 模型一对照就找到了 → 修好。
- **D15 的答案**在《数据仓库使用说明》里（T+1、凌晨 3 点全量刷新，所以查不到一小时前的单）——
  **标题不提示「实时性 / 数据延迟」** → 模型带着标题逐条找，找不到一份"像"的，于是**更有底气地拒答**。
- **D14 同理**：《销售区域划分规则》里有「2025 年起福建由华南划归华东」，
  但标题不提示「历史沿革」→ 结论照旧拒绝，只是理由变得更像那么回事。

**所以：给清单既治「凭空断言手上没有」，也可能加重「按名字找、名字不对就断言没有」。**
两个方向的错其实是同一个病根的两面——**模型只能凭「名字」判断手上有没有，而不是凭「内容」。**

#### ★★ 方法论：**连混淆矩阵都看不见这次换血**

两行的混淆矩阵**逐格相同**：

```
document 行：12 [OK] | 1 | . | 2      ← 两次完全一样
```

**格子的计数一样，只是「哪道题坐在格子里」换了。**
准确率看不出来、矩阵也看不出来——**只有逐题明细能看出来**。
（基线是 D10/D12/D14 错，改后是 D12/D14/D15 错。）

**但分组能看出来**：

| 分类 | 基线 | 改后 |
|---|---|---|
| 精确编号（D10） | 0.00 | **1.00** |
| 语义（7 条，含 D14/D15） | 0.71 | **0.57** |

→ **「评测要分层」本轮第四次兑现：分组比总数更早暴露换血。** 只报一个总分的评测，
会把「一条修好、一条弄坏」读成「什么都没发生」。

#### 这次修正要留吗？**留着，但要说清它值什么**

- **留着的理由**：它删掉了一份**确定已经过期**的硬编码清单（提示词里写着「订单表，含…」，
  而实际是 20 张表）。**结构上更对——不再有会悄悄过期的东西。**
- **但要说清**：**实测收益为零**。而「更对」和「更有用」是两件事，这次就是一次实证。
- **真正该做的下一步**（归 迭代 24「路由 v2」）：清单里**不是只写标题，而是写标题 + 一句内容提示**
  （如「《数据仓库使用说明》——含数据刷新频率 / T+1」）。这样 D14/D15 那种「内容在、标题不提示」
  的题才有救。**这是个具体的、可验证的假设，正好拿 迭代 24 的多策略对比来量。**

## 七、局限与诚实边界

- **`answer_relevancy` 已知区分度低**（迭代 15：43 次判分只否 1 次），报告里保留只作透明，别用它下结论。
- **判分噪声有量级**：同一输入送两次可差 0.20（=1 个片段/5）→ 15 条上的平均差异 **<0.05 不可区分**。
- **路由准确率自身有噪声**：28 条上 **±1 条 ≈ 0.036**，小于 2 条（0.07）的提升不可声称。
- **执行准确率受题面歧义影响**：只取 database/both 的 8 条，其中 B02/B03/X04 题面没写时间范围
  （见 迭代 22 发现 2）——**这 3 条会拉低这个数，读的时候要知道**。
- **报告不覆盖支路级 A/B**（混合检索 / 重排 / 表筛选 / few-shot 消融）——
  那些是 迭代 26 的消融表，本轮只做「当前系统整体什么水平」这一张。
