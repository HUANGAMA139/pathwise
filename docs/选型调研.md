# 选型调研：为什么这个项目没走 fork 路线

> 调研时间 （迭代 1 前后）。**许可证与仓库状态会变，动手前请重新确认。**
>
> 这份文档回答两个问题：**「让 Agent 自己决定走文档检索还是数据库查询」这件事，开源里到底有没有现成的？** 以及 **「如果有，能不能拿过来用？」**

---

## 一、开源里有没有现成方案

结论：**没有。** 三类项目各占一半，没有一类在做「该走哪条路」这个决策。

| 类别 | 代表项目 | 它们实际怎么做的 |
|---|---|---|
| **数据问答类** | SQLBot · WrenAI · DB-GPT · spring-ai-alibaba DataAgent · SuperSonic | 本质都是 **Text2SQL**。里面的 RAG 组件**只用来召回表名和术语**——它是「让 SQL 写得更准」的手段，**不是独立的文档问答支路** |
| **RAG 类** | RAGFlow · Spring AI 官方 rag-example | **完全不碰 SQL**。能给你一段口径定义，但给不出数字 |
| **多引擎路由** | LlamaIndex `RouterQueryEngine` + `NLSQLTableQueryEngine` | **唯一原生做多引擎路由的范式**，但只有 Python 版，**Java 侧没有等价物** |

### 这对本项目意味着什么

对使用者来说这是个缺口；对作者来说这是个机会——**空白意味着「路由决策」和「双路评测」天然属于原创部分**，而不是把别人的东西重写一遍。

两个具体的差异点：

1. **四值而不是二值。** 上面的项目即使碰到「两边都要」的情况，也没有一个显式的 `both` 出口；更没有 `refuse`（明确拒答）这个状态。**二选一的题，模型永远能选出一个答案，哪怕答案是错的。**
2. **评测把路由当作一等公民。** 四值路由直接就是测试集的 `expected_route` 标注列，所以「路由准不准」是**确定性**的、没有判分噪声，而且能出混淆矩阵看**错在哪**。同类项目通常只报一个端到端的准确率。

## 三、为什么是「自研主干 + 参照架构」，不是 fork

考虑过直接 fork `spring-ai-alibaba/DataAgent` 再改造。**放弃了**，两个原因：

**1. 反对改名式套壳。**
DataAgent 知名度高，fork 过来改个名很容易被面试官或读者识破。更重要的是——**那样学不到东西**。把别人的结构重命名一遍，你得到的是「我读懂了它」，不是「我知道为什么这么设计」。

**2. 它的赛道和本项目不同。**
DataAgent 本质仍是 Text2SQL。它没有「文档支路」这个概念，也就没有「路由节点」。**要做的是在它的思路上补两样它没有的东西**，而不是改它的名字。

### 具体参照了什么

| 来源 | 参照的内容 | 本项目怎么用 |
|---|---|---|
| `spring-ai-alibaba/DataAgent`（Apache-2.0） | StateGraph 编排 · RAG 增强 · HITL · MCP Server 暴露方式 | **只读架构，未复制代码。** 在它的思路上补上**文档工具分支**与**路由决策节点** |
| `spring-ai-alibaba/examples`（Apache-2.0） | `nl2sql` · `rag` · `tool-calling` · `graph` · `evaluation` 五个示例模块 | 用途是「**这三件事该怎么用 Spring AI Alibaba 的 API 做**」——**具体实现全部重写** |

> **一句话**：参照的是**「这类系统该怎么搭」**，不是**「这段代码该怎么写」**。

---

## 四、范围围栏（明确不做的事）

写在选型阶段的「不做」，避免项目无边界膨胀：

- **GraphRAG / Text2Cypher** —— 和「路由决策」这条主线无关
- **微调** —— 本项目的兴趣点在**系统设计**，不在模型训练
- **多智能体** —— 单 Agent + 双支路已经足够暴露问题
- **前端美化 / 云原生部署** —— 不是这个项目的验证目标
