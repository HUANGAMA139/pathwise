## 〇、先说清「学」的那两个例子，以及为什么没有照抄

计划里给了两个 spring-ai-alibaba 的例子。我把两个的 pom 都拉下来看了：

| 例子 | 它实际用的东西 | 本项目怎么办 |
|---|---|---|
| `spring-ai-alibaba-observability-example` | 一个多模块工程：`observability-example` / `-arms` / `observationhandler` / `-langfuse`。核心是 **Micrometer**（`Timer`、`LongTaskTimer`、`TracingObservationHandler`）+ **`micrometer-tracing-bridge-brave`** + **`zipkin-reporter-brave`** + `spring-boot-starter-actuator`，跑起来还要一个 **Zipkin 容器** | **只借它的「思路」，不借它的栈。** 见下面「为什么自建轨迹」 |
| `spring-ai-alibaba-chat-memory-example` | `spring-ai-alibaba-starter-memory` / `-memory-jdbc` / `-memory-redis` 三个 starter，外加 sqlite / jedis / mysql 驱动，演示多种会话存储后端 | **一个都不引。** 本项目 迭代 4（`ContextCompactor`）+ 迭代 28（`ConversationalAgent` + `ChatSummarizer`）已经有自己的多轮机制，缺的不是能力，是「没接进对外服务」 |

**为什么 observability 那个例子不能照搬**：它很强，但它解决的是「多实例、跨服务、要看分布式链路」的场景。
本项目是**单进程、单实例**，引入 Zipkin 容器 + Brave 桥 + 一整套跨度体系，
换来的是一张漂亮的水位图，代价是**每次启动多一个要维护的容器、多三个要对齐版本的依赖**。
而本轮真正缺的东西很小：**一次提问的每一步，能按请求收拢成一份东西打出来、并且回给调用方。**
——这个用 4 个小类（共约 200 行）就做到了，零新依赖。

> 这不是「不用现成轮子」，是**先想清楚轮子解决的是哪个问题**。
> 判据和 迭代 16 手写 BM25、迭代 17 手写 MMR、迭代 21 手写 `SqlGuard` 一样：
> **需求只有三条（按请求收拢 / 带耗时 / 能返回），引一个框架的成本大于收益。**

**为什么 chat-memory 那三个 starter 不引**：它们的价值在于**把会话持久化到 JDBC / Redis**。
本项目现在会话在内存里——这是**有意的**（单机演示够用），而且**换掉它只需要改一个类**
（`web/SessionStore`：把 `ConcurrentHashMap` 换成 Redis/JDBC）。
在还没需要持久化的时候引三个 starter，只会多三套版本矩阵要维护。

## 一、日志追踪 → **结构化轨迹**

### 1.1 先承认：日志其实早就打全了

迭代 28 那天的日志里，路由选了哪条、检索到几段、SQL 是什么、材料多少字——**全都打出来了**。
所以本轮要解决的不是「没有日志」，而是日志的两个固有毛病：

| 毛病 | 具体表现 |
|---|---|
| **散** | 一次提问的痕迹散在几十行里，还夹着别的请求；想看「这次到底走了哪几步、每步多久」得拿时间戳去拼。并发一来就拼不出来了 |
| **不出去** | 轨迹只进控制台。**外部调用方拿到的只是一个孤立答案**——`ask_data_question` 原来只回「路由决策 + 答案」，SQL 和片段全留在服务端 |

### 1.2 做了什么

新增 `trace/` 四个类（约 200 行，**零新依赖**）：

| 类 | 干什么 |
|---|---|
| `TraceStage` | 阶段枚举：路由 / 文档检索 / 数据库查询 / 拼材料 / 模型综合 / 拒答。**用枚举不用 String**，理由同 `RouteDecision.Route`：拼错要在编译期暴露 |
| `TraceStep` | 一步：阶段 + 证据摘要 + 毫秒 |
| `TraceRecorder` | 收集器。`timed(...)` 量一段记一步，**抛异常时也记一笔再抛**——「哪一步炸的、炸之前跑了多久」正是排查最需要的 |
| `Trace` | 不可变结果：`requestId` + 各步 + 总耗时（+ `cached` 标记）。`render()` 可直接打日志，也可直接进响应体 |

插桩点全在 `SmartQaAgent` 里，一共 5 处（就是原来那 5 条 `log.info` 的位置）：

```
  ├─ 路由         2051 ms  document (1.00) —— 理由：问题明确询问…
  ├─ 文档检索      925 ms  topK=10 → 10 段（来源：06,01,03）
  ├─ 数据库查询     18 ms  1 行  SQL: SELECT SUM(order_amount - COALESCE(refund_amount, 0)) AS net_sales…
  ├─ 拼材料         0 ms  材料 1751 字（含出处）
  └─ 模型综合     6002 ms  答案 210 字
```

**`detail` 写的是「证据摘要」，不是「执行成功」这种哪一步都成立的话**——
迭代 4 那条原则：中间产物是错误放大器，最终答案坏了，你得能一眼看出是哪一步先偏的。

### 1.3 契约动了哪一处

`SmartQaAgent.Answer` 加了最后一个字段 `Trace trace`。

**为什么加在最后一位**：`Answer` 从 迭代 8 起就叫「完整轨迹」，但只带了**结果**（决策/片段/SQL/答案），没带**过程**。
现在把过程补上。加在末尾之后，所有读 `decision()`/`chunks()`/`dbResult()` 的老代码（迭代 15/23/28 的评测）**一行都不用改**。

改构造点只有一处文件：`SmartQaAgent` 内部那 4 个 `new Answer(...)`（静态检查的「构造参数个数」那一类正好守着它）。

### 1.4 MCP 那条路也一起补上了

`ask_data_question` 的返回值从「路由决策 + 答案」变成 **「路由决策 + 答案 + 本次轨迹」**。
外部系统（Claude Desktop、别人的 Agent）拿到的因此是一个**可核对**的东西，
而不只是一个「信不信由你」的结论——这是 迭代 8 定 `QueryResult.sql` 那条原则的延伸：
**从「答案里附 SQL」扩成「整条链路可回带」。**

## 二、缓存 —— **本轮最重要的一个设计决定：缓存放哪一层**

需求很直白：**相同问题不重复调模型**。

### 2.1 最省事的做法，正好是错的

最省事是把缓存塞进 `SmartQaAgent`——那样所有调用方自动受益。

**但那会毁掉历史基线。** 迭代 15 / 23 / 28 的评测**全部直接调 `SmartQaAgent`**。
缓存一旦进了 Agent，评测就会命中缓存：耗时变了、端到端可能也变了，
**而且不会报任何错**——项目从 迭代 14 起一直在守的「旧基线一键复现」当场失效。

### 2.2 所以缓存放在服务层

```
  REST /chat ─┐
              ├─→ QaService（查缓存 → 未命中才调 Agent → 回填）─→ SmartQaAgent
  MCP 工具   ─┘                                                  ↑
  迭代 15/23/28 的评测 ───────────────────────────────────────────┘（直接调，永远不带缓存）
```

**缓存本身没变，只是换了位置：评测走不到它，线上用得到它。**
这就是「同一件事放在哪一层，决定了它会不会变成一个不响的错」。

### 2.3 实现（手写，不引 Caffeine）

`service/AnswerCache`，约 120 行：TTL 过期 + 容量上限（最久没存进来的先走）+ 命中率统计。
`key` 只做一层归一化（去首尾空格、连续空格压成一个）——
**再往下（去标点、改词序）就开始改变语义了，那是改写器的活，不是缓存该干的事。**

三条边界写在类注释里：

1. **只该被服务层用**（理由见上）；
2. **内存缓存，重启即失效**——改了语料或表结构之后旧答案就过期了，**这一步没有自动检测，靠重启**；
3. **拒答也缓存**——拒答同样要一次路由调用，缓存它一样省钱。

## 三、多轮对话 → 接进 REST `/chat`

### 3.1 迭代 28 做了一半

迭代 28 造出了 `ConversationalAgent`（会话改写消解指代）+ `ChatSummarizer`，
但**它只有 demo 在用**——对外服务还是单轮直调 `SmartQaAgent`。
本轮补的就是这一环。

### 3.2 新增的接口

| 方法 | 作用 |
|---|---|
| `POST /chat` `{"question": "..."}` | **单轮**，走服务层 → **有缓存** |
| `POST /chat` `{"sessionId":"abc","question":"它的分母为什么…"}` | **多轮**，走会话表 → 指代消解 + 上下文压缩 |
| `DELETE /chat/{sessionId}` | 结束会话（客户端想「重新开始」） |
| `GET /health` | 健康检查 + **缓存命中率 + 会话数**（Docker 的 healthcheck 打它） |
| `GET /` | 用法说明 |

`web/SessionStore` 三个取舍写在类注释里：**内存（重启即清空）**、
**有上限（最久没用的先回收，否则「每次带一个新 sessionId」就是内存泄漏入口）**、
**同会话串行（`synchronized`——多轮本来就有顺序语义）**。

### 3.3 两个「为什么不」

**为什么 MCP 不做多轮**：MCP 的工具调用语义接近无状态单发；
要它带会话就得在工具签名里塞 sessionId、还得让客户端自己维护——
**多轮有自己的正确归宿（HTTP 会话），不该硬塞进工具协议。**

**为什么多轮不缓存**：改写后的自足问题确实是会话无关的，按它做 key 技术上可行；
但那样省下的只是一次综合调用（**改写本身仍要调模型**），收益小、语义却更容易错
（同一句话在不同会话里指代不同，改写一旦有偏差就会张冠李戴）。
**这是有意的范围选择，不是漏了**——写在 `ChatController` 的类注释里。

## 四、Docker —— 一条命令起服务

### 4.1 三个文件

| 文件 | 作用 |
|---|---|
| `Dockerfile` | 多阶段：`maven:3.9-eclipse-temurin-17` 编译 → `eclipse-temurin:17-jre` 运行。最终镜像里没有 Maven、没有源码 |
| `.dockerignore` | 挡掉 `target/`、`.git/`、`backup-*.sql` 等 |
| `docker-compose.yml` | 新增 `app` 服务 |

```powershell
# 只起两个库（= 你以前的行为，一点没变）
docker compose up -d

# 一条命令起「应用 + 两个库」
docker compose --profile full up -d --build
```

### 4.2 为什么把 app 放进 profile 而不是直接加进 services

你现在的习惯是**从 IDE 跑应用**、只用 compose 起两个库。
如果把 `app` 直接加进去，`docker compose up -d` 就会变成「连应用一起 build 起来」——
**把你原来的用法悄悄换掉了**。放进 `profiles` 之后，两种用法各归各位，还不用记第二个 compose 文件。

### 4.3 四个容易踩的点（都已处理）

1. **容器里的 `localhost` 指容器自己。** 所以环境变量里必须写**服务名**：`jdbc:postgresql://pgvector:5432/...`。本项目的数据源早就走 `${SDAQ_*}` 环境变量了，所以这里只要覆盖，代码一行不用改。
2. **必须等库真的能连再起应用。** `depends_on` 配的是 `condition: service_healthy`——不等的话，应用一启动就去建 `vector_store` 表，必然失败。
3. **`AI_DASHSCOPE_API_KEY` 故意不给默认值。** key 只存在宿主机环境变量里，**绝不落进 compose 文件**。没设的话 compose 会警告并留空，应用启动时才报错——比在文件里写个假占位串好。
   （⚠️ 这里**不能用** `${VAR:?err}` 那种写法：compose 在解析阶段就会替所有服务展开变量，**连不带 profile 的 `docker compose up -d`（只起库）都会因此失败**，那等于把老用法弄坏了。）
4. **显式设 UTF-8。** 日志/语料/提示词全是中文。容器默认 locale 不是 UTF-8 时控制台会乱码，而**它不影响程序运行**——正是那种「不响的错」。设了三处：`LANG` / `LC_ALL` / `-Dfile.encoding=UTF-8`。

**另外故意没做的一件事**：没有做「先拷 `pom.xml` 拉依赖」那一层构建缓存。
那样确实能让改代码时不重下依赖，但 `mvn dependency:go-offline` 在多仓库
（本项目 pom 里配了 aliyun 仓库）场景下**会偶发失败**，
而我**没法在本地验证它到底成不成**——所以宁可放弃这层优化，换一个「肯定能跑通」的构建。

### ② REST —— ✅ **已实跑**，并**抓出一个「不响的错」**

> **先避一个坑**：别用 `curl`。Windows PowerShell 5.1 里 `curl` 是 **`Invoke-WebRequest` 的别名**，
> 不是真 curl，`-s` / `-H` / `-d` 会直接报参数不存在。要么写 `curl.exe`（带后缀），要么用下面的原生写法。

```powershell
# 多轮第 1 轮：埋下「客单价」
$b = @{ sessionId="demo"; question="客单价怎么算？" } | ConvertTo-Json
Invoke-RestMethod -Uri http://localhost:8080/chat -Method Post -ContentType "application/json; charset=utf-8" -Body ([Text.Encoding]::UTF8.GetBytes($b))

# 多轮第 2 轮：用「它」回指 —— 看返回里的 .standalone
$b = @{ sessionId="demo"; question="它的分母为什么必须用已完成订单数？" } | ConvertTo-Json
Invoke-RestMethod -Uri http://localhost:8080/chat -Method Post -ContentType "application/json; charset=utf-8" -Body ([Text.Encoding]::UTF8.GetBytes($b))
```

`[Text.Encoding]::UTF8.GetBytes($b)` 这一段**别省**：PS 5.1 发字符串 body 默认按 ISO-8859-1 编码，
**中文会变成 `?`**，而且服务端不报错，你只会看到一个答非所问的回复。

**实跑结果（摘录，取自加 charset 之后的干净那一跑）：**

