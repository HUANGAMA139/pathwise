# 迭代 21 · SQL 安全边界

> 目标：让「模型生成的 SQL」不能为所欲为——只读白名单 · 禁 DDL/DML · 行数上限与超时 · 敏感字段脱敏。
> 新增：`tools/text2sql/SqlGuard`（准入）· `ColumnMasker`（出参）· `agent/SqlSafetyDemo`（测试用例）
> · `docker/init-business-db-ro.sql`（只读账号）
> 改动：`Text2SqlDatabaseTool`（护栏接入 + **故障注入挪到护栏之前** + 脱敏 + 语句级行数上限）· `BusinessDb`（超时留连接层；行数上限搬走）
> 开启方式：
> ```
> mvn spring-boot:run "-Dspring-boot.run.arguments=--sdaq.exp21.enabled=true"
> ```

---

## 一、为什么这一节面试加分

在此之前，我一直在让这个系统**更准**。本轮让它**更安全**。

区别在于：**准确率可以差一点，安全不能差一点。**

而这一节的分量在面试里比功能本身大，理由很直接：
**能主动想到「让模型生成 SQL 必须有安全边界」，体现的是生产意识，而不是「我照着教程跑通了」。**
很多人的项目停在「能跑」——数据问答能出个数，然后就没有然后了。
面试官问「你这个项目有什么风险」，答不出东西，和答得出这四层，是两种人。

**这个项目里唯一真正危险的操作，就是把模型生成的字符串直接丢给数据库执行。**
前面所有的评测、消融、对比，都在优化「它有多大概率写对」；
本轮要处理的是「它写错的时候，最坏能坏到哪」。

## 二、四层防御（本文的骨架）

| 层 | 在哪 | 做什么 | 状态 |
|---|---|---|---|
| ① 提示词 | `Text2SqlDatabaseTool.SYSTEM_PROMPT` | 告诉模型只输出 SQL、只能用给定的表 | 迭代 18 起 |
| ② **应用层准入** | **`SqlGuard`** | 白名单 + 禁 DDL/DML + 拒多语句 + 危险函数 | **本轮** |
| ③ **数据库权限** | **`docker/init-business-db-ro.sql`** | 只读账号，只有 SELECT | **已建好并切过去了**（`sdaq.business-db.username = sdaq_readonly`） |
| ④ 实例隔离 | `docker-compose.yml` | 业务库和向量库是两个库，业务库里没有向量数据 | 迭代 18 起 |

另有两层只管「出」和「资源」，和上面正交：

| 关注点 | 在哪 | 做什么 |
|---|---|---|
| 出参 | `ColumnMasker` | 结果里的敏感列打码 |
| 资源 | `BusinessDb` + `Text2SqlDatabaseTool` | 超时（连接层）+ 行数上限（**语句层** —— 配在连接层会截断元数据，见第六节） |

> **【本轮最重要的一句】应用层这一层是可以被绕过的，所以它不该是唯一一层。**
> **纵深防御的意思是「假设每一层都会被绕过」，而不是「我这一层写得够好」。**

## 三、第 ② 层：准入护栏的五条规则

`SqlGuard.check(sql)` 回答一个问题：**这条 SQL 准不准跑。**

| 规则 | 拦什么 |
|---|---|
| 1. 白名单 | 只放行 `SELECT` / `WITH` 开头 |
| 2. **整句扫黑名单** | `INSERT/UPDATE/DELETE/DROP/CREATE/ALTER/TRUNCATE/GRANT/…` 出现在**任何位置**都拒 |
| 3. 拒多语句 | `SELECT …; DROP …` 是经典组合 |
| 4. 拒 `SELECT … INTO` / `FOR UPDATE`、`FOR SHARE` | 前者会建表，后者会加锁 |
| 5. 危险函数黑名单 | `pg_sleep`（睡死库）/ `pg_read_file`（读服务器文件）/ `pg_terminate_backend`（掐连接）等 |

### 最容易被忽略的那个洞：白名单**不能只看第一个词**

这条值得单独说，因为它看着像对的、实际能绕过：

```sql
WITH d AS (DELETE FROM sales_orders RETURNING *) SELECT * FROM d
```

首词是 `WITH`，一个「只看开头」的白名单会**高高兴兴地放行**——然后表就被删了。
**所以白名单（看开头）和黑名单（扫整句）必须同时有，缺一不可。**

### 一个把「误报」和「漏报」同时解决掉的动作

判定之前**先把字符串字面量和注释挖掉**，只留「会真正执行的部分」。

```java
先剥字符串，再剥注释   [对]
先剥注释，再剥字符串   [错]   // 字符串里的 '--' 会被当成注释起点，吃掉半条语句
```

**这个顺序坑和 迭代 13 写 Java 静态检查脚本时踩的是同一个**——那次也是先剥注释、
结果 `"classpath*:corpus/*.md"` 里的 `/*` 被当成块注释起点，吃掉了半张文件。

挖掉之后两头都对了：

- **不误报**：`WHERE status = 'DELETED'` 里的 DELETED 在字符串里；`-- DROP 很危险` 是注释；
  `created_at` 里的 `create` 因为 `\b` 把下划线当词字符而匹配不上。
- **不漏报**：`/* x */ DROP TABLE t` 里 DROP 在注释**外**，照样看得见。

## 四、第 ② 层的边界：它拦不住什么（诚实版）

**这一节比上一节重要。** 不写它，就等于在暗示「我这层是完备的」。

`SqlGuard` 已知挡不住的：

| 缺口 | 后果 |
|---|---|
| PostgreSQL 的 **dollar-quoting**（`$$ … $$`） | 扫描器只认 `'…'` 和 `"…"`，会把 `$$` 里的内容当成真实代码 → **误报**（把合法查询拦下），不会漏放 |
| `E'…'` 里的**反斜杠转义** | 同上 |
| 任何我没想到的新写法 | 未知 |

注意这两个已知缺口的后果都是**误报**而不是漏放——因为它们让扫描器「多看见」了关键字，
不是「少看见」。这是**刻意选的偏向**：宁可错杀，不可放过。

**但这仍然意味着：不能把第 ② 层当成最后一道防线。**

## 五、第 ③ 层：只读账号（真正硬的那一层）

`docker/init-business-db-ro.sql`：建一个只有 `SELECT` 的账号 `sdaq_readonly`，
并且显式 `REVOKE` 掉写权限、序列权限、建表权限。

**为什么这一层比应用层硬**：应用层是「我判断你不能写」，数据库权限是「你**做不到**写」。
前者依赖我的代码没有洞，后者不依赖任何东西。

启用只需要一行配置（应用侧只做 SELECT，换账号照样跑）：

```yaml
sdaq.business-db:
  username: sdaq_readonly
  password: sdaq_ro_pwd
```

应用方式（对已经在跑的库，`psql -f` 即可，**不用清数据卷**）：

```
docker compose cp docker/init-business-db-ro.sql business-db:/tmp/init-business-db-ro.sql
docker compose exec business-db psql -U sdaq -d business_db -f /tmp/init-business-db-ro.sql
```

> 顺带一句：这个脚本**不建表、不改任何表结构**，所以它不会影响 迭代 18 的基线。
> 只有「扩表」和「改表注释」那类动 schema 的操作才会毁基线（见 迭代 20 第七节）。

## 六、资源上限与脱敏：三个容易做反的地方

### 1. 行数上限要配在【语句】那一层 —— 不是连接层，更不是提示词层

```
text2sql.max-rows           执行上限（PreparedStatement.setMaxRows，语句级截断）
text2sql.max-context-rows   进 prompt 的上限（防上下文爆）
```

**为什么不能「查回来一万行再丢掉九千九百行」**：内存已经吃过了，丢掉只是掩饰。
上限必须在**驱动**那一层生效，行根本不被拉回来。

**但「驱动层」不等于「连接层」——这个区别是实跑打脸打出来的。**

我第一版把 `setMaxRows` 设在整个 `JdbcTemplate` 上（连接级）。跑出来是这样：

```
元数据读取完成：5 张表 / 5 列 / 3 条外键      ← 本该是 26 列
```

**它把元数据查询也一起截断了。** 上限调成 5 的时候，`SchemaRenderer` 查
`information_schema.columns` 也只拿回 5 行 → **注入给模型的表结构悄悄少了 21 列，
而且不报错**。模型会拿着半张表结构去写 SQL。

根因是这两件事要的上限**完全不同，不该共用一个**：

| | 是谁的查询 | 要不要限行 |
|---|---|---|
| `information_schema` 元数据 | **我们自己的** | 一条都不能少 |
| 模型生成的 SQL | **模型写的** | 才需要防跑飞 |

所以上限搬到了语句级（`PreparedStatement.setMaxRows`），只作用于模型那条 SQL；
而**超时仍然留在连接层**——「某条语句跑太久」对元数据查询同样有害。
demo 里为此加了一个**回归检查**：把上限调成 5 之后，元数据必须还是 26 列。

> **一句话：安全措施配错了作用域，它自己就会变成一个「不响的错」。**

**而且撞到上限必须说出来**。工具会在返回的 SQL 后面附一行：

```
-- [已被截断] 只返回前 5 行（上限 sdaq.text2sql.max-rows）
```

因为这时候 `rowCount` **已经不是真实行数**了（真实行数我们拿不到），
不说出来的话，模型会把前 N 行当成完整结果——**又是一个「不响的错」**。

### 2. 脱敏要按【底层列名】判定 —— 但 `getColumnName` 并不给底层列名（也是实跑打脸）

我原本的推理听着很对：

```
getColumnLabel(i)  →  AS 之后的名字（给人看的）
getColumnName(i)   →  表里那一列的真名（别名遮不住）   ← 【这一步是错的】
```

**JDBC 契约上确实这么写，但 PG 驱动不是这么实现的。** 实测 `SELECT order_id AS 订单号`：
`getColumnName` 返回的就是「订单号」。于是「按列名脱敏」被一个 `AS` 绕过，而且不报错 ——
demo 第一次跑出来正是 `没打码 [X]`。

真正管用的是 PG 驱动专有的 **`PgResultSetMetaData.getBaseColumnName(int)`**：
它拿结果集元数据里的**表 OID + 列号**去反查，别名改不掉。

**已知缺口（比我想的大得多）**：只要结果列**不是直接的列引用**，就拿不到底层列名（OID 是 0），
于是退回显示名 → **不打码**。实测撞到的三种：

| 写法 | 底层列名 | 脱敏 |
|---|---|---|
| `SELECT order_id AS 订单号 FROM sales_orders` | `order_id` ✓ | **打码** |
| `... UNION ALL SELECT ...`（集合操作的结果列没有底层 OID） | 拿不到 | **不打码** |
| `SELECT MAX(customer_name) AS x`（聚合 / 表达式） | 拿不到 | **不打码** |

★ **而这件事是「同一个问题跑两次」才暴露的**：第一次模型写的是简单 `SELECT`（打码 ✓），
第二次它自作主张加了 `UNION ALL`（不打码 ✗）。**判定随模型的写法翻来覆去。**

> 所以后来把这个用例改成**固定 SQL**（`runSql` 跳过模型），两个形状各测一次 ——
> **测试要能被信任，前提是它的输入可控。** 依赖模型输出的「测试」只是观察，不是验证。

**结论：按列名脱敏只是第一步，不是终点。** 要真严格，得在数据库侧做
（视图、列级权限），或者干脆别让模型能把敏感列查出来。

> ⚠️ **这一条是「我以为我知道这个 API，其实不知道」的活教材。**
> 我不是靠重读文档纠正的，是靠**跑出来一句「没打码」**纠正的。
> 所以「这一层到底生效了没有」必须有一个能观测的出口——就像 ③ 那条要去看表还在不在。

> 说明：demo 里验这一条用的是 `order_id`（注入成 `order_id AS 订单号`）而不是 `customer_name`——
> 因为客户名在 `customers` 表里，而那张表属于 迭代 19 新增的 15 张，**库还没扩表、它现在不存在**。
> 这一节验的是**机制**，不是某张表；真正的敏感列名单在 `sdaq.text2sql.masked-columns`。

### 3. 超时是「万一漏过去」的兜底

`pg_sleep` 本来就被第 ② 层拦着。但**如果只有准入层，就等于没有纵深**——
万一有东西漏过去，它还得有个东西能占不住连接。这就是超时。

demo 里特意**绕过护栏**直接打一条 `SELECT pg_sleep(3)`，验证超时确实会中断它。

## 七、测试用例（本轮真正的产出）

`--sdaq.exp21.enabled=true` 跑三组用例。**这一节就是「验过」的凭证。**

### ① 攻击清单：18 条，必须全拦

覆盖：DDL 删表/清空/改结构/建表、DML 增删改、权限提升、
多语句拼接、**`WITH` 里藏 DML**（2 条）、`SELECT INTO`、`FOR UPDATE`、
危险函数（`pg_sleep` / `pg_read_file`）、注释前缀绕过、维护命令。

### ② 合法查询：13 条，必须全放

**这组和 ① 一样重要。** 护栏写歪了最常见的形态不是「拦不住坏人」，而是「把好人也拦了」——
一条正常查询被拒，用户只看到一个莫名其妙的失败。所以这组里放了：

- 四种**误报陷阱**：关键字在字符串里 / 在注释里 / 列名含 `CREATE` / 合法的 `FETCH` 分页
- 其它不该误伤的：`status = 'DELETED'`、尾分号带尾注释、`::timestamp`
- **迭代 20 真实生成过的 4 条 SQL 原文** —— 用真实输出做回归，比用自己编的样例可信得多

### ③ 端到端：让模型真的「写出」`DROP TABLE`

做法是**故障注入**（迭代 20 留的那个口子）：把模型 SQL 的第一个 `SELECT` 换成
`DROP TABLE orders_archive; SELECT`。于是模型「写出来」的其实是一条 DROP——这就是真实威胁的形状。

**关键是最后那一步：独立验证表还在不在。**

```
注入前：orders_archive 有 12 行
工具返回：【已拦截】
注入后：orders_archive 有 12 行
★ 独立验证（不是听工具自己说）：表还在、行数没变 [OK] 真的拦住了
```

只看工具返回「已阻止」是不够的——那只是它**说**自己拦了。
**真正能证明拦住了的，是独立地去看一眼表还在不在。**

### 复现值（实跑之前，先看规则写对没有）

沙箱没有 JDK，所以把 Java 里的攻击/放行清单抠出来、用 Python 复刻 `SqlGuard` 的规则跑了一遍：

```
① 攻击清单   拦下 18 / 18
② 合法查询   放行 13 / 13
```

### 实跑结果：**跑了三次才全绿**

| 组 | 结果 | 第几次才对 |
|---|---|---|
| ① 攻击清单 | 拦下 **18 / 18** | 第 1 次 |
| ② 合法查询 | 放行 **13 / 13** | 第 1 次 |
| ③ 端到端 DROP | 已拦截；**独立验证 orders_archive 12 行没变** | 第 1 次 |
| ④ 行数上限 | 截断如实上报；回归检查「元数据仍 26 列」 | 第 2 次（第 1 次元数据被截断成 5 列） |
| ⑤ 查询超时 | `ERROR: canceling statement due to user request` | 第 1 次 |
| ⑥ 脱敏 | ①简单列引用 `O***` 打码 / ②UNION 确认不打码（已知缺口） | 第 3 次 |
| ★ 元数据完整性 | **5 张表 / 26 列 / 5 个主键 / 3 条外键** | 第 3 次（第 1、2 次是 0 条外键） |

**三次跑分别抓出四个 bug**，全部是真 bug、全部不报错：

| # | 现象 | 根因 | 在哪一节 |
|---|---|---|---|
| 1 | 元数据只剩 **5 列**（本该 26） | 行数上限设在**连接层**，把元数据查询也截断了 | §六.1 |
| 2 | 脱敏**没生效** | `getColumnName` 在 PG 上返回的是**别名** | §六.2 |
| 3 | 元数据变成 **0 条外键** | `information_schema.table_constraints` 按权限过滤，只读账号看不见约束 | §八.6 |
| 4 | 脱敏判定**两次跑不一样** | 用例的输入是模型输出，而模型有时写 `UNION ALL` | §八.7 |

> **四个 bug 里有三个是靠「顺手看一眼日志里的数字」发现的**（列数、外键数、脱敏结果）。
> 唯一一个靠断言发现的，还是因为它把判定从「观察」变成了「验证」。
> **所以这一节真正练出来的不是安全规则，是「让每一层都有可观测的出口」。**

## 八、我本轮做反的七件事

前三条是写代码时自己发现的；**第 4—7 条是实跑替我发现的——那四条更值钱。**

### 1. `FETCH` 不该进黑名单

我第一版把 `FETCH` 列进了禁止词（因为它是游标操作）。但
**`FETCH FIRST 10 ROWS ONLY` 是合法的只读分页写法**——列进去就会把正常查询拦掉。
而游标版的 `FETCH` 需要先 `DECLARE`（已被拦），所以不放它进来是安全的。
**这一条是写测试用例时被「②」那组逼出来的**：先写用例、再写规则，就会立刻发现这种问题。

### 2. 故障注入必须挪到护栏【之前】

迭代 20 时故障注入排在护栏之后。当时无害（注入的是个 SELECT）。
但本轮不行了：验收要求「故意让它生成 `DROP TABLE`，验证被拦住」——
**如果注入发生在护栏之后，那条 DROP 就绕过了护栏，验收是假的。**

语义上也更对：故障注入模拟的是「模型写出了这条 SQL」，那就该受和模型输出一样的检查。

### 3. `[已阻止]` 这个字面量不能改

拦截消息里我本来想写 `[已阻止/多语句]`——但**诊断集的判据靠 `"[已阻止]"` 这个字面量**认出
「这次没跑成」。加了斜杠就匹配不上了，失败会被当成「跑成功但结果为空」，
**数字整体偏乐观而且不报错**。

这正是 迭代 20 栽过的同一个坑（自修复失败的标记）。所以现在把规则和理由**附在标记后面**：

```
-- [已阻止] 多语句：一条语句之外还有别的语句（分号后面还有内容）
```

### 4. ★ 行数上限设在了连接层，把元数据查询也截断了（**实跑发现**）

见第六节第 1 条。**这是本轮最隐蔽的一个 bug**：它不报错、也不影响任何一条测试通过，
只是让注入给模型的表结构**少了 21 列**——模型会拿着半张表去写 SQL，
而你只会觉得「它最近怎么老写错列名」。

发现它的路径很偶然：我在 demo 里把上限调成 5 做截断演示，
**日志里跟着冒出一句「5 张表 / 5 列」**——正常应该是 26 列。
**如果我没顺手看一眼那行日志，这个 bug 会一直躺在那儿。**

> 所以 demo 里现在加了一条**回归检查**：把上限调成 5 之后，元数据必须还是 26 列。
> **「顺手看一眼日志里的数字对不对」不是洁癖——本轮它就值 21 列。**

### 5. ★ 脱敏按 `getColumnName` 判定 —— 但 PG 驱动返回的是别名（**实跑发现**）

见第六节第 2 条。**这是「我以为我知道这个 API」被实跑纠正的一次。**

值得记的是**我是怎么发现的**：demo 打印了 `没打码 [X]`。
如果我当初只把「脱敏配了 8 个列名」写进日志就收工，这一层会一直是**假的**——
看起来配好了、实际一点用没有，而且不报错。

> 这和 ③ 那条「去看表还在不在」是同一个道理：
> **「我配了」和「它生效了」之间，隔着一句可观测的输出。**

### 6. ★ 换上只读账号之后，**外键全部消失了**（**实跑发现，而且是最隐蔽的一条**）

启用第 ③ 层、重启，日志里第一行就不一样：

```
元数据读取完成：5 张表 / 26 列 / 0 条外键      ← 换账号之前是 3 条
```

**换个账号，表结构注入就少了一半的结构信息，而且不报错。**

根因是 PostgreSQL 文档里那句容易被略过的话：
`information_schema.table_constraints` **只显示「当前用户拥有、或持有 SELECT 【以外】权限的表」上的约束**。
只读账号只有 SELECT —— 于是约束一条都看不见。
（`information_schema.columns` 没有这个限制，所以 26 列还在，这就更迷惑人了。）

**后果**：模型拿到的表结构里再没有 `sales_orders.region -> regions.region_name` 这些线索，
它写 JOIN 只能靠猜——**一个安全加固把能力悄悄削掉了一块，没有任何一处报错。**

修法：**主键/外键改走 `pg_catalog`**（`pg_constraint`），系统目录对所有用户可读。

> **这是同一件事踩的第二次**：迭代 18 拿列注释时，也是因为 `information_schema` 里没有那个字段
> 而转去 `pg_catalog`。**教训：要拿「结构元数据」，一律优先 `pg_catalog`；
> `information_schema` 是带权限过滤的视图，会按当前账号悄悄少给你东西。**
>
> 顺带把「主键数」也加进了那行日志（原来是「N 张表 / N 列 / N 条外键」）。
> **这条发现完全是靠「顺手看一眼日志里的数字」得到的** —— 如果我只打「元数据读取完成」，
> 这个 bug 会一直躺着。

### 7. ★ 脱敏的判定，居然随模型怎么写 SQL 而变（**实跑发现**）

同一个问题「列出订单号和完成时间」，两次跑：

```
第一次  模型写：SELECT order_id, completed_at FROM sales_orders                       → 打码 ✓
第二次  模型写：SELECT order_id, completed_at FROM sales_orders
                UNION ALL SELECT order_id, completed_at FROM orders_archive           → 不打码 ✗
```

原因见第六节第 2 条：`UNION` 的结果列**没有底层表 OID**，`getBaseColumnName` 拿不到东西，
只能退回显示名，而显示名不在脱敏名单里。

**所以问题不在脱敏写错了 —— 在于这个「测试用例」的输入是不可控的。**
判定随模型的即兴发挥翻来覆去，那它测的就不是脱敏，是模型的脾气。

改成固定 SQL 之后（`runSql` 跳过模型，两种形状各测一次），两个用例都是确定性的，
而且**顺带把「按列名脱敏」的边界也一起测出来了**——同列、两种写法、一个打一个不打。

> **一条能带走的规矩：测试要能被信任，前提是它的输入可控。**
> 依赖模型输出的所谓「测试」，只是在观察。

### 顺带：我的静态自检也有同一个毛病的洞

加完「构造参数个数」检查之后它一直报「通过」，我以为没事了。实际上它**漏掉了所有带前缀的
`new`**——`new Text2SqlDatabaseTool.Options(...)` 里的 `Options` 压根没被检查
（第一版正则只认 `new Options(`；第二版把前缀写成「小写开头」，而
`Text2SqlDatabaseTool.` 是**大写开头的外层类名**，照样漏）。

修对之后它一次报出 **3 处参数个数对不上**——正好是会让 `mvn` 编译失败的那 3 处。

> **检查器说「通过」的时候，先确认它到底查了什么。**
> **一个漏查的检查器比没有检查器更危险**——它会让你放心地把 bug 提交上去。

## 十、交付后编译失败：一条真实的教训（比本轮任何一条规则都值钱）

代码交出去之后，第一次 `mvn` **编译不过**，三处错误，全是同一个原因：

```
SqlRepairDemo.java:[146] 无法将 Options 应用到给定类型
  需要: int, TableSelector, int, String, int, SqlFault, SqlGuard, ColumnMasker   ← 8 个
  找到: int, <nulltype>, int, String, int, <nulltype>                            ← 6 个
```

迭代 21 把 `Text2SqlDatabaseTool.Options` 从 6 个字段加到了 8 个，
但 迭代 20 的 `SqlRepairDemo` 里有 **3 个调用点**还是直接用记录构造器写的 6 个参数。

**这正是项目「技术坑」表里那条：**
> 沙箱无 JDK，「静态检查」只能查括号和拼写，**查不出签名不一致**。
> 凡跨文件改了签名，必须把所有调用点过一遍。

**我知道这条、也自认为做了调用点检查——但还是漏了。** 漏在哪很具体：
我给旧构造器留了 `Options.simple()` / `withTableFilter()` 两个工厂方法，
就以为「旧调用点不受影响」；可 `SqlRepairDemo` 走的是**记录的直接构造器**，不是工厂。

### 所以加了一类检查：构造参数个数

`scripts/static-check.py` 现在多查一条：**把项目里所有 `record` 和公开构造器的参数个数收集起来，
再逐个对 `new X(...)` 的实参个数**。本轮这个错它能直接抓到。

（写这条检查时我自己又被误报咬了两口，两次根因是同一个：**`<` `>` 到底算不算括号**。
`() -> foo(a, b)` 里箭头那个 `>`、`repairAttempts > 0` 里大于号那个 `>`，
都会把「深度」减成负数，于是后面的逗号漏算/多算。
最后分成两种模式：**解析声明时认泛型，统计实参时不认**。
两个坑都写进了代码注释。）

> **教训一句话：能自动查的东西不要靠「我过了一遍」。**
> 而且**新增检查本身也会误报**——它第一次跑报了 2 处「参数个数对不上」，
> 全是我自己检查器的 bug，真代码是好的。**误报会让人把工具关掉，所以检查器也要被测。**

### 紧接着第二次编译失败：`runtime` 作用域的依赖不在编译期 classpath 上

```
程序包org.postgresql.jdbc不存在
```

修完参数个数、跑第二次 `mvn`，又炸了，这次是**另一个原因**：

我为了拿「别名遮不住的底层列名」，import 了 PG 驱动的 `PgResultSetMetaData`。
但 pom 里那条依赖写的是 **`<scope>runtime</scope>`**——
而 **runtime 作用域的依赖不在【编译期】classpath 上**，所以这个包编译时根本不存在。

原来写 runtime 是因为「它只是连库用」，没有任何代码在编译期引用驱动类。
**现在有代码引用了，scope 就该改成 compile**（一行改动，且不改变打包结果）。

> **这一类错（依赖可见性）静态自检天生查不出来**——它不认识 classpath。
> 所以又在 `scripts/static-check.py` 里加了一条窄检查：
> **pom 里标了 `<scope>runtime</scope>` 的依赖，源码里不许 import 它的包。**
> （groupId 通常就是包根，所以这条能自动对上：`org.postgresql` ↔ `groupId org.postgresql`。）
> 加完我**特意把 pom 改回 runtime 跑了一次**，确认它真会响——
> 因为刚吃过「检查器有洞」的亏，不敢再假设它有效。

### 这一节两次编译失败的共同点

| 编译错误 | 我漏在哪 | 补了什么 |
|---|---|---|
| `Options` 参数个数对不上（3 处） | 以为给旧构造器留了工厂方法就没事了，没注意那个 demo 走的是**记录的直接构造器** | 检查器的**构造参数个数**比对 |
| `程序包 org.postgresql.jdbc 不存在` | 顺手 import 了驱动类，**没回头看 pom 的 scope** | 检查器的**runtime 作用域**比对 |

**两次都不是「不会写」，而是「没验证到」**——而且两次都能被一条自动检查接住。
所以本轮真正的收获不是这几条安全规则，是**「把漏掉的东西变成检查」这个反射**。

## 十一、局限

1. **第 ③ 层已启用**：只读账号建好了，应用也切过去了
   （`sdaq.business-db.username = sdaq_readonly`）。**这是四层里唯一「不依赖我代码没有洞」的一层。**
   验证方式：用 `sdaq_readonly` 去 `DROP TABLE` 会报 `must be owner of table`。
2. **聚合敏感列绕得过按列名脱敏**（`SELECT MAX(customer_name) AS x`）——
   见第六节第 2 条的「已知缺口」。真要严格得上数据库侧的视图或列级权限。
3. **脱敏规则很粗**：保留首字符 + `***`。真实系统要按类型分开（手机号留前 3 后 4、
   邮箱留域名），每一条都要单独论证「这样真的脱敏了吗」。
4. **黑名单式的危险函数清单永远不全。** 本轮列的是「读文件 / 拒绝服务 / 进程控制」三类里最常见的那些。
5. **行数上限的截断上报是「撞到才报」**：如果一条查询恰好返回 1000 行（不是被截断），
   也会被报成「可能被截断」。这是保守方向的误报，可以接受，但要记着。
6. **超时只在 demo 里用 `pg_sleep` 验过**，真实场景里「慢查询」的形状（大表扫描、复杂 JOIN）
   没测过——因为这个库太小，跑不出慢查询。
7. **没有审计日志。** 生产上「谁在什么时候让模型查了什么」是要留痕的，本轮只打了普通日志。
