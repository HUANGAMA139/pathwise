# v25 · 路由失败的代价分析 + 兜底策略设计

> 本轮**不写新功能**，只做分析。产出是这份文档。
> **方法**：不空谈「哪个方向更危险」，而是拿本项目**实测的 35 次路由误判**来对账——
> 项目自己立的规矩：**写进文档的「发现」必须能被某条实测输出指出来**。

---

## 一、先看实测：错误是不是均匀分布在四个方向上

把 v23 报告 + v24 五策略矩阵里的**所有误判**按方向汇总（可复现）：

```bash
python3 -c "
import csv,collections
rows=list(csv.DictReader(open('eval/router-compare.csv',encoding='utf-8')))
a=collections.Counter((r['expected'],r['actual']) for r in rows if r['correct']=='0')
[print(f'{e} -> {x}: {n}') for (e,x),n in a.most_common()]"
```

**5 个策略合计 35 次误判：**

> ⚠️ **这里说「5 个」是对的**——本文用的是 v24 首跑那一批数据，**当时还没有实验臂 A3**（它 2026-10-09 才补上，见 `docs/24` 5.3.1）。
> **别把下面的「5 个策略」和「现在是 6 个策略」搞混。** 加 A3 之后的误判分布没有重算。

| 方向 | 次数 | 出现在哪些策略 |
|---|---|---|
| **`document → database`** | **17** | **每一个策略都有**（含最强的 A） |
| `document → refuse` | 13 | A2 / B / C |
| `both → database` | 3 | 只有 D |
| `document → both` | 1 | B |
| `both → document` | 1 | D |
| `database → document` | **0** | —— |
| `database → both/refuse` | **0** | —— |
| `none → 任何` | **0** | —— |

**两条一眼可见的事实：**

1. **所有策略的错都集中在 `document → X` 这一个方向。** 连最强的 A（**本次跑 27/28**）
   **唯一那条错也是 `document → database`**。
   → **错误不是均匀撒在四个方向上的。想兜底，应该把力气压在这一个方向上，而不是四面平均。**
   ⚠️ **注**：这句是**基于本文那一跑**的；后来复跑两次，A 的错题里也出现了 `document → refuse`（D14/D15）——
   **「最强的策略只错这一个方向」不是稳的**。方向分布的总趋势不变，但别把它说成铁的。
2. **计划里担心的 `database → document`、`both 只走一边`、`refuse 却硬答`，一次都没出现。**

**但第二条不能读成「这三类没问题」**——测试集里 `database` 只有 4 条、`both` 4 条、`none` 5 条。
**样本这么小，10% 的错率也不会显形。** 缺的是**证据**，不是**风险**。
（这和 v15「3 处路由错全是同一个病」是同一类观察：**小样本上的「没发生」只能说「还没看到」。**）

## 二、逐方向代价（每格配实证，或明确写「未观察到」）

### `document → database` —— **最危险，且实测最多（17 次）**

计划说它会「产生一个似是而非的数字，用户完全无法察觉」。**本项目的证据比这更细，分两种：**

**（a）问题一看就不是要数字 → 用户其实能察觉。**
例：`B/C` 把 **D02「未完成的订单算不算进销售额？」**（是非题）、
**D07「退了货以后钱什么时候从销售额里减掉」**（问时点）路由到 database。
这类错误**答非所问得很明显**——用户问「算不算」，得到一个数字，一眼就不对。

**（b）问题看起来就要数字 → 这才是真正无法察觉的。**
v23 基线里 `D12「每个订单平均贡献多少钱」` 被判 `database`，答案是
**「每个订单平均贡献 4234285.71 元」**——**数字真实、有 SQL 出处、措辞自然**。
用户问的是一句话，拿到一个数，**没有任何理由怀疑它**。

> ★ **但这里必须诚实**：D12 的期望路由本身**可争议**（v24 第 5.4 节）——
> 5 个策略**全部**把它判成 database，包括最强的 LLM。
> 所以它是一条**「不一定算错」的错**，不适合单独当作铁证。

**结论**：`document → database` 的危险**不是均匀的**，要害在 **(b) 那一小类**：
**问题的措辞本身就在要一个数字，而正确答案需要一份口径。**

### `document → refuse` —— 较轻，但代价被低估了（13 次）

用户拿到的是「这不在我能力范围内」。**用户不会拿到错数字**，这符合计划说的「较轻」。

但**实测里它出现得非常多**（13 次，占 37%）——因为它来自最弱的那两个策略
（B 的关键词一个都没命中就 refuse）。**它伤的是「能用率」，不是「正确率」**：
A2 在 D10/D14 上让用户吃了一个「我不知道」，而那两份文档**明明在库里**。
→ **这一类是「召回损失」，v23 把它叫「路由不知道我手上有什么」。**

### `both 只走了一边` —— **计划说「部分错误」，实测说「比部分错误更坏」**

**v8 已经实测过一次，而且推翻了当时的预期**（`docs/08-路由误判会污染答案.md`）：

> 关键词路由把「销售额是怎么算的」（**定义题**）误判成 `both`。
> 当时的预期是「多查一次库，浪费点 token」。
> **实际后果**：答案里多了一句
> 「例如，2026年第二季度华东区已完成订单的销售额为 **128,450,000 元**」。

**那个数字是真的、出处标注是正确的、模型没有骗人**——问题出在**上游**：
一次误判把无关支路的材料喂进了上下文，模型顺手当「例子」写了出来。

★ **所以 `both` 不是安全牌。** 误判成 `both` 的后果不是「答案更全」，而是
**答案里出现用户没问的内容，而且很难察觉**。这一条要**单独列在代价表里**，
它介于「轻」和「重」之间：不像假数字那样直接错，但**用户也发现不了**。

### `refuse → 硬答` —— **未观察到**

测试集 5 条 `none`，**5 个策略全判对**（5 条全 refuse）。
**但这不等于安全**：`none` 只有 5 条，且都是「今天天气」「你好」这种**一眼越界**的题。
真正难的是**「看起来像业务问题、其实库里答不了」**——那一类本轮没有测。
（v18 的 D7「福建省销售额」就是这种题，但它挂在 document/both 那边，不在 `none`。）

## 三、★★ 对通用说法的两点修正（都来自本项目的实测）

### 修正 1：「对危险方向卡更严的置信度阈值」——**这条路在本项目已经死了**

计划给的示范答案是：

> 「错的方向不同代价不同，`document→database` 会产生不可察觉的假数据，
> 所以我对这个方向的置信度阈值卡得更严。」

**这个答案听起来很对，但在本项目走不通**——因为**置信度没有区分度**：

- v9：9 次路由判断，置信度**全在 0.95~1.00**；同一问题两次跑给出 0.95 和 1.00。
- v15：同一道题两次跑出**不同路由**（DOCUMENT → REFUSE），而模型给的**还是 0.95**。
- v24：本次 28 题 × 5 策略里，模型输出的置信度**最低 0.90、绝大多数 0.95~1.00**。

**阈值卡在哪儿都拦不住东西**——它会把所有东西一起放过去。
所以「按方向调阈值」这一步**缺一个可用的信号**，不是缺一个更聪明的阈值。

### 修正 2：**真正「无法察觉」的假数字，主要不在路由层，而在支路的口径层**

计划把 `document → database` 定为「最坏的错误类型」。**但从本项目的实测看，
最隐蔽的假数字来自另一处——数据库支路内部的口径错误**：

v18 实测（`docs/18-Text2SQL原理与Schema注入.md`）：

- 8/8 道涉及期间的题**都用了 `created_at`**（该用 `completed_at`）→ 27,300,000（正确 36,100,000）；
- **D4 全国合计：多算 740 万（漏状态过滤）− 少算 900 万（跨期那单）= 67,760,000，
  而正确是 69,360,000，只差 2.3%。**

★ **两处错方向相反、互相抵消，最终数字看着完全合理。**
而且**这一层是路由完全管不到的**：路由判对了（确实是 database 问题），
SQL 也跑通了，**只是口径错了**。

**所以「假数字」的风险有两条来源，路由只占其中一条：**

| 来源 | 触发条件 | 可察觉性 | 本项目证据 |
|---|---|---|---|
| 路由层：`document → database` | 定义题被送进库 | **部分可察觉**（问「算不算」却得到数字） | D12（可争议）、B/C 的 D02/D07 |
| **支路层：口径/取值错** | 路由对、SQL 跑通、**口径错** | **几乎不可察觉** | **v18 的 D1/D4/D5/D8** |

→ **兜底不能只修路由。**「把 SQL 和结果附在答案里」也**防不住**这一层——
v18 的 D4 就是**附了 SQL、但没人会去核**的那种。

## 四、兜底策略设计（三类，各带代价）

**前提：置信度不可用**（第三节）。所以下面三条**都不依赖模型自报的把握程度**。

### 兜底 A：让「危险方向的产物」自带证据 —— **已实现，但要认清它防什么**

**现状**：`QueryResult` 带 `sql`（v8 定的契约）、综合提示词第 2 条要求「引用数字必须说明来自哪条查询」、
v21 起 database 支路的答案带完整 SQL 与结果。

**它防的是**：「模型没查库却声称查到了」（v4 那种编造）。
**它防不住**：v18 的 D4——**真查了、SQL 也附了、但数字是口径错的**。
**代价**：0（已经做了）。**所以它必须留着，但不能把它当兜底的全部。**

### 兜底 B：对危险方向做**一次定向复核** —— 可量化，本轮只设计不实现

**思路**：不调阈值（没有信号），而是**对已经落在危险方向上的判定，额外问一次**：

> 有一个问题被路由成了「数据库」。请只回答一件事：
> **这个问题要的是一个数字，还是一个定义/规则？**
> 只输出 `数字` 或 `定义`。

**为什么这次可行**：它问的是**一个具体的判断**，不是「你有多确定」——
后者是模型给不出信息量的东西（第三节）。

**代价（用 v24 的实测数估）**：只在**被路由到 database 的请求**上多一次调用。
本测试集里那是 4/28 ≈ **14%**；v24 的 A 策略单次路由是 **878 prompt + 71 completion token、1.86 s**。
→ 摊到全部请求：**约 +14% 的路由 token、+0.26 s 平均延迟**。
**相对于「可能产生一个无法察觉的假数字」，这个代价是便宜的**（对比：`both` 要 +3.8 s，见第五节）。

**风险要说清**：这是**又一次 LLM 判断**，而 LLM 判断本身有错（v24 的 5 策略证明过）。
**它降低的是概率，不是杜绝。** 所以 B 要配 A（附证据）一起用。

### 兜底 C：「拿不准就 both」——**被 v8 的数据否掉了**

直觉上，both 最稳（两边都查）。**但 v8 实测：both 会把无关支路的材料带进上下文，
让答案里出现用户没问过的内容**（那个 128,450,000）。**用户同样察觉不了。**

→ **所以 both 提高的是「信息覆盖率」，不是「答案正确性」。**
把它当兜底，等于**用一种不可察觉的错，换掉另一种不可察觉的错**。

## 五、`both` 的成本：实测数字

v23 报告的端到端日志（8 条 database/both 用例）：

| 支路 | 用例 | 平均耗时 |
|---|---|---|
| `database` | B01—B04 | **5.4 s**（4465 / 5780 / 6777 / 4541） |
| `both` | X01—X04 | **9.2 s**（8247 / 6586 / 8143 / 13711） |

→ **`both` ≈ 单支路的 1.7 倍，多花约 3.8 秒**（多一趟文档检索+精排，还要模型综合两类材料）。
而且这是**每次都要付**的成本——不是只在出错时才付。

**所以「什么阈值下值得走 both」这个问题，在本项目里的诚实答案是：**
**在没有可靠置信度的情况下，没有「阈值」可设**；能把 both 用对的场景是
**问题里明确同时要数字和口径**（X01—X04 那类，A 策略 4/4 全对）——
那是**靠问题本身**判出来的，不是靠置信度。

## 七、局限（这份分析自己的边界）

- **35 次误判来自 5 个策略在 28 题上的结果**，其中两个策略（B/D）本身很弱，
  它们的错**不代表产品路径的失败分布**。产品路径 A 只有 1 条错。
- **方向分布强烈受测试集构成影响**（15 document / 4 database / 4 both / 5 none）。
  **换一个测试集，分布会变。**
- **「未观察到」全部按「还没看到」处理，没有按「不存在」处理**（第一节）。
- 延迟数字来自单次运行，**看数量级**。
