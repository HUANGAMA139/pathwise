## 二、改造后：五层显式落位

| 层 | 对应 Spring AI 槽位 | 项目里的实现 | 档位 |
|---|---|---|---|
| ① **改写器** | `QueryTransformer` | **`LlmQueryRewriter`（本轮新写）** / `NoOpQueryRewriter` | `none` \| `llm` |
| ② **检索器** | `DocumentRetriever` | `VectorDocumentTool` / `hybrid::searchBm25` / `HybridDocumentTool` | `vector` \| `bm25` \| `hybrid` |
| ③ **融合** | `DocumentJoiner` | `RrfDocumentJoiner`（迭代 16 写的，**在 hybrid 内部**） | 见下 |
| ④ **重排器** | `DocumentPostProcessor` | `LlmReranker` / `MmrDocumentPostProcessor` | `none` \| `llm` \| `mmr` |
| ⑤ **注入器** | `QueryAugmenter` | **`DefaultContextAugmenter`（本轮从主干抽出来）** | `default` |

`RagPipeline.retrieve()` 就是 ①→②③→④→⑤ 一条直线，返回
`{ 改写后的查询, 片段, 拼好的材料 }`。

## 三、★ 两处「没照计划做」，理由都写在这里

### 1. 没有用框架的 `RetrievalAugmentationAdvisor`，而是显式自组装

**不是不想用，是它不该用在这里。** 它拥有**整个请求生命周期**（改写→检索→注入→**生成**），
而本项目的生成前面横着一个四值路由和一条数据库支路：

- `both` 的时候它只能管文档那一半，数据库那一半要另外并进来；
- 它会把「检索 + 生成」绑成一个不可分的整体，而本项目必须在这两步之间
  **插入「有没有真查过」的证据**（迭代 21 那条防线的落点）。

**所以只借框架的接口（`Query` / `DocumentPostProcessor` / `DocumentJoiner`），不借它的编排。**
这和 迭代 17 那句「框架给插槽、插槽里放什么才是对业务的理解」是同一条判断——
**这次是第四次遇到「框架里只有洞」**。

> **另一个现实原因**：`QueryTransformer` / `QueryAugmenter` 在**锁定的 1.1.0 里确切包名与签名，
> 我无法在沙箱里核实**（拉不到源码）。项目已经被「官方文档与 1.1.0 不符」坑过三次，
> 再来一次就是第 4 次「交付后 mvn 报找不到符号」。
> **所以新增的两层用项目自己的接口**——语义上仍是五件套的对应层，只是接口自己定。
> 要换成框架接口时，先核实包名，再改那两个文件（各一个接口、一个实现）。

### 2. 融合（③）没有做成独立开关

**因为「融合」不是一个可以关掉的独立动作——它只在两路都开的时候才存在。**
所以它体现为检索档位的一个取值：`hybrid` = 两路 + RRF；`vector` / `bm25` = 单路、不融合。

**把融合单独做成开关会造出一个无意义的组合**（单路 + 融合）。
消融表里「融合」这一维就是 `vector / bm25 / hybrid` 的对比——**也正是 迭代 16 量出负收益的那一维。**

## 四、★★ 一段不能省的检查：这是不是**纯重构**

把套娃改成 pipeline，**如果行为变了，迭代 15/23 的所有基线都会跟着漂，而且不会报错。**
所以 demo 最先跑的不是消融，是**回归检查**：

> `rewrite=none` 时，逐题比对「新 pipeline 返回的片段 id 序列」和「旧装配返回的片段 id 序列」。
> **不一致就是重构出错，不是「效果」。**

**只跑 `none` / `mmr` 两档重排**——`llm` 档是模型输出，两次跑本来就可能不同（迭代 17 已写明），
把它放进比对里会把「模型抖动」误报成「重构出错」。**一个会误报的检查等于没有检查。**

对应地：`sdaq.rag.pipeline.enabled` **默认 false**。pipeline 照建（廉价），但**先不接进主干**——
**量过才开**（同 迭代 20 的 `few-shot-size`）。

## 五、结果（实跑）

### 5.0 回归检查 —— **通过，这是本轮的第一结论**

```
逐题比对 90 次，不一致 0 次 —— [OK] 纯重构，行为未变（迭代 15/23 的基线不受影响）
```

（90 = 3 检索档 × 2 重排档（none/mmr）× 15 题；`llm` 重排档排除，理由见第四节。）

**还有一条独立佐证**：`none+vector+none` MRR **0.906**、`none+hybrid+none` **0.847** ——
与 迭代 16/17 记录的数字**逐位一致**。**两条独立证据说同一件事：这次改造没动行为。**

> **唯一一处对不上的**：迭代 17 记的 `hybrid+llm` 是 MRR 0.911，本轮 `none+hybrid+llm` 是 **0.922**。
> 这一档含模型调用（精排），**有运行间抖动**——迭代 17 自己就写明「结论要看两次跑是否一致」。
> 差值 0.011 在抖动带内，**不算矛盾**。

### 5.2 ★★ 发现 1：改写是本轮唯一被证明有效的新层 —— 而它的收益**高度依赖下游通道**

按「改写 off / llm」配成对，只看 MRR：

| 下游通道 | 重排 | 改写 none | 改写 llm | 差 |
|---|---|---|---|---|
| **bm25** | none | 0.756 | **0.922** | **+0.166** |
| **bm25** | llm | 0.833 | 0.911 | +0.078 |
| **bm25** | mmr | 0.817 | 0.917 | +0.100 |
| hybrid | none | 0.847 | 0.861 | +0.014 |
| hybrid | llm | 0.922 | 0.922 | 0 |
| vector | none | 0.906 | 0.902 | **−0.004** |
| vector | llm | 0.922 | 0.933 | +0.011 |

**hit@1 上的对比更刺眼**：`bm25+none` 在改写后从 **0.67 → 0.87（+0.20）**，
而 `vector+none` 从 0.87 → 0.87（**一点没动**）。

**机制很清楚，日志里有原文为证**——改写把口语换成了文档里的说法：

```
客户退的钱什么时候少算          →  退货金额扣减时点
退了货以后钱什么时候从销售额里减掉  →  退货金额从销售额中扣减的时点
销售额是怎么算的？              →  销售额计算方法
```

**而 BM25 正是那个只能靠字面重合的通道**（它就是字符二元组）。
向量本来就在做「同义改写」这件事，所以它不需要帮忙。

> ★ **「这一层对谁有用」比「这一层有没有用」是更值钱的结论。**
> 如果只报一个总分，会得出「改写让 MRR 涨了一点」；拆开看才知道：
> **它真正的价值是把弱通道（BM25）拉到接近强通道的水平** —— 也就是说，
> 它省下的是「为了让 BM25 能用而上向量」的那部分成本。
>
> **代价要说清楚**：每次提问多一次模型调用。收益是 +0.166 MRR（在 BM25 上），
> 在向量上则是 **−0.004（等于白花）**。

### 5.3 发现 2：融合（第③层）又一次是负的 —— 迭代 16 的结论第三次复现

每对同条件下 hybrid 都不如 vector：

| 条件 | vector | hybrid |
|---|---|---|
| 改写 none、重排 none | **0.906** | 0.847 |
| 改写 llm、重排 none | **0.902** | 0.861 |
| 改写 none、重排 llm | **0.922** | 0.922（打平） |
| 改写 llm、重排 llm | **0.933** | 0.922 |

**这次是在 18 格网格里、加了改写之后复现的**——比 迭代 16 那一次条件更全，
但结论没变：**RRF 的前提「两路可信度相当」在这批语料上仍不成立**（BM25 太弱）。

### 5.4 发现 3：精排（第④层）复现 迭代 17 —— 能补救，但补不出超额收益

- **它把融合丢掉的找回来了**：`hybrid+none 0.847 → hybrid+llm 0.922`（迭代 17 的核心结论，逐位复现）。
- **但追不过纯向量**：`hybrid+llm 0.922 < vector+llm 0.933`。
- **MMR 的取舍也复现**：多样性从 0.675/0.685 压到 0.630~0.640，而命中率不动或略降。
- **全局最优是 `llm+vector+llm`（MRR 0.933）** —— 即「改写 + 纯向量 + 精排」。

### 5.5 发现 4：精确率在精排后**下降**（迭代 14 那个现象又出现）

`vector+none` 精确率 0.533 → `vector+llm` 0.493。
迭代 14 记过同一条：「召回变好、精确率反而略降」——精排把「相关但不来自期望文档」的片段提了上来。
**这一列和命中率要一起看，单看一列都会得出片面结论。**

### 5.6 关于第⑤层（注入器）

**它本轮不参与打分**（表里没有它的列）——因为这张表全是**检索**指标，而注入器影响的是**生成**。
它本轮只完成了「从主干里抽出来、变成可替换的一层」，**不声称它有效**。
要量它得看 迭代 23 的端到端指标或答案忠实性。

## 六、局限与诚实边界

- **第⑤层（注入器）本轮量不了**：它影响**生成**，而这张表全是**检索**指标。
  **不声称它有效，只把它做成可替换的**。要量它得看 迭代 23 的端到端指标或忠实性。
- **`llm` 档（改写与重排）有模型波动**，即使 `temperature=0`。**结论要看两次跑是否一致**；
  不一致的地方不能说成「效果」（迭代 17 的纪律）。
- **改写只量到「检索」这一层**：它是否有用，看的是 hit@k/MRR 动不动——
  **改了词但没把正确片段提上来，就不算有用。**
- **18 组里有一半带 `llm`**，跑一轮约 150 次模型调用（改写已按题记忆化，否则要 ×9）。
- **单次运行、15 道题**：hit@1 上差 1 道题就是 0.067，**小差距不可声称**。
