> 目标：造一个业务库（5 张表、3 条外键），实现 `DatabaseTool` v1——**表结构注入 → 模型生成 SQL → 执行**。

## 一、Text2SQL 难在哪（原理部分）

Text2SQL 听起来像「把问题翻译成 SQL」，但真正难的不是翻译，是**模型看不到的东西**。

> **这一节原本写的是「三层」，跑完第一次之后改成了「四层」**——真实数据告诉我漏了一层，
> 而且漏掉的恰恰是本次最大的失分点（见第六节发现 1）。这个修正本身就是本轮的产出之一。

```
① 表结构（Schema）      有哪些表、哪些列、什么类型、谁和谁能 JOIN
② 值域（Values）        那一列里【实际存着】哪些取值：'华东' 还是 '华东区'？
③ 业务语义（Semantics） 该用哪一列算数、哪张表能用于统计
④ 方言与执行（Dialect） 语法细节、NULL、类型转换、执行报错
```

四层里：**① 是可注入的；② 也能注入（数据字典 / 样例行 / few-shot），但本轮没注入；③ 不在库里；④ 会自己报错。**

**②③ 都不在库里**——「取值长什么样」要去数据字典或样例行拿，「该用哪一列」写在制度文档里。
**所以 Text2SQL 支路同样需要文档知识。**

### 「模型不知道你的表结构」具体会怎样

它不会说「我不知道」，它会**编一个看起来很像的表名**。比如问「产品线的销售额」，
库里 `products.line_code` 是产品线，但模型可能写出 `FROM product_lines`——
因为真实世界里「产品线」确实常常是张独立的表。**这类错会响**（数据库报 column/relation does not exist），是最好处理的。

### 真正危险的是第 ②③ 层

SQL 语法完全正确、能跑、有结果，**但答案是错的，而且一声不响**。

本轮的数据集里埋了五个这样的坑，每一个都是「数据库不报错、用户看不出」：

| 坑 | 表结构里看得见什么 | 表结构里看不见什么 | 正确知识在哪 |
|---|---|---|---|
| 用 `created_at` 还是 `completed_at` 归期 | 两个 timestamp 列都在 | 哪个才是统计归属依据 | 语料 01 第二节 |
| 哪些 `status` 计入销售额 | 列注释列了 5 个取值 | 只有 `COMPLETED`/`REFUNDED` 计入 | 语料 01 第三节 |
| `refund_amount` 为 NULL 怎么算 | 列可空（NOT NULL 没标） | 要 `COALESCE(...,0)` | 语料 04 第三节 |
| `orders_archive` 能不能用 | 它和 `sales_orders` 结构几乎一样 | 它是归档表，不能做当期统计 | 语料 04 第四节 |
| **取值是 `'华东'` 还是 `'华东区'`** | 只有列名和注释「区域名，中文」 | **列里实际存着哪些字面量** | **数据字典 / 样例行（迭代 20 few-shot）** ← 本轮实测第一大失分点 |

**这就是 迭代 4「编造过程」和 迭代 8「假数字」在 Text2SQL 支路上的重演**，
只不过这次编造不是模型凭空想的，而是**它用一个合法的 SQL 问错了问题**。

## 二、业务库：5 张表，全部与语料咬合

`docker/init-business-db.sql`（由 `scripts/gen-business-seed.py` 生成，改数据请改脚本）：

| 表 | 行数 | 角色 | 出自语料 |
|---|---|---|---|
| `regions` | 6 | 销售区域字典 | 02 |
| `region_provinces` | 31 | 区域↔省份映射 | 02（语料原话「需要额外的映射关系」） |
| `products` | 8 | 产品与型号 | 05 |
| `sales_orders` | 48 | 当期订单（2025 Q1 起） | 01 / 04 |
| `orders_archive` | 12 | 历史归档（2024 及以前）—— **陷阱表** | 04 |

外键 3 条：`region_provinces.region_name → regions`、`sales_orders.region → regions`、
`sales_orders.product_code → products`。

### 三个刻意埋的点

**1. 语料 02 的两个坑都在数据里。** `福建 → 华东`（2025 年起由华南划归）、`山东 → 华北`（不是行政区划的华东）。
问「山东算华东吗」，文档说不算，而库里 `region_provinces` 也说不算——**这是文档和数据库的少见的「都答得了」区域**，迭代 23 做路由时要留意。

**2. `orders_archive` 是语料 04 点名的那张表。** 语料原文：「业务库里另有一张 `orders_archive` 是历史归档表，
不要用它做当期统计。」本轮把这句话变成了真实存在的一张表——**于是「模型会不会用错它」第一次可以被观测**。

**3. 一条「创建在 Q1、完成在 Q2」的订单**（`ORD-20260201`，3 月 28 日创建、4 月 5 日完成，900 万）。
它把「归期用哪个时间」从一句口诀变成了**可量化的一刀**：
- 按 `completed_at`：它在 Q2 → 2026Q1 华东 = **18,300,000**
- 按 `created_at`：它跑到 Q1 → 2026Q1 华东 = **27,300,000**

### ⚠️ 重建业务库（大概率需要，因为 business-db 从 迭代 1 就起过了）

`docker-entrypoint-initdb.d` 里的脚本**只在数据卷为空时执行一次**。
business-db 容器如果早就起过，数据卷已经存在，**本轮这个初始化脚本不会自动跑**。两种办法：

```
# 办法一（推荐）：删掉业务库的数据卷重建。注意只动 business-db，别碰 pgvector
docker compose rm -sf business-db
docker volume rm smart-data-qa_business_data
docker compose up -d business-db

# 办法二：不删卷，直接把脚本灌进去（脚本自己带 DROP TABLE IF EXISTS，可重复执行）
docker compose cp docker/init-business-db.sql business-db:/tmp/init-business-db.sql
docker compose exec business-db psql -U sdaq -d business_db -f /tmp/init-business-db.sql
```

验证（应看到 6 / 31 / 8 / 48 / 12 行）：

```
docker compose exec business-db psql -U sdaq -d business_db -c "SELECT count(*) FROM sales_orders;"
```

## 三、表结构注入：`SchemaRenderer`

它**读元数据**，不写死 DDL。原因很实际：**写死的表结构会和你真实的库悄悄脱节**——
加了一列忘了改常量，模型就永远看不到那一列，而这件事不报错。另一个原因是 迭代 19：
那时要「先筛表再注入」，而筛表的前提是「先拿到全部表名」——读元数据是天然的形状。

读的内容：表名 · 列名 · 类型 · 是否可空 · 默认值 · **列注释** · 主键 · **外键**。

> 顺带一个查 API 的坑：`information_schema.columns` 里**没有注释字段**。
> 列注释在 `pg_description`，要 join `pg_class` / `pg_attribute`（`objsubid = 0` 是表注释，`> 0` 是列注释）。

注入 prompt 的文本长这样（**复现值**——沙箱无 JDK 与 PG，这段是按 `init-business-db.sql` 的元数据在沙箱里复刻渲染出来的，不是实跑输出）：

```
表 orders_archive  —— 历史订单归档表
  order_id        varchar(16)             PK  NOT NULL  -- 订单号
  region          varchar(16)             NOT NULL  -- 销售区域名
  product_code    varchar(16)             NOT NULL  -- 产品编码
  order_amount    numeric(14,2)           NOT NULL  -- 订单金额（不含税）
  refund_amount   numeric(14,2)           -- 退货金额（不含税），可为空
  status          varchar(16)             NOT NULL  -- 订单状态
  created_at      timestamp               NOT NULL  -- 下单时间
  completed_at    timestamp               -- 订单完成时间
  archived_at     timestamp               NOT NULL  DEFAULT now()  -- 归档时间
  ...

表 sales_orders  —— 当期销售订单
  order_id        varchar(16)             PK  NOT NULL  -- 订单号，ORD- + 8 位数字
  region          varchar(16)             NOT NULL  -> regions.region_name  -- 销售区域名，取值见 regions
  product_code    varchar(16)             NOT NULL  -> products.product_code  -- 产品编码
  order_amount    numeric(14,2)           NOT NULL  -- 订单金额（不含税）
  refund_amount   numeric(14,2)           -- 退货金额（不含税），可为空
  status          varchar(16)             NOT NULL  -- 订单状态：CREATED/PAID/COMPLETED/REFUNDED/CANCELLED
  created_at      timestamp               NOT NULL  -- 下单时间
  completed_at    timestamp               -- 订单完成时间，未完成时为 NULL

外键关系（JOIN 用）：
  region_provinces.region_name -> regions.region_name
  sales_orders.product_code -> products.product_code
  sales_orders.region -> regions.region_name
```

全文约 2100 字符（≈1000 token 量级）。**注意注释的写法是有分寸的**：
只给「事实」（列是什么、有哪些取值、谁引用谁），**不给「规则」**（该用哪一列、哪张表不能用于当期统计）。
`status` 的注释列了 5 个取值，但没说只有 2 个计入——**规则在语料 01 里**。

**这个分寸不是失误，是本轮刻意留出来的观察点。**

## 四、v1 做什么、不做什么

`Text2SqlDatabaseTool` 的三步：

```
1. schema = SchemaRenderer.render()          // 懒加载 + 缓存
2. sql    = 模型(系统提示词 + 表结构 + 问题)   // temperature = 0
3. 执行 → QueryResult(sql, columns, rows, rowCount)
```

`DatabaseTool` 接口**一个字没改**——这是 迭代 8 定下的契约第二次兑现（第一次是 迭代 14 换向量检索）。

### 边界写在代码里，免得以后自己忘

| 本轮没做 | 为什么不做 | 什么时候做 |
|---|---|---|
| 表筛选（表多了 prompt 会爆） | 5 张表还不爆，先跑通链路 | 迭代 19（复用 迭代 16 的混合检索） |
| few-shot 样例 | 要先有 v1 的错误数据，才知道该给什么样例 | 迭代 20 |
| **错误自修复**（报错回灌给模型让它改） | **本轮就是要看见错误**。一上来就自动修，就体会不到模型有多容易写错 | 迭代 20 |
| 完整 SQL 安全边界 | 本轮只有一条最小护栏 | 迭代 21 |
| 执行准确率评测 | 诊断跑一遍 ≠ 一条命令出报告 | 迭代 22 |

### 三个刻意的设计（都会在 迭代 19—22 里被检验）

**1. 提示词里给模型一个说「我不会」的出口。**
> 「如果这个问题用现有的表和字段**无法回答**，就只输出一行以 `--` 开头的注释说明原因，
> 不要勉强写一条查不出正确答案的 SQL，更不要编一个数字。」

不给出口，模型必须给一个答案，它就会硬编一个看起来合理的数字（迭代 4 见过「我打过电话」）。
**给了出口之后它用不用**，是本轮最值得看的一件事。

**2. 报错如实上报，不回灌、不重试。** 执行失败时返回的 SQL 后面附一行 `-- [执行失败] <原因>`。
`QueryResult.sql` 是「真实执行痕迹」，所以失败的痕迹也记在这里——**「查了但没查到」和「压根没跑成」必须能分开**。

**3. 结果行数与放进上下文的行数分开。**
`rowCount` 记真实行数，`rows` 只放前 `sdaq.text2sql.max-context-rows`（默认 50）行。
迭代 8 定 `QueryResult` 时把这两个字段分开，本轮第一次真的用上——**上下文要控，事实不能丢**。

### 唯一的那条护栏

完整的安全边界（DDL/DML 一律拒绝、行数上限、超时、脱敏、故意的 `DROP TABLE` 测试）是 迭代 21 的交付物。
但本轮只加一条最小的：**只放行 `SELECT` / `WITH` 开头的语句，其余拦下并上报**。
这不是提前做了 迭代 21，而是给它留一个「已有的第一层」——
「不加任何判断就把模型生成的字符串丢给数据库执行」在本轮就已经是个隐患了。

另外 `sdaq.business-db.query-timeout-seconds`（默认 15）也是一个兜底：别让一条写坏的 SQL 把演示卡死。

## 五、诊断 demo：9 道题，照着四类失败模式设计

`--sdaq.exp18.enabled=true`。它会**先把注入的表结构原样打出来**（本轮交付物的正面），
再逐题打印 **生成的 SQL / 查出的结果 / 期望答案 / 判定**。

期望答案**不是手写的**，是 `scripts/gen-business-seed.py` 从同一份种子数据算出来的。
理由很实际：7 单净销售额手算错了的话，这个 demo 会把错的当成对来判——
**那就成了「量具坏了但看起来正常」，迭代 15 已经栽过三次。**

| 题 | 问题 | 期望 | 探什么 |
|---|---|---|---|
| D1 | 2026Q2 华东区的销售额是多少？ | 36,100,000 | 区域 + 状态 + 归期 + NULL 四件事都对 |
| D2 | 2026Q2 各区域的销售额排名 | 华东 36,100,000 … 东北 1,500,000 | GROUP BY / ORDER BY |
| D3 | 2026Q2 XR 产品线的销售额 | 68,200,000 | **要 JOIN `products` 拿 `line_code`** |
| D4 | 2026Q2 全国销售额合计 | 69,360,000 | 没有区域条件时会不会漏状态过滤 |
| **D5** | 2026Q1 华东区的销售额是多少？ | **18,300,000** | **★归期陷阱：用 `created_at` 会算成 27,300,000** |
| D6 | 华东区都包含哪些省份？ | 上海、江苏、浙江、安徽、福建 | JOIN `region_provinces`；**文档也能答**（重叠区） |
| **D7** | 2026Q2 福建省的销售额是多少？ | **库里没有省份维度 → 应说「算不出来」** | **★能力边界：最坏答案是给一个像样的假数字** |
| **D8** | 2024 年华东区的销售额是多少？ | **18,300,000（在 `orders_archive` 里）** | **★归档表陷阱：只查 `sales_orders` 会得到 0 行** |
| D9 | 2026Q2 华东区的客单价是多少？ | ≈6,016,667 | **★口径题：分母口径在语料 06，不在库里** |

判定分三档：**数值类自动比**（结果里有没有数字落在期望值 ±1% 内）、
**拒答类自动评**（模型是用注释说了「答不了」，还是硬答了）、**口径/文本类标「需人工判断」**。

> 诊断可以有「人工判断」这一档，**指标不能**。正式的执行准确率是 迭代 22，用 `eval/` 那套脚手架。

## 六、实测结果（首次跑通）

```
mvn spring-boot:run "-Dspring-boot.run.arguments=--sdaq.exp18.enabled=true"
```

**编译一次通过**，业务库连上，表结构渲染 **5 张表 / 26 列 / 3 条外键，耗时 110 ms**。
9 道题的判定：

```
自动判定通过 0 ／ 明确失败 7 ／ 需人工判断 2
```

**一条都没通过。** 但这不是代码坏了——**逐题看下来，SQL 几乎全都合法、全都执行成功。**
失败全部落在「不响的错」那一类。下面这五条是本轮的产出。

### 发现 1（本轮最重要）：模型猜错的是【取值】，不是表结构

四道带区域过滤的题——D1、D5、D6、D8——**全部返回 0 行**，原因是同一个：

```
库里存的是    region_name = '华东'
模型写的是    region_name = '华东区'      ← 照抄了问题里的说法
```

SQL 合法、执行成功、返回 0 行、**数据库一声不响**。D6（华东包含哪些省份）本该返回 5 行，也是 0 行。

> **表结构注入给了「表、列、类型、可空、主键、外键、注释」，唯独没给「列里到底存了哪些取值」。**
> 模型手里只有 `-- 销售区域名，中文` 这一句注释，于是它按问题里的字面写法去猜，猜错了。

这是本轮最大的失分点，**也是我事先没预料到的一条**：我预判的坑是「选错列」，
实际最大的坑是「猜错取值」。两者都叫「模型不知道你的库」，但**修法完全不同**——
选错列要补业务语义（在文档里），**猜错取值要补数据字典或 few-shot**。

> 迭代 20 的现成靶子：把这 6 个区域值放进 few-shot 样例。这是本轮留下的最具体的一个口子。
>
> **一个值得注意的细节**：语料 02《销售区域划分规则》第一节那张表里，**就写着这 6 个区域名**
> （华东 / 华南 / 华北 / 华中 / 西部 / 东北）。也就是说——**本轮这 4 道题缺的那个「值域」，
> 文档支路里其实有。** 这让 `both` 又多了一层含义：不只是「数字在库、口径在文档」，
> 而是**「值域也可能在文档里」**。迭代 23 做路由时值得回头看这一条。

### 发现 2：8 道涉及期间的题，8 道都用了 `created_at`

`completed_at` 的列注释是「订单完成时间，未完成时为 NULL」，`created_at` 是「下单时间」。
**8 道带期间条件的题，8 道都选了 `created_at`。**

```
D2 华东（created_at + PAID/COMPLETED） = 27,300,000   ← 期望 36,100,000
D4 全国（created_at，无状态过滤）      = 67,760,000   ← 期望 69,360,000
```

**27,300,000 这个数字，正好是种子数据里埋的那一刀**（`ORD-20260201` 创建在 3 月、完成在 4 月）——
只不过方向相反：它把 Q1 创建的那一单**从 Q2 里踢了出去**。

**预测被证实了**：谓词里写 `completed_at` 还是 `created_at`，表结构里**真的看不出来**
（我只给了事实、没给规则），而模型**默认选了看起来更自然的那个**。

### 发现 3：两个错误互相抵消，答案看起来很正常（最危险的一条）

D4 的 67,760,000 是**两个错误叠出来的**：

```
正确值（completed_at + 只计 COMPLETED/REFUNDED）                    69,360,000
  + 多算：created 在 Q2、但状态不该计的单（CANCELLED/PAID/CREATED）   +7,400,000
  - 少算：created 在 Q1、但完成在 Q2 的那一单                        -9,000,000
  = 67,760,000   ← 与日志逐位吻合
```

**一个 +740 万、一个 −900 万，最后离正确答案只差 2.3%。**
只看最后那个数字，绝对不会发现里面有**两个方向相反的错误**。
这就是「不报错的错」最难的地方：**错得多了，反而更像对的。**

### 发现 4：`AVG()` 在 0 行上返回【1 行 NULL】，不是 0 行

D9 的日志：

```
【返回 1 行】
avg_order_value
                  ← 这里是 NULL，当时被渲染成了空白
```

`rowCount = 1`——**看起来是「查到了」**，实际值是 NULL。
**「0 行」和「1 行 NULL」在 `rowCount` 上是两回事，在用户眼里却一样，都是「没有数」。**

> 这是本轮第二次撞到同一件事：**中间产物必须打出来。**
> 当场改了 `Text2SqlDatabaseTool`——单元格是 NULL 时渲染成字面量 `NULL`，不再是空串。
> 理由：「值是 NULL」和「值是空字符串」本来就不是一回事，而 `refund_amount` 可为空
> 正是语料 04 点名的坑。改完之后这类「看起来成功的失败」一眼可见。

### 发现 5：D7 的 SQL 是「错误的正确形式」

问「福建省的销售额」，模型写的是：

```sql
FROM sales_orders o
JOIN region_provinces rp ON o.region = rp.region_name
WHERE rp.province_name = '福建省'
```

它**知道**要去 JOIN `region_provinces`（说明外键标注起作用了），但这个 JOIN **口径是错的**：
`region → province` 是一对多，按 `province_name` 过滤**根本不会缩小订单集合**——
只要省份名写对，它会返回**整个华东区**的销售额，而不是福建的。

它最后返回 0，只是因为 `'福建省'` 这个取值也不对（库里是 `'福建'`）。
**两个错误叠在一起，让一个口径错误的查询「看起来像是在正确地报告：库里没有数据」。**

## 七、结论：表结构注入只解决了四分之一

回到第一节那四层，对照本轮的实测：

```
① 表结构      → 本轮解决了（SchemaRenderer 注入）
② 值域        → 本轮【没】注入，而且是本次最大的失分点（4 道题因它返回 0 行）
③ 业务语义    → 本轮【没】解决，也不该在 Text2SQL 支路里解决
④ 方言与执行  → 数据库会自己报错，最好办
```

**② 和 ③ 是两条不同的缺口，必须分清**：

- **② 值域**：`'华东'` 还是 `'华东区'`。这是**确定性的事实**——库里就存着，只是没告诉模型。
  修法是工程性的：数据字典、样例行、few-shot。**不需要文档，也不需要模型变聪明。**
- **③ 业务语义**：「用 `completed_at` 还是 `created_at`」**在语料 01**；
  「`orders_archive` 不能用于当期统计」**在语料 04**；「客单价的分母只计 `COMPLETED`」**在语料 06**。
  这些**不在库里，也不该塞回库里**——它们是制度，而制度会变（语料 01 就有 v3.0/v3.1/v3.2 三个版本）。

> **Text2SQL 支路同样需要文档知识。** 这不是缺陷，这正是「双支路 + 路由」存在的理由——
> 也是 `both` 这个路由值最实在的用武之地：**一个问题的数字在库里、口径在文档里。**

这一条和 迭代 12 选语料时定的原则（「每份语料都要和业务库的数据咬合上」）接上了：
当时是**设计**上咬合，本轮是**执行**上真的咬合了。

**一个要诚实记下来的点**：本轮 0 通过，**其中一半的锅是我的库没把值域告诉模型**（发现 1），
不是模型笨。所以「Text2SQL v1 不行」这个结论**不成立**——
本轮真正立住的是**「缺什么」的清单**。迭代 20 补上值域之后再跑一次，那组数字才有资格叫「v1 的水平」。

## 八、本轮踩到的坑（复用前必看）

| 坑 | 说明与正确做法 |
|---|---|
| **注册一个 `DataSource` bean 会让 Spring Boot 数据源自动配置整体让位** | `DataSourceAutoConfiguration` 挂着 `@ConditionalOnMissingBean(DataSource.class)`。项目里已经有一个自动配置的 DataSource（5432 的 pgvector），它是 `PgVectorStore` 和自动配置那个 `JdbcTemplate` 的唯一来源。**再加一个 DataSource bean，`PgVectorStore` 和 迭代 16 的混合检索会一起挂。** 同理 `JdbcTemplateAutoConfiguration` 挂着 `@ConditionalOnMissingBean(JdbcOperations.class)`，所以业务库的 `JdbcTemplate` 也**不能**注册成 bean（两个都注册 → 现有注入点变成「候选不唯一」；给业务库那个标 `@Primary` 更糟，等于让 `CorpusIngestor` 往业务库写向量）。**做法：把业务库的数据源和 JdbcTemplate 关进一个叫 `BusinessDb` 的普通类里，需要就注入 `BusinessDb`** |
| **`information_schema.columns` 没有注释字段** | 列注释在 `pg_description`，要 join `pg_class` + `pg_attribute`（`objsubid = 0` 是表注释，`> 0` 是列注释，`attnum = objsubid` 取列名） |
| **业务库要在**「表结构注入」时才连，不能在建 bean 时就连 | 否则 迭代 18 之后「只跑 RAG 的人」被迫也要把业务库开着。`DriverManagerDataSource` 构造时不建连接，加上元数据懒加载 + 缓存，业务库没起时应用照常启动，只有业务支路真正查库时才失败 |
| **`docker-entrypoint-initdb.d` 只在数据卷为空时执行** | business-db 从 迭代 1 就起过 → 数据卷已存在 → 本轮的初始化脚本**不会自动跑**。重建或手工 `psql -f` 见本文第二节。别用 `docker compose down -v`——那会把 pgvector 的数据一起清掉 |
| `queryForList` 在「0 行」时拿不到列名 | 用 `RowCallbackHandler`（`jdbc.query(sql, rs -> …)`），列名从 `ResultSetMetaData` 取一次。**「查到了但一行没有」和「列名都不对」是两种要分开的情况** |
| 模型输出会带 markdown 代码围栏（三个反引号）和一句中文 | 直接发出去必是语法错误，而报错会指向反引号——**一个把错误指向别处的 bug**。`SqlText.extractSql` 剥围栏、丢语言标记、去尾分号。**但不去注释行**——模型答「答不了」时输出的就是注释 |
| SQL 生成要 `temperature = 0` | 同 迭代 17 精排的理由：要的是稳定复现，不是发挥 |
| `e.getMessage()` 会带整条 SQL 和一堆细节 | 日志里先剥到根因（`while (cause != null) root = cause;`）再截断，否则一条报错刷满屏 |

## 九、局限

1. **只跑了一次。** 模型输出有波动（temperature=0 只是减小它，迭代 15/17 都验过这一点），
   所以「0 通过 / 7 失败 / 2 人工」这组数字**要再跑一次才算稳**。
2. **这组数字不能当成「Text2SQL v1 的水平」。** 一半的失败来自「库没把值域告诉模型」（发现 1）。
   迭代 20 补上 few-shot 后重跑，才是那一轮该对比的基线。
3. **两个预埋陷阱没验证到**：D5（归期列）和 D8（归档表）都被更早的取值错挡住了——
   取值一错就 0 行，轮不到它们出场。**要单独验它们，得先让取值对得上。**
4. **只有 5 张表、48 行数据。** 表筛选（迭代 19）要的是「表多了 prompt 会爆」，
   这个规模还没爆——**所以本轮也测不出 迭代 19 的必要性**，只能先记成已知未验证项。
   这一轮表结构只占约 2100 字符，`tokens` 上完全没有压力。
5. **判定是「粗判定」。** 数值档用「结果里有没有数字落在 ±1% 内」，比的是**存在性不是位置**，
   可能放过「碰巧包含期望值」的结果（比如 D2 那种多行结果，只要有任何一个数字撞上就算过）。
   **这是诊断，不是指标**——正式评测在 迭代 22。
6. **护栏只有一条。** 只拦非 `SELECT/WITH`，没有行数上限、没有脱敏、没有 DDL/DML 白名单测试。迭代 21。
7. **`region_provinces` 答不了「某省的销售额」。** 订单表只有区域没有省份，
   这是语料 02 明确的设计（「如果要按省份分析，需要额外的映射关系」）。
   **D7 那道题的正确回答就是「算不出来」。**
   而这次模型的做法比「答不了」更糟——它写了一个**口径错误但看起来高级的 JOIN**（发现 5）。
8. **`orders_archive` 与 `sales_orders` 结构重复、且没有外键。** 真实归档表就是这样，
   但这也意味着模型「选错表」时不会有任何约束提示它。这个坑是刻意保留的。
