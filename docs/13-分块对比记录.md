## 一、本轮学的：Spring AI 的 ETL 三段式

### 1. 三段分别是什么

```
DocumentReader  →  DocumentTransformer  →  DocumentWriter
     （读）              （切/清洗）              （写）
```

这是 RAG 在「有向量库之前」的完整形状。三段各自对应一个接口，**能单独替换**：

| 段 | 接口 | 职责 |
|---|---|---|
| Reader | `DocumentReader` | 从某个来源（文件、目录、URL、数据库）读出一批 `Document` |
| Transformer | `DocumentTransformer` | 在 `Document` 上做变换——**分块是其中一种**（`TextSplitter` 就是一个 Transformer） |
| Writer | `DocumentWriter` | 把处理好的 `Document` 写去某个地方（向量库最常见） |

关键认识：**分块不是独立的一步，它是「变换」这一段的子类。**
所以 `TokenTextSplitter` 继承的是 `TextSplitter`，而 `TextSplitter` 实现的是
`DocumentTransformer`——它输入 `List<Document>`，输出 `List<Document>`。

### 2. 本项目怎么映射

```
CorpusLoader.loadDocuments()  →  DocumentChunker.split()  →  MockDocumentTool
      （Reader）                     （Transformer）            （Writer 的占位）
```

`CorpusLoader` 返回 `List<Document>`，`DocumentChunker` 用 Spring AI 的
`TokenTextSplitter` 把它们切成 `List<Chunk>`，再塞进检索工具。

**这一改动本身是本轮最重要的结构变化**：迭代 12 的 `CorpusLoader` 直接返回
`List<Chunk>`，把「一个文件 = 一个片段」写死在了读的那一步。本轮把「读」和「切」
拆开，Read 返回 `Document`、切单独一步——**这才让「换一种切法」成为可能**，
迭代 13 的对比实验就是靠这一点做出来的。同一个道理，迭代 14 换检索方式时，
前两段一行都不用动。

### 3. 为什么 Reader 那一段没用框架的

框架有 `TextReader`，但我们用的是 `ResourcePatternResolver` 自己读。理由：

- 语料是 classpath 下的 6 个 `.md`，读它们只需要「找文件 + 读成字符串」，一行的事
- `TextReader` 会往元数据里塞它自己的一套字段，我们要的 `source`（正文一级标题）
  还得再剥一层、再补一次
- **Reader 这一段没有「自己写会写错」的地方**——而 Transformer 那一段有（见第二节），
  所以框架真正值钱的是中间那一段

这不是「框架不好」，是**只在框架真的替你解决难点的地方用它**。

### 4. 本轮第三段还是空的

`MockDocumentTool` 现在是内存里的一批片段，不是向量库。
**ETL 的「Writer」这一段本轮是占位的**，迭代 14 接 pgvector 时才算真正补上。

## 二、读源码才弄清的两件事（并修正了之前的说法）

写这段代码时撞了两次墙，两次都是「文档/印象」和「1.1.0 真实行为」不一致。
**都读了源码才搞清**，记下来是因为这类事只有源码能回答。

### 1. 「自定义标点」这个参数，1.1.0 根本没有

原来打算给切分器传一组中文标点 `。！？；：、`，让它在中文句子边界上切。
查 1.1.3 的官方 javadoc，构造器确实长这样：

```java
TokenTextSplitter(int chunkSize, int minChunkSizeChars, int minChunkLengthToEmbed,
                  int maxNumChunks, boolean keepSeparator, List<Character> punctuationMarks)
```

**但 1.1.0 没有这个参数。** 拉 1.1.0 的源码确认，它只有三个构造器
（无参、`boolean`、五参），标点是**硬编码**的：

```java
int lastPunctuation = Math.max(chunkText.lastIndexOf('.'),
    Math.max(chunkText.lastIndexOf('?'),
    Math.max(chunkText.lastIndexOf('!'), chunkText.lastIndexOf('\n'))));
```

只有 `.` `?` `!` 和换行。1.1.2 也还没有。**带 `punctuationMarks` 的版本是 1.1.3 才加的。**

而本项目锁在 1.1.0——`spring-ai-alibaba` 1.1.0.0 的 pom 里
`<spring-ai.version>1.1.0</spring-ai.version>` 是写死的。所以**这个版本拿不到中文标点**。

**教训（比结论更值钱）**：Spring AI 的官方文档站现在展示的是 2.x，
和 1.1.0 有实质差异；**同一个小版本线内部，API 也可能不一样**。
凡是「传参控制框架行为」的写法，都要先确认**你锁的那个版本**有没有这个参数。

### 2. `minChunkSizeChars` 的真实含义 —— 不是「合并小块」

原来的注释（和很多二手资料）说的是：小于 `minChunkSizeChars` 的块会被**合并**。
**1.1.0 的源码里它只出现一次**：

```java
if (lastPunctuation != -1 && lastPunctuation > this.minChunkSizeChars) {
    chunkText = chunkText.substring(0, lastPunctuation + 1);
}
```

它是**标点截断的字符下标下界**——只有当「窗口内最后一个标点」的位置**大于**它，
才允许在该标点处截断。所以它调的偏大时（框架默认 350），
小块永远够不到这个下界，标点截断触发不了，块就在 **token 边界上被硬切**。

表现出来像是「chunkSize 没生效」，**实际是截断被这个下界挡住了**。
这解释了为什么「要切小块就得把它一起调小」——原因不是合并，是**够不到下界**。

### 3. 顺带撞出来的第三个问题：它把 `.` 当句号，会切在版本号中间

这条是实验跑出来才看见的。语料 01 的最后一段是版本变更记录：

```
- v3.0（2025-01）：归属期间由创建时间改为完成时间
```

切完之后多出一个 26 字的碎片块，内容是：

```
0（2025-01）：归属期间由创建时间改为完成时间
```

**它切在了 `v3.0` 中间。** 因为 `.` 在标点列表里——切分器以为那是句号。
同理，小数、版本号、域名、文件扩展名（`application.yml`）都会被当成句子边界。

**这是「按字符判断语义边界」这类做法的通病**：`.` 是不是句号，取决于上下文，
而切分器没有上下文。（这条以后还会再遇到——检索层的字符匹配也是同一个病根。）

## 三、实验设计

| 项 | 设置 |
|---|---|
| 唯一变量 | `chunkSize` ∈ {200, 500, 1000}（token） |
| `minChunkSizeChars` | 跟随取 `chunkSize / 2`（即 100 / 250 / 500） |
| 语料 | 6 份，共 5117 字（**不变**） |
| 问题 | 5 个，各带**人工标注的正确答案所在文档**（**不变**） |
| 检索 | `MockDocumentTool` 的字符 2-gram 匹配，取前 3 段（**不变**） |

**为什么必须标注正确答案**：不标注就算不出精确率。这也是 迭代 15 评测集的结构——
问题 + 期望来源。

四个量：

- **片段数 / 平均字数**：切法的直接结果
- **命中率**：正确答案所在的文档有没有被召回
- **精确率**：召回的 3 段里有几段真的来自那份文档（其余是噪声）
- **材料字数**：一次检索喂给模型多少字（**这是上下文成本**，对应 迭代 4 的压缩压力）

## 五、三个观察

### 1. 命中率这个指标，切法再怎么变都是 5/5 —— 它区分不出好坏

答案确实在那份文档里，块大块小都躲不掉。**命中率根本没有信息量。**
这是 迭代 11 那条结论的复现：**只报一个总分，分不清该改哪儿。**
真正有区分度的是精确率和材料字数——一个量噪声，一个量成本。

### 2. 块越小，精确率越高、材料越少 —— 但代价是碎片

材料字数从 1892 降到 589（**不到三分之一**），精确率从 0.57 升到 0.87。
方向完全符合预期。

但代价也露出来了。`chunkSize=200` 切出 3 个 ≤40 字的碎片块，比如：

```
01-销售数据统计口径说明#4   26 字   0（2025-01）：归属期间由创建时间改为完成时间
02-销售区域划分规则#4       17 字   影响所有跨期对比。见第二节的说明。
03-售后与退货管理流程#4     14 字   不是一回事，见第一节的说明。
```

第一个就是第二节说的**切在 `v3.0` 中间**。
后两个是**结论脱离了前提**——「不是一回事」脱离了它否定的那句话之后，
这段话作为独立片段是没有意义的。

**这正是「块太小 → 上下文割裂」的实物证据**，而且它证明的不是「200 不好」，
而是这个切分器在细粒度上**边界不可靠**。

### 3. 「块太大」的害处在 1000 上暴露得最清楚

- 材料字数 2700——**一多半是无关内容**
- 精确率 0.33——召回 3 段只有 1 段是对的
- **`XR-2000B` / `XR-2000C` 落在同一个块里，检索层面再也分不开**

第三条最重要：这两个型号**价格和定位都不同，混了就是数据事故**（语料 05 的原文），
而 迭代 12 留的这个待办，答案就在这里——**块太大，迭代 16 的混合检索也救不回来**
（两个编码在同一个块里，关键词通道同样无法区分）。

### 4. 附带发现：这个切分器对参数高度敏感

把 `chunkSize` 从 250 调到 350（步长 50），碎片块数是 **3 → 1 → 3**：

| chunkSize | 150 | 200 | 250 | 300 | 350 | 400 | 500 |
|---|---|---|---|---|---|---|---|
| 碎片块数（≤40 字） | 3 | 3 | 3 | **1** | 3 | 3 | 0 |
| B/C 能区分 | 是 | 是 | 是 | **是** | 是 | 否 | 否 |

**参数变一点点，切片质量就跳变**——因为它依赖「最后一个标点落在哪」，
而这取决于 token 边界和标点位置的巧合。**这说明切片质量不稳定**，
也说明「靠调 chunkSize 把分块调好」这条路本身走不远。

## 六、结论：chunkSize 定多少

**取 300。**

理由（按权重排）：

1. **`XR-2000B` / `XR-2000C` 必须能分开是硬约束**——这是数据正确性问题，不是体验问题。
   数据上这个约束的临界点在 **350 和 400 之间**：≤350 可分，≥400 不可分。
2. 在可分的那一档里，**300 的碎片块最少（1 个，其余档位都是 3 个）**，
   平均材料字数也低（752，对比 350 的 1096）。
3. 200 虽然精确率最高（0.87），但碎片 3 个、且 05 被切成 5 段，
   碎片其一正是那个切坏的版本号。

**但要写清楚：300 是「在这 6 份语料上」的最优，不是普遍真理。**

真正的结论不是「300 这个数字好」，而是**这个切分器的边界逻辑不够用**：

- 它按字符猜句子边界，所以会切在 `v3.0` 里（第二节第 3 条）
- 它对参数不连续敏感（第五节第 4 条）
- 它没有 Markdown 结构的概念，不知道表格行不能脱离表头

**正确的方向是「按语义边界切」**——按 Markdown 的块结构（标题、列表项、表格行）
或按真正的中文句子边界切。这需要换掉 `TokenTextSplitter`（升到 1.1.3 用
`punctuationMarks`，或者绕开它用同一个 jtokkit 分词器自己切）。
**两条路都会动到已验证的版本矩阵，列为 迭代 15 之后的改进项。**

在此之前，`300` 是在当前能力下最好的取值。

## 七、局限（必须写清楚，否则这张表会被过度解读）

1. **检索方式仍是字符匹配，不是向量检索。** 所以「精确率」衡量的是
   *字符匹配的精确率*。换成向量检索后数字会变（迭代 14）。
2. **语料只有 6 份、5117 字。** 这个规模下三种切法命中率都好看。
   真实规模（几百上千份）下，块大的劣势会更明显——因为干扰项变多。
3. **精确率按「是否来自正确文档」算，没有判断片段是否真的回答了问题。**
   同一份文档里也有无关段落。更严格的评测要判断**片段级相关性**（迭代 15）。
   例：`XR-2000B 是什么产品？` 的理想片段是含型号表的那一段，
   但检索返回的首个片段是含「例如 `XR-2000B`」的编码结构段——
   同属 05 号文档，精确率算它对，但它其实不是最好的材料。
4. **5 个问题太少**，不足以支撑统计结论。它够暴露问题和方向，不够下定量判断。
5. **数字来自源码级复现，不是 Java 实跑**（见文首说明）。请以本地实跑为准。

## 九、复现说明

本文数字来自一份复现脚本，它做了两件事：

1. 逐行对齐 Spring AI 1.1.0 的 `TokenTextSplitter.doSplit`（含标点列表、
   `minChunkSizeChars` 语义、`keepSeparator`、尾部剩余 token 的处理），
   用 tiktoken 的 `cl100k_base` 做 token 化——与 jtokkit 使用的是同一套编码
2. 逐行对齐 `MockDocumentTool.crudeScore` 的 2-gram 打分与排序

**没有模拟的部分**：略去了 Java 的 `System.lineSeparator()` 影响
（已确认 6 份语料全是 LF，Windows 上该替换是空操作）。

**对账结果**：`spring-boot:run` 实跑输出与本文表格**逐项一致**。
也就是说，这套复现方法在这个项目上是可靠的——**沙箱没有 JDK 时，
纯计算类实验仍然可以先算出来、再让本地实跑验收**。
