# 阶段一自检（迭代 1—5）

> 阶段一的目标：**把 Agent 的发动机拆开看明白。**
> 这份清单用来检查这个目标有没有达到。
>
> **用法**：先看左边的问题，**自己讲一遍**（出声讲或者写两句），讲完再对照下面的参考答案。
> 直接读答案是没用的——「读着觉得懂」和「能讲出来」是两件事。
>
> 全答得出来 = 阶段一过关，可以进阶段二。

## 一、基本功

### 问题：画出 Agent 的循环图

不看代码，在纸上画出 `MinimalAgentLoop` 干的事。画完之后对照：

```
把消息列表 + 工具定义 发给模型
        ↓
模型返回一条消息
        ↓
它有没有要求调用工具（tool_calls）？
        ├── 有 → 执行工具 → 把结果作为一条 role=tool 的消息塞回列表 → 回到第一步
        └── 没有 → 循环结束，这条消息就是最终回答
```

**过关标准**：你能画出这个结构，并且能指出**唯一的出口是「模型没要求调工具」**，
而不是任何代码里写死的次数判断。

## 二、四个必答问题

### 1. 模型怎么决定调哪个工具？

**参考答案**：靠你给它的**工具说明书**。请求里的 `tools` 数组包含每个工具的
`name`、`description`、`parameters`——**这三样全部会成为模型提示词的一部分**，
它据此判断「这个问题该不该调我、参数怎么填」。

**关键认知**：`description` 不是注释，**是提示词**。写得含糊，模型就选不准。
这一点在 迭代 8 设计路由时会变得非常关键。

### 2. 工具结果怎么回到模型？

**参考答案**：作为一条新消息追加到消息列表里，并且**必须带上 `tool_call_id`**，
和模型那次请求的 `id` 配对。然后**把整份列表重新发给模型**。

**关键认知**：
- 模型是**无状态**的——它没有记忆，每一轮都是从头发读一遍整份消息列表。
  所以它「知道」工具结果，纯粹是因为那条消息躺在列表里。
- `id` 配对不是形式要求，是硬约束。对不上，服务端直接报 400。
  迭代 3 的实验二你亲眼见过。
- 一旦历史里有工具调用，**消息列表不能随便切**（迭代 4 的压缩就栽在这上面）。

### 3. 上下文长了怎么办？

**参考答案**：压缩。迭代 4 的 `ContextCompactor` 把消息列表切成三段：

```
[system]  [较早的对话 → 变成一段摘要]  [最近的对话]
   ↑                ↑                      ↑
永不压缩       交给模型总结             永不压缩
```

**过关标准**：能说出**这两个「永不」各自的理由**——
system 是模型的角色说明，压掉等于换了个人；最近的对话是接下来几轮最需要的，
只有压远处才有意义。

**加分项**：答出压缩的代价——**信息可能走样**。迭代 4 实测见过两种：
摘要污染（把助手的建议记成用户的要求）、编造过程（声称做过没做过的事）。

### 4. 循环什么时候结束？

**参考答案**：模型不再返回 `tool_calls` 的时候。也就是**它自己判断「够了」**。

**关键认知**：走几轮、调不调工具、调几次——**都是模型决定的，不是代码决定的**。
你写的循环只提供「能调工具」这个能力和「结果回灌」这个动作。

**加分项**：`MAX_STEPS` 那种上限是**兜底**，不是正常出口。
它的作用是防止模型犯轴无限循环，不是用来控制流程的。

## 三、阶段一积累的六个概念

| 概念 | 一句话 | 讲不清就回去看 |
|---|---|---|
| 工作流 vs 智能体 | 决策权在代码里还是模型手里 | 迭代 1 笔记 + Building Effective Agents |
| ReAct | 让模型先写「想」再写「做」，推理显式化 | 迭代 3 |
| 原生 tool_calls vs 文本协议 | 前者由服务端保证结构，后者靠约定、很脆 | 迭代 2 与 迭代 3 对比 |
| 消息列表的配对约束 | assistant 的 tool_calls 和 tool 结果必须成对 | 迭代 2 实验二 |
| 上下文压缩 | 三段切分，两头不动、中间摘要 | 迭代 4 |
| 权限门 + 计划 | 按风险分级放行；计划放在消息列表外面所以压不到 | 迭代 5 |

## 四、两个值得能讲出来的「现场」

这两个是你亲手跑出来的，面试时讲细节比讲概念有说服力。

**1. 上下文压缩时，模型编造了用户没提过的要求。**

第一轮跑，回答里出现了「3 家咖啡馆」「手划摇橹船」——用户从没说过。
原因是摘要把**助手自己的建议**记了进去，模型之后把建议当成了用户的要求。
收紧摘要提示词（只记录用户说过的）后，幻觉消失。

**2. 模型声称自己做过没做过的事。**

同样的回答里还有「实查地图+商户电话确认」——它不可能打过电话。
**这类错改提示词治不了**，而且正对应项目最大的风险：模型没查库却说「我已查询，结果是 1.28 亿」。

**行动项（迭代 21）**：答案必须附真实执行痕迹（SQL 原文 + 返回行数），
让「有没有真查过」可验证。
