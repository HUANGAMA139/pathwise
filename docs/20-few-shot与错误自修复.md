# 迭代 20 · few-shot + 错误自修复

> 目标：① 给几个「问题 → SQL」样例；② SQL 报错时把错误回灌给模型让它改，而不是直接抛给用户。
> 记住这一节的一句话：**这是「Agent 比固定工作流强」最直观的那个例子。**
> 新增：`src/main/resources/text2sql/few-shot.md` · `tools/text2sql/FewShotExamples` · `Text2SqlDiagnostic` · `agent/SqlRepairDemo`
> 改动：`Text2SqlDatabaseTool`（few-shot 注入 + 自修复循环 + 故障注入口子 + 参数收进 `Options`）
> 开启方式：
> ```
> mvn spring-boot:run "-Dspring-boot.run.arguments=--sdaq.exp20.enabled=true"
> ```

## 一、两件事治两个症状

迭代 18 那 9 道题跑完，失败分成了**性质完全不同的两半**——本轮这两件事正好一人管一半：

| | 症状 | 本轮的手段 |
|---|---|---|
| **跑不通** | SQL 执行**报错**（字段名写错、类型不对） | **错误自修复**：把报错回灌给模型 |
| **跑得通但答案错** | SQL 合法、有结果、**数据库一声不响** | **few-shot**：把「值域」这类隐性规则示范给它 |

**分界线就是「数据库报不报错」。** 这个分法不是本轮发明的——迭代 18 的结论就是
「最危险的错误都是不报错的那些」。所以修法也必须分开：
报错的错可以**自动**修（有明确的信号），不报错的错只能**提前**防（靠样例/规则/文档）。

**一个反过来的推论**：**「0 行」不该触发自修复。** 0 行不是错误，
迭代 18 已经证明它既可能是「真的没数据」、也可能是「取值写错了」。
拿 0 行去重试，等于让模型瞎猜——而且会把本该由 few-shot 解决的**值域**问题，
变成一连串随机试探。这条下面还会再说一次，因为它是自修复最容易做歪的地方。

## 二、12-Factor Agents 里那一条：把错误压缩进上下文

本轮要用的就是那一句。它的意思是：

> **别把错误当成异常抛给上层，要把它当成一次新的输入。**

对应到代码上，`executeWithRepair` 的形状是这样的：

```
生成 SQL → 执行 ─失败─→ 把【失败的 SQL + 数据库报错 + 表结构】塞回上下文 → 模型改 → 再执行
                    └─成功─→ 返回结果（并把「修过 N 次」记在 SQL 里）
```

**为什么这一圈就是 Agent 相对流水线的增量**：固定流水线里「生成 → 执行」是一条直线，
一报错整条挂掉，用户拿到的是一个异常。而模型本来就有能力看懂
`column "order_amout" does not exist` 并把它改对——**缺的只是有人把这句话递给它。**
把报错递回去，是**只有 Agent 才做得出来**的动作（流水线没有「再想一次」这个环节）。

> 面试里被问「为什么用 Agent 不用固定工作流」时，这是最实在的答案：
> **不是因为 Agent 更时髦，是因为流水线遇到 SQL 报错只能挂，而 Agent 能自己看错误重试。**

## 三、few-shot：补的是【值域】

### 它对着 迭代 18 最大的失分点打

迭代 18 实测：**4 道题因为把 `'华东'` 写成 `'华东区'` 而返回 0 行，而且不报错。**
表结构注入给了表、列、类型、可空、主键、外键、注释，**唯独没给「列里到底存了哪些字面量」**。

few-shot 正是补这个的常规手段：给一条「问『华东区』、SQL 里写 `'华东'`」的样例，
模型**照样式**就学到了——比在提示词里写一句「区域名不带区字」更自然，
因为它不需要「读懂规则再应用」。

### 样例长这样（`text2sql/few-shot.md`，7 条）

按价值排序，消融实验从 0 条一路加上去，所以最有价值的放最前面：

| # | 样例教什么 |
|---|---|
| 1 | **值域 + 归期列 + 状态过滤 + NULL** —— 一条样例压四个坑（`region = '华东'`、`completed_at`、`COMPLETED/REFUNDED`、`COALESCE`） |
| 2 | 产品线要 JOIN `products` 拿 `line_code` |
| 3 | **2024 年及以前走 `orders_archive`** |
| 4 | 排名：按净额 `ORDER BY ... DESC`，不用硬 JOIN `regions` |
| 5 | 省份映射在 `region_provinces`；订单表**没有省份** → 「某省的销售额」算不出来 |
| 6 | **客单价的分母只计 `COMPLETED`**，且不要用 `AVG()` |
| 7 | `order_items` 是明细，**口径上的「销售额」不用它** |

### 为什么样例放在资源文件里，不写在代码里

三条都很实际：**它是数据不是逻辑**（加一条不该改 Java）；**要能快速对错样例**
（看到某题错了，第一反应就是「该加个样例」，改 .md 比改代码快，diff 也清楚）；
**要能做消融**（`sdaq.text2sql.few-shot-size` 从 0 加到满，才知道样例值多少分）。

### 一条必须说清的边界：这和「口径该在文档里」有点冲突

样例 1 和 6 里写着「归期看 `completed_at`」「客单价分母只计 `COMPLETED`」——
**这不就是把该在文档里的口径编进了 prompt 吗？** 是的，而且必须承认这个张力。

区别在**时机**：

```
口径作为【回答时的依据】 → 在文档里（用户要能被引用、被核实）
口径作为【写 SQL 时就必须遵守的约束】 → few-shot 里（模型不先知道它，WHERE 就写不对）
```

所以 few-shot **不是替代文档**，它是把少数「生成时就必须遵守」的规则做成了样式。
**代价也得记着**：样例一多，prompt 就变成了一份会漂移的第二真相——
文档改了它不会自动跟着改。所以样例要少而准，不能无节制地堆。

## 四、自修复的四条纪律

每条都对应一种「修歪了」的方式：

| 纪律 | 不这么做的后果 |
|---|---|
| **只有执行报错才修，0 行不修** | 0 行不是错误。拿它重试 = 让模型瞎猜，还会把值域问题变成随机试探 |
| **修好的语句仍要过只读护栏** | 「第一次 SELECT、修一次变成 DROP」是必须拦的 |
| **修不出可用 SQL 就收手，不硬撑** | 模型连着两次给出空/纯注释/非只读，就该停，如实上报 |
| **修复痕迹留在返回的 SQL 里** | `QueryResult.sql` 是「答案是怎么来的」的唯一证据；只看最终那条，看不出它是重试来的 |

### 提示词里最要紧的一条：**只修错，别换题**

```
2. 【只修导致报错的地方】——表名、字段名、类型、函数用法。
   不要改变查询的意图、统计口径和筛选条件。
```

**模型很容易把「修错」做成「换一个问题来答」**：原 SQL 因为列名写错而报错，
它干脆改成查另一张表，报错没了、答案也变了。那种「修好了」是最坏的：
**报错消失，错误留下。**

第 4 条同样重要：如果报错本身就说明「这个库答不了这个问题」，
正确的修法是**承认答不了**，而不是绕出一条能跑通的 SQL。
（迭代 18 的 D7 就是这么栽的：模型写了个口径错误的 JOIN，报错没了、答案是错的。）

## 五、验收怎么做：控制变量，不是等模型偶然写错

产出要求是「故意注入一个错误（比如改了字段名），系统能自修复」。
**靠等模型偶然写错来验证是不行的**——碰运气、且不可重复。所以做法是：

```
1) 先正常跑一次 D1，拿到模型真的写出来的那条 SQL
2) 从这条 SQL 里挑一个真实的标识，把它改坏   ← 这就是「故意注入」
3) 同一条坏 SQL：repair=0 跑一次（应当失败）、repair=2 跑一次（应当自己改回来）
```

第 2 步的「挑」是在**模型真的写出的 SQL** 上做的（按 `order_amount` → `sales_orders` →
`refund_amount`… 的顺序找第一个出现过的），所以不会出现「注入没生效」这种假验收。
工具侧还加了一句保险：注入后如果 SQL 没变化，会**明确告警**说这次注入没匹配上——
不能让「没注进去」被当成「注入了但修好了」。

为此在 `Text2SqlDatabaseTool` 上加了一个默认关闭的 `Options.fault` 口子。
它不只是为本轮：**迭代 21 要验「故意让它生成 `DROP TABLE`，安全边界拦不拦得住」，
用的是同一个口子**——故障注入是自修复测试和安全测试的共同工具。

### 发现 1：**一条样例就修掉了四个坑**（0 → 4）

n=1 只注入样例 1，D1/D3/D4/D5 四道同时转正。看它写出来的 SQL：

```sql
SELECT SUM(order_amount - COALESCE(refund_amount, 0)) AS net_sales
FROM sales_orders
WHERE region = '华东'                    -- 值域：不再写 '华东区'
  AND status IN ('COMPLETED', 'REFUNDED') -- 状态过滤：不再写成 PAID
  AND completed_at >= '2026-04-01' ...    -- 归期列：不再用 created_at
```

**迭代 18 里那句「一条样例压四个坑」的设计成立了**——值域、归期列、状态过滤、NULL 处理，
全都在这一条里被示范掉了。这个杠杆比很高：412 字符换回 4 道题。

### 发现 2：三个坑各自需要哪条样例，能一一对上

| 从哪条开始转正 | 靠的是哪条样例 |
|---|---|
| D8（2024 → 归档表） | 样例 3「2024 年 → `orders_archive`」 |
| D7（福建 → 答不了） | 样例 5「订单表只有区域名，没有省份字段」 |
| D9（客单价分母） | 样例 6「分母只计 `COMPLETED`，不要用 `AVG()`」 |

**这是一次很干净的对账**：样例是按「哪个坑」挑的，转正的时点也对得上。

D9 尤其能看出样例在起作用：n=1 和 n=3 时它写的是
`AVG(order_amount - COALESCE(refund_amount,0))` + `status IN ('COMPLETED','REFUNDED')`
→ 分母是 7 单、算出 5,157,143（那是**另一种合法读法**）；
n=7 注入样例 6 之后才改成 `SUM(...) / COUNT(*)` + `status = 'COMPLETED'` → 6,016,667 ✓。

### 发现 3（本轮最有价值的一条）：D7 从「硬编一个假数字」变成「如实说答不了」

这是全表里唯一一道**性质变了**的题，而不是「值算对了」：

```
n=1  D7 → SELECT SUM(...) FROM sales_orders o
          JOIN region_provinces rp ON o.region = rp.region_name
          WHERE rp.province_name = '福建省'      ← 口径错的 JOIN，返回 1 行
n=3  D7 → 同上，但把 '福建省' 改成了 '福建'      ← 取值对了，于是【真的返回了一个数字】
n=7  D7 → -- 无法回答：订单表中没有「省份」字段，只有「区域」字段；
          福建省属于哪个销售区域需查 region_provinces 表，但……因此无法直接统计
```

**注意 n=3 那一步最危险**：取值改对之后，那个口径错误的 JOIN **不再返回 0 行，而是返回整个华东的销售额**，
并被当成「福建的销售额」报出来。
（按 SQL 结构推，它返回的就是 **36,100,000** —— 和问「华东的销售额」得到的数字**一模一样**。
日志里只打了「返回 1 行」没打值，所以这是从 SQL 和种子数据推出来的，不是读出来的。）
**样例 5 补上之后，模型才主动承认答不了。**

这正是 迭代 18 记下的那条「假数字」风险的完整生命史：
**从「写错 → 报 0 行 → 看起来像没数据」到「取值修正 → 返回一个像模像样的错数字」再到「如实拒答」。**
中间那一步比以前更危险，而它是**修上一个 bug 修出来的**：
`JOIN region_provinces` 这个动作本身没错（外键标注起作用了），错的是**它在一对多关系上用过滤当筛选**——
这个错在取值不对时被 0 行掩盖着，取值一修对就暴露成「一个看起来完全正常的数字」。

### 发现 4：自修复验收通过（控制变量，不是碰运气）

```
第 1 步  正常跑一次 D1，拿到模型写的 SQL
第 2 步  故障注入：order_amount -> order_amount_typo
第 3 步a repair=0 → 失败：
         ERROR: column "order_amount_typo" does not exist 位置：12        [期望] 应当失败 —— 符合
第 3 步b repair=2 → 成功：自修复 1 次后执行成功，返回 36100000.00
         返回的 SQL 开头带着痕迹：
         -- [自修复 1 次后成功] 首次失败：ERROR: column "order_amount_typo" does not exist 位置：12
                                                                       [期望] 应当自愈 —— 符合
```

三条都对上了：**注入生效了**、**不修就失败**、**修了就好，而且把痕迹留在了 SQL 里**。

### 发现 5：那两档「需人工判断」**盖住了一部分真实改进**

判据把 D2 和 D6 归成「人工」——它们本来就没有机器判法（一个是多行排名、一个是文本列表）。
但**它们也变好了**：

- **D6**：n=0 返回 **0 行**（`'华东区'` 写错），n≥1 返回 **5 行**（对的，华东就是 5 个省）——
  **行数就能看出它修好了**，只是判据没写这一条。
- **D2**：n=0 用的是 `created_at`（迭代 18 里算出 27,300,000），n≥1 全改成 `completed_at`。
  从 SQL 看是对的，但数值没被自动核对过。

**所以「0 通过 / 7 失败 / 2 人工」这句话低估了 n=0 的糟糕程度，也低估了 n=7 的改善幅度。**
按行为看，n=7 时**九道题应当全对**（7 道自动确认 + 2 道人工档里 D6 已由行数确认）。

> 这条值得记：**判据的粒度决定了你能看见多少改进。** 人工档不是「没结论」，
> 而是「结论要靠人补」——所以人工档里的题，跑完一定要有人去看一眼。

## 七、★ 一条被实跑修正的判断：旧基线**确实**可复现，但它有个前提

写这个 demo 的时候，我以为「迭代 19 扩表已经把 迭代 18 的基线毁了」，还把它当成当时的头号发现。
**实跑把它推翻了**——而且是往好的方向推翻：

```
[Text2SQL] 元数据读取完成：5 张表 / 26 列 / 3 条外键
n=0 → 0 通过 / 7 失败 / 2 人工     ← 与 迭代 18 记下的数字【逐位一致】
```

**库还是 5 张表**，`docker/init-business-db-extra.sql` 还没被执行。所以：

- ✅ **「旧基线可复现」这条纪律第一次被真正验证**（而不只是声称）：
  同一份代码路径（不筛表、无 few-shot、不自修复）+ 同一份库 → 逐位复现 迭代 18。
  这是 迭代 14 以来一直在守的东西，本轮终于有了第一手证据。
- ⚠️ **但它有个前提：库不能变。** 而扩表脚本已经躺在仓库里了。
  **它一旦执行，迭代 18 的基线就再也复现不出来**——因为
  **代码侧有 `mode` 可以切回去，数据侧没有。**

### 我犯的这个错本身也值得记

我把一个**尚未发生的风险**写成了**已经发生的发现**，还写进了文档和记忆。
这和 迭代 15 那个「差点把『框架判得太严』这个听起来很合理的错解释写进文档」是同一类错误：
**推论听起来对，但它不是跑出来的。**

区别在于：迭代 18/19 的发现都有一条实测数字支撑，而这条没有——
它的依据是「扩表脚本存在」，不是「扩表已经发生」。**这两件事差得很远。**

> **所以规矩再加一条：写进文档的「发现」，必须能被某一条实测输出指出来。**
> 没有数字支撑的，只能写成「风险」或「预判」，并且明确标注它是预判。

### 因此多了一条真实的取舍（下次动手前必须想清楚）

| 要做什么 | 代价 |
|---|---|
| 跑 迭代 19（表筛选） | 必须先灌扩表脚本 → **迭代 18 的基线当场作废** |
| 保住 迭代 18 的基线 | 就不能扩表 → 迭代 19 跑不了 |

**两条路不能同时要。** 可选的做法：
先跑完所有需要「5 张表基线」的对比，再扩表；
或者扩表前把 5 张表的库 `pg_dump` 留一份，用另一个端口起一个老库。
**唯一不行的是**：先扩了表，回头才发现有个对比没做——因为**库没有 `mode` 可以切回去**。

## 八、本轮踩到的坑（复用前必看）

| 坑 | 说明与正确做法 |
|---|---|
| **旧基线可复现，但前提是库不能变** | 代码侧有 `mode` 可以切回去，**数据侧没有**。扩表脚本一旦执行，跑在 5 张表库上的 迭代 18 基线就**再也复现不出来**（本轮 `n=0` 那次逐位复现 0/7/2，可能是最后一次）。**动库之前先问：有没有人要拿这个库做对比？** |
| **不要把自己的「推论」写成「发现」** | 我写 demo 时把「扩表已经毁了 迭代 18 的基线」当成当时的头号发现，还写进了文档和记忆；**实跑证明库根本没扩过**。规矩：**写进文档的「发现」必须能被某条实测输出指出来**；没有数字支撑的只能写成「风险」或「预判」，并明确标注。这和 迭代 15 那个「差点把『框架判得太严』这个听起来很合理的错解释写进文档」是同一类错误 |
| **自修复很容易被做歪成「换个问题来答」** | 报错消失、错误留下。提示词必须明确「只修导致报错的地方，不要改变查询意图」 |
| **「0 行」不能触发自修复** | 0 行不是错误；拿它重试等于让模型瞎猜 |
| **失败标记必须和判据对齐** | 诊断集靠字面量 `[执行失败]` 认出「没跑成」。自修复失败若换个写法，判据会把它当成「跑成功但结果为空」——**数字整体偏乐观，且不报错**。所以两种失败都带 `[执行失败]` |
| **参数涨到 10 个就该收进对象** | 10 个位置参数没人读得懂，而且加错一个**不会报错**（类型一样就编过了）。本轮抽成了 `Text2SqlDatabaseTool.Options` |
| **few-shot 文件解析失败必须响** | 「文件在、却一条都没解析出来」是最难发现的静默失败（程序照跑，只是样例没生效，你会以为是「样例没用」）。加载器对这种直接抛异常，而且做成一启动就加载 |

## 九、局限

1. **few-shot 的样例是「知道这 9 道题的答案」之后写的 —— 这是训练集等于测试集。**
   0 通过 → 7 通过 这个提升是**上界**，不是泛化能力。真正的检验要拿一套**没见过的**问题，
   本轮没有这样的留出集。**所以「默认开 7 条」这个决定只在这 9 道题上是数据支撑的。**
2. **判据的人工档盖住了改进**（发现 5）：D6 从 0 行变 5 行、D2 从错列变对列，
   但判据都报「需人工判断」。**看「7 通过」会低估实际改善幅度。**
3. **自修复的验收是「注入一个人造错误」**，不是真实场景里的错。真实的 SQL 错误更多样
   （类型不匹配、聚合用法、方言），本轮只验了「标识写错」这一类。
4. **自修复的成本没单独记。** 每次失败多一次模型调用；本轮唯一那次修复多花了约 2 秒。
   迭代 22 出执行准确率时应该一起记延迟。
5. **few-shot 和「口径在文档里」的张力**（第三节）本轮只是点出来，没有解决——
   而且消融证明它确实有效，所以这个张力是「值得付的代价」还是「在绕开文档」，仍然没答。
6. **`repair-attempts` 没扫。** 只跑 2 次；1 次够不够、3 次有没有收益，都没试。
7. **本轮只跑了 迭代 20 的 demo。迭代 19 的表筛选还没实跑**，而且**跑它之前必须先灌扩表脚本**——
   而那会把 迭代 18 的基线（也就是本轮 `n=0` 那一行）变成不可复现。见第七节。
