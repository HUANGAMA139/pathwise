# 迭代 6–7 实测：用框架的代价——拦截点没了，Advisor 也补不上

> 迭代 6 跑 `SpringAiAgentLoop`、迭代 7 跑 `AdvisorAndOutputDemo` 时观察到
> **这份是 迭代 21（SQL 安全边界）的直接输入，别删。**

---

## 现象

迭代 6 的任务是把 迭代 2 的手写循环换成 Spring AI 的 `ChatClient`。
写完后跑了两次调用，**代码一字不差**：

```java
chat.prompt(问题).tools(tools).call().content()
```

**运行 A**（`北京今天天气怎么样？`）日志：

```
>> [工具被调用] getWeather(city=北京)
模型最终回答：北京本轮有小雨，气温为18℃……
```

**运行 B**（`把订单 A1001 和 A1002 永久删除。`）日志：

```
>> [工具被调用] deleteOrders(orderIds=A1001,A1002)
!! 这个破坏性操作真的执行了 —— 我们的代码全程没有机会拦它
模型最终回答：订单 A1001 和 A1002 已成功永久删除。
```

**删除真的发生了。没有任何东西拦住它。**

---

## 为什么

`@Tool` 标注的方法会被框架**自动执行**，这是它的设计目的——
官方文档原话：*Spring AI handles the full round-trip automatically*。

一次 `.call()` 内部自动完成：

```
发请求 → 收到 tool_calls → 反射调用你的 Java 方法
                → 结果包装成消息塞回 → 再发一次 → 直到模型不再要工具
```

**这四步就是 迭代 2 手写的那个 while 循环**，现在跑在框架肚子里。

**代价在这里**：迭代 2/5 的循环是手写的，所以存在一个明确的
「执行工具之前」的位置，可以在那里插权限检查。
**现在这个位置不存在了**——工具是被框架反射调用的，中间没有你的代码。

---

## 和 迭代 5 的关键区别（两类完全不同的失败）

| | 迭代 5 | 迭代 6 |
|---|---|---|
| 模型做了什么 | **自称**完成了删除，实际没删 | **真的**执行了删除，并如实汇报 |
| 谁有问题 | 模型（自述不可信） | **我们的设计**（工具没防护） |
| 修法 | 改成拿实际执行对账 | 给工具加防护 / 找回拦截点 |

**迭代 6 这类更危险**：模型没有说谎——「已成功永久删除」是准确的。
**问题不会以「模型在骗你」的形式暴露，它会以「一切正常」的形式发生。**

对本项目意味着：如果数据库工具没有防护，模型可以真的去执行破坏性 SQL，
而用户和日志都看不到任何异常。

## 重建控制权的几条路（迭代 21 选一条落地）

1. ~~**自定义 Advisor**~~ —— **迭代 7 实测排除了它**，原因见下
2. **包装 ToolCallback**——不让框架直接持有原始工具，而是包一层，
   在里面做权限判断 ← **目前看最可行**
3. **关掉自动执行**——让框架只返回 tool_calls，自己执行并回灌
   （就是回到 迭代 2 的写法，但那样又失去了框架的便利）

### 迭代 7 的修正：Advisor 解决不了这个问题

原本以为 Advisor 可以插在工具执行前。**迭代 7 实测证明不行**，证据是日志的嵌套关系：

```
[Advisor] >>> 进入
      >> [工具被调用] getWeather(city=北京)     <- 夹在中间
[Advisor] <<< 返回。整段耗时 2155 ms
```

**一次 Advisor 的进入/返回，把整个工具往返整段包住了。**
说明工具循环跑在 Advisor **里面**，而不是由 Advisor 逐步编排。

所以分层是：

```
Advisor 层        ← 能看到「整个模型调用」的请求和最终响应
   └── 工具循环    ← 在这里面，Advisor 看不到单次工具调用
```

**结论**：Advisor 是「整次调用之前/之后」的扩展点（RAG 检索注入、对话记忆、
日志追踪、重试都挂这里，迭代 26 的模块化 RAG 全靠它），
但**它拦不到「每个工具执行前」**。

> 注：Spring AI **2.0** 才把工具循环提到 advisor 链上（官方原话：
> *makes the tool calling loop a first-class, composable component of the
> ChatClient's advisor chain*）。**1.1.0 做不到**，所以要拦住单个工具，只能选 2 或 3。

### 顺带一个坑：CallAdvisor 不包 streaming

迭代 7 还实测到：`CallAdvisor` 只在 `.call()` 时生效，`.stream()` **完全绕过它**。
日志里流式那段没有任何 Advisor 输出，**也不报错**。

意味着挂在 Advisor 上的日志/限流/重试/审计，在流式路径上会**静默失效**。
要用得实现 `StreamAdvisor`。

**这又是一个「不报错的错误」**——和 迭代 4 的摘要污染、迭代 5 的进度条同一个家族。

## 可推广的原则

**引入框架时，要明确问一句：它接管了什么，我因此失去了哪些介入点？**

省掉的代码不会凭空消失，它变成了框架内部的一步。如果那一步恰好是你需要控制的
（权限、审计、限流、幂等），你就必须去找它的扩展点，而不是假设「框架会处理好」。
