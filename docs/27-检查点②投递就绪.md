## 二、★ 核对才看出来的一件事：**产品跑的配置 ≠ 本轮量出的最优配置**

主链路当前的实际档位（从 `application.yml` 读出来，不是凭记忆）：

```
retrieval.mode = hybrid        rerank.mode = llm
rag.rewrite.mode = none        rag.pipeline.enabled = false
```

→ 它对应消融表里的 **`none+hybrid+llm` = MRR 0.922**。
而 迭代 26 量出的最优是 **`llm+vector+llm` = 0.933**。

**但这不代表该改配置**——把差值和噪声摆在一起看：

| 候选改动 | 从 | 到 | 差 | 判断 |
|---|---|---|---|---|
| 加改写（hybrid 上） | `none+hybrid+llm` 0.922 | `llm+hybrid+llm` 0.922 | **0** | 白花一次调用 |
| 改 retrieval=vector（不开改写） | `none+hybrid+llm` 0.922 | `none+vector+llm` 0.922 | **0** | 打平 |
| **vector + 改写** | 0.922 | `llm+vector+llm` **0.933** | **+0.011** | **在抖动带内**（llm 档单次跑的抖动就有 ±0.011，迭代 17 已写明） |

**结论：消融找到了一个「最优」，但它和产品配置的差距落在噪声里——不值得为它改配置。**
这本身就是「所有优化都要通过评测验证」的另一半：**评测也能否掉一个优化。**

> ★ 但有一处**值得改，理由是成本不是准确率**：在**不精排**的条件下，hybrid 明显不如 vector
> （0.847 vs 0.906，差 0.059，超出噪声）。精排把这个差距抹平了（0.922 vs 0.922），
> 可**hybrid 要多维护一路 BM25 索引 + 一次融合**。**同样的准确率，少做一件事**——这是笔划算的账。
> （要不要改，留到 迭代 28——那里本来就是做端到端消融。）

## 三、现在这个系统**能**做什么（带数字）

1. **四值路由**：给一个问题，判断走文档 / 数据库 / 两边都要 / 拒答。28 题上 **27/28**。
2. **文档问答（RAG）**：19 个片段的 pgvector 检索 + BM25 + 精排/MMR，**hit@1 0.87~0.93**，答案带出处。
3. **数据问答（Text2SQL）**：20 张表的业务库，筛表 → 注入表结构 → 生成 SQL → 执行 → 失败自修复。**few-shot 7 条之后，迭代 18 那 9 道题全部通过**（0 → 7）。
4. **一条命令出评测报告**：六类指标 + 混淆矩阵 + 分类分组 + agent/basic-rag 对照。
5. **对外暴露**：MCP Server，3 个工具（高层问答 + 两个低层工具），`http://localhost:8080/mcp`。
6. **安全边界四层**：提示词 / `SqlGuard` 准入（18 条攻击全拦、13 条合法全放）/ **只读账号**（唯一不依赖我代码没洞的一层）/ 实例隔离；外加脱敏与行数超时。
7. **可复现**：**17 个独立 demo 开关** + 7 张消融 CSV，任意一轮的基线都能一键跑回来（迭代 26 刚用回归检查证明了这一点）。

## 四、★★ 现在这个系统**不能**做什么

**这一节才是这份小结的价值所在。** 每一条都有出处。

### 4.1 数字上的三条硬边界（对外引用时必须带上说明）

| 数字 | **不能这么说** | 应该说 |
|---|---|---|
| 路由准确率 **0.89~0.96** | 「我的路由准确率 96%」 | 28 题小样本，**run-to-run 摆动实测 ±2 条（0.071）**；且错误**集中在 `document→X`**，其中 `document→database`（会产生不可察觉的假数字）**一次都没消掉** |
| 端到端正确率 0.71 / 执行准确率 **0.38** | 「执行准确率只有 38%」 | **3/8 的失败是测试集缺陷**（B02/B03/X04 题面没写时间范围），不是系统的锅。真实水平 ≈ 3/5 + 3 条待修题 |
| 检索 hit@1 0.87 | 「我的检索 87% 准确」 | 是 **15 道 document 题**上的**文档级**命中率（不是片段级）；且**1 道题就是 0.067** |

### 4.2 能力上的缺口

1. **多轮对话没做**：`ContextCompactor`（迭代 4）实现了、有独立 demo，**但不在主链路里**。每次问答是独立的。
2. **值域该由谁提供，没结**：现在靠 few-shot 把 `'华东'` 教给模型，**但样例一多，提示词就变成一份会漂移的第二真相**（迭代 20 就记了这个代价）。
3. **口径错的假数字，路由层管不到**：迭代 18 的 D4（两个方向相反的错抵消、只差 2.3%）是最隐蔽的一档，**附了 SQL 也防不住**（迭代 25 第三节）。
4. **`both` 不是安全牌**：误判成 both 会把无关支路的材料带进上下文（迭代 8 实测：答案里多一个没问过的数字）。
5. **降级路径没被量过**：路由失败会降级到关键词（准确率 14/28），表筛选失败会降级到全量——**这两条降级路一次都没在评测里被触发过**。
6. **MCP 那条路自 迭代 10 之后没再端到端验过**：之后数据库支路从 mock 换成了真 Text2SQL、加了安全边界，**README 里「别人可以接入」这句话的最近一次验证是 迭代 10**。每次启动能看到「Registered tools: 3」，但那只证明**注册了**，不证明**调得通**。
7. **权限门 / Plan 没接入**（迭代 5 的产物），项目复杂度还没到那一步。
8. **没有前端、没有并发、没有部署**（范围围栏内，明确不做）。
9. **检索层的成本维度没量**：迭代 24 给路由做了「token 成本」，**但检索层没做**——比如「rerank 那一次调用值不值 0.016 MRR」，本轮答不了。

### 4.3 安全上的诚实边界

- 脱敏**按列名**，已知缺口：`UNION` / 聚合列拿不到底层表 OID → **能绕过**（迭代 21 固化成了用例）。
- `SqlGuard` 挡不住 PG 的 `$$…$$` 和 `E''` 转义——**后果是误报不是漏放**（刻意选的偏向），所以**它不该是唯一一层**。真正硬的是只读账号。

3. 降级路径加进 迭代 23 的报告（跑一遍能看到自然触发与否）；
4. 其余留给 迭代 28—30 的范围内。

> ★ **不要为了「都学过」而补。** 上面第 1、2 条是**已经在对外承诺里的话**，属于必须兑现；
