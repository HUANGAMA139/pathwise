# 迭代 16 · 混合检索 + RRF 融合

> 目标：给文档支路挂上「向量 + BM25」双通道，用 RRF 融合，然后和单路比
> 新增：`tools/hybrid/`（`Bm25Index` · `RrfDocumentJoiner` · `HybridDocumentTool`）· `agent/HybridRetrievalDemo`
> 开启方式：
> ```
> mvn spring-boot:run "-Dspring-boot.run.arguments=--sdaq.exp16.enabled=true"
> ```

---

## 一、本轮最大的发现：框架里这两个东西都没有

先说清楚，因为它直接决定了本轮的工作量：

| 需要的东西 | Spring AI 1.1.0 里有吗 |
|---|---|
| `DocumentJoiner` 接口 | ✅ 有（`org.springframework.ai.rag.retrieval.join`，在 `spring-ai-rag`） |
| **RRF 融合作** | ❌ **没有**。唯一的实现是 `ConcatenationDocumentJoiner`——那是「拼接」，不是「融合」 |
| **BM25 / 关键词检索** | ❌ **完全没有**（整个模块树里搜不到） |

所以本轮有两大块是自己写的。**这两个空白正好落在项目的原创点上**（迭代 12 就在说关键词通道，
迭代 14 发现向量分不开近似编码时又点了一次名）。

### 拼接 vs 融合：差别不在实现，在假设

`ConcatenationDocumentJoiner` 做的事是：多路结果拼起来 → 按 id 去重 → **按分数排序**。
它隐含一个假设：**各路的分数可以直接比大小**。而我们的两路分数根本不可比：

```
向量：1 - 余弦距离，挤在 0.6~0.8（迭代 14 实测：有一题 top5 跨度只有 0.0378）
BM25：IDF 加权求和，量纲完全不同（0~10 那种量级）
```

**直接比大小等于让 BM25 的分数量纲决定一切。** 这是「拼接」和「融合」的分界线。

## 二、BM25：它是 迭代 8 那个「2-gram 粗匹配」长大后的样子

`MockDocumentTool.crudeScore` 当年也是数二元组命中比例，但它缺三样东西：

| 缺的 | 补上之后 |
|---|---|
| **IDF** | 全语料都有的词（「销售」）不该和罕见词同权——越稀有的词越有区分力 |
| **词频饱和**（`k1`） | 同一个词出现 10 次不该是出现 1 次的 10 倍 |
| **长度归一化**（`b`） | 长片段天然更容易命中，要按长度打折 |

补上这三样就是 BM25：

```
score(q,d) = Σ   IDF(t) · tf(t,d)·(k1+1) / ( tf(t,d) + k1·(1-b+b·|d|/avgdl) )
           t∈q
IDF(t) = ln( 1 + (N - df(t) + 0.5) / (df(t) + 0.5) )       k1=1.2  b=0.75
```

**这条线索值得记**：迭代 8 的「粗匹配」不是被 迭代 14 的向量检索淘汰了，它是**没长完**。
本轮补完，它成了双通道里不可或缺的一半。

### 为什么用字符二元组，而不是中文分词

中文没有空格，BM25 需要先切「词」。两条路：引分词器（jieba/HanLP）或切二元组。
选了**二元组**：零依赖，中文上效果可接受。

**代价要认清**：它切出来的**不是词**。「销售额」会变成「销售」+「售额」——
语义上有点怪，但检索层能用（查询和文档切出的是同一套二元组）。

### 两个容易写错的地方

1. **切词不能跨越标点。** 先把文本按标点/空白分段、在段内再切二元组。
   否则「…说明。销售额…」去掉句号后会切出一个根本不存在的「明销」。
2. **并列时排序必须确定。** 只按分数排的话，同分文档的顺序取决于哈希表遍历顺序，
   两次跑会给出不同结果——迭代 15 已经在路由上吃过一次「非确定性」的亏。所以同分按文档 id 升序。

## 三、RRF：只比名次，不比分数

```
RRF(d) = Σ_over_each_retriever  1 / (k + rank_i(d))          k = 60
```

只用「这个文档在某一路里排第几」，所以：

- **天然免疫量纲问题**——不用归一化分数，也不用调权重
- **只有「两路都排前面」的文档才会浮上来**——rank=1 贡献 1/61≈0.0164，rank=5 只有 1/65≈0.0154，
  差得不多。这个「两路共识」正是我们要的东西
- `k=60` 是 RRF 原论文取值：k 越大，名次的边际差异越被压平，结果越不被任何一路的极端排名左右。
  **这是「稳健」而非「最优」的取舍**

### 一条 迭代 14 的伏笔在这里兑现

迭代 14 发现：**关键词通道能把 `XR-2000B` 和 `XR-2000C` 分开，靠的不是分数更高
（它俩得分完全相同，都是 0.833333），而是「命中的是哪个片段」。**

当时就写了「融合时用 RRF 比用分数加权更对」——因为分数加权正好会把这个唯一的优势抹掉。
本轮成了实现：**RRF 只看名次，所以那条优势被完整保留。**

## 四、装配上的三件事

### 1. 两个通道必须共享同一个 id 空间

这是融合的前提（`DocumentJoiner` 按 `Document::getId()` 去重）。麻烦在于两边的天然 id 不一样：

```
pgvector 表的 id 列是 uuid（迭代 14 的坑）；业务 id 是 01-...#2，存在元数据里
```

所以 `HybridDocumentTool` **把两路都归一到业务 id**——不是「碰巧一样」，是**构造上强制一样**。
如果两边各用各的 id，RRF 会把「两路共识」变成「谁都没共识」，融合比单路还差，**而且不报错**。

`RrfDocumentJoiner` 里因此放了一个自检：**打印「被两路同时命中」的候选个数**。
这个数接近 0 就说明 id 空间没对上。

### 2. BM25 读的是向量库同一张表，不是重新切一遍

`SELECT id, content, metadata FROM vector_store`。理由：**重新用 CorpusLoader + DocumentChunker
切一遍的话，两路看到的就是两份数据了**——万一分块参数变了、或库里是旧版本，
向量和关键词就在两批不同片段上检索，融合结果没有意义。

### 3. 一个被逼出来的顺序 bug：BM25 索引必须懒加载

Spring 的 **bean 在容器刷新时创建**，而**语料入库是个 `ApplicationRunner`**——
迭代 14 那条 `@Order(HIGHEST_PRECEDENCE)` 只保证 runner 之间谁先跑。

所以「bean 构造」永远早于「入库」。**如果在构造时读库建索引，
全新数据库上会读到 0 行，然后这个索引永远是空的**——而且不报错，
只是混合检索退化成一个只剩向量在干活的哑巴。

懒加载把这个顺序问题消掉了：真正第一次检索时，入库早就跑完了。

## 五、本轮怎么测：绕开端到端

迭代 15 花了一整天才量出两个噪声底：

```
判分噪声 0.20 / 条（同一输入送两次判分差一个片段）
路由噪声 ±1 条 ≈ 0.036（同一题两次跑出不同路由）
```

拿端到端总分去比 迭代 15，真实增益会被这两个噪声吃掉。而更根本的是：
**语义族那 3 道题失败在路由层，检索根本不会执行**——混合检索在这几道上影响为零，
端到端数字会**系统性低估**它。

所以这个实验**绕开路由和生成，只测检索**：

| 指标 | 含义 | 成本 |
|---|---|---|
| `hit@1 / hit@3 / hit@5` | 正确文档的片段有没有出现在前 k 名 | **零 LLM 调用** |
| `MRR` | 正确文档的片段第一次出现名次的倒数，取平均 | **零 LLM 调用** |
| `精确率` | 返回片段里来自正确文档的比例 | **零 LLM 调用** |

**零 LLM 调用意味着零噪声**——差异是多少就是多少，而且**两次跑结果必须一模一样**
（这也顺便检验了上面那两条「确定性排序」有没有做对）。

### 一个必须写清的边界

这里的「正确」是**文档级**的（测试集标了期望出处是哪份文档），不是片段级。
所以 `hit@k` 回答的是「找对那份文档了吗」，不是「找对那一段了吗」。

### 三个入口是有意的

`HybridDocumentTool` 除了 `search`（融合）还公开了 `searchVector` / `searchBm25`。
**没有单路的对照，就说不出「融合好多少」。** 产品路径只用 `search`。

### 顺带做的开关：`sdaq.retrieval.mode`

```
vector = 只向量（迭代 14 的基线，**可复现**）
bm25   = 只关键词
hybrid = 双通道 + RRF 融合（默认）
```

**这是个「靠对比数字说话」的项目——一旦旧基线跑不了了，以后任何改进都失去参照。**
迭代 15 那条「metrics.csv 追加而不是覆盖」是同一个道理，只是这次管的是代码。

## 六、实测结果

### 6.1 第一次跑：**混合反而比单向量差**

```
配置       hit@1   hit@3   hit@5   MRR     精确率   平均返回数
vector     0.87    0.93    1.00    0.906   0.533    5.0
bm25       0.67    0.87    0.87    0.756   0.460    4.1
hybrid     0.73    0.93    1.00    0.847   0.480    5.0     ← （候选 5、k=60）
```

**hit@1 从 0.87 掉到 0.73。融合没有提升，反而变差了。**

这一条必须原样记下来，不许粉饰：**本轮是「做了混合检索」但没有「混合检索有效」的一次。**
用户的目标「提升多少不重要，重要的是你有数据」正好对上——**数据说有负作用，那就记录负作用。**

### 6.2 逐题表把机制暴露出来了

| 用例 | vector | bm25 | hybrid | 说明 |
|---|---|---|---|---|
| D01 | **1** | 2 | **2** | 融合把它从第 1 挤到第 2 |
| …（D02~D10 全部都是 1/1/1） | | | | |
| D11 | **1** | — | **2** | BM25 完全没召回；RRF 日志：**0 个被两路同时命中** |
| D12 | 4 | 2 | 2 | 融合把它从第 4 提到第 2（**唯一变好的一题**） |
| D13 | 1 | 3 | 1 | |
| D15 | **3** | — | **5** | 同样 0 个同时命中；从第 3 掉到第 5 |

三个机制，逐题表里都能指出来：

**（a）RRF 给两路同等权重，而 BM25 明显更弱。**
BM25 的 hit@1 是 0.67，向量是 0.87——**弱的那一路会把强的那一路拖下来**。
这是 RRF 的已知前提：它假设各路**可信度相当**。我们这里不相当。

**（b）RRF 的秩粒度太粗，(1,2) 和 (2,1) 是同分的。**
D01：向量排 1、BM25 排 2，融合后变第 2。原因是
**`(向量第1, BM25第2)` 和 `(向量第2, BM25第1)` 算出来的 RRF 分完全相同**（都是 1/61 + 1/62），
谁在前面由同分排序（按 id 升序）决定——**不是证据决定的**。
`k=60` 把名次差异压得太平，两个排名换一下位置对总分毫无影响。

**（c）零字面重合的题上，两路完全不相交。**
D11 和 D15 的 RRF 日志打的是「融合 7 个候选（其中 **0 个**被两路同时命中）」。
这说明两路检索到的是**完全不相交**的集合——RRF 这时只是在**交错拼接两份名单**
（两边 rank1 都是 1/61，打平），于是向量原本排第 3 的正确片段被挤到第 5。

> **这个「0 个同时命中」正是我预埋的自检，它在关键位置响了。**
> 而其余题目显示 2~4 个同时命中——**说明两个通道的 id 空间是对上的**
> （迭代 15 那套「pgvector 主键是 uuid、业务 id 得进元数据」的归一没有白做）。
> 所以这个 0 不是 bug，是两路**真的分歧**。

### 6.3 迭代 14 那个伏笔：**没验成，而且是量测的问题**

迭代 14 留的问题是：「关键词通道能不能把 `XR-2000B` / `XR-2000C` 分开」。
本轮 `D10` 的结果是 **vector 1 / bm25 1 / hybrid 1**——看起来「两个通道都命中了」。

**但这个结果什么也没证明。** 因为我们的指标是**文档级**的：
只要召回的片段来自《05-产品线与编码规则》就算命中，而这两个型号本来就在同一份文档里。
**文档级指标看不见 B/C 的区别**——那需要片段级的标注。

这正是第五节那条「文档级，非片段级」的边界在起作用。
**要真的回答 迭代 14 那个问题，得看「查 B 和查 C 返回的首个片段是不是同一个」**（迭代 14 就是这么测的）。

### 6.4 参数网格跑完了：**假设被否掉，且能证明为什么**

```
配置               候选   k     hit@1   hit@3   hit@5   MRR     精确率
vector             -      -     0.87    0.93    1.00    0.906   0.533
bm25               -      -     0.67    0.87    0.87    0.756   0.460
hybrid-c5-k10/30/60     5  10/30/60 0.73  0.93    1.00    0.847   0.480
hybrid-c10-k10/30/60   10  10/30/60 0.73  0.93    1.00    0.847   0.480
hybrid-c20-k10/30/60   20  10/30/60 0.73  0.93    1.00    0.836   0.467
```

**（1）`k` 从 10 到 60，数字一模一样——这是数学必然，不是代码没生效。**

```
score = 1/(k+a) + 1/(k+b)
k ≫ 名次时：  score ≈ (2/k) · (1 - (a+b)/(2k))        a、b 是两路里的名次
```

**顺序几乎只由「名次之和 a+b」决定，k 只影响近似并列的情况。** 而「两路都命中」的文档
在任何 k 下都压过「只在一路里」的文档（两项正数 vs 一项）。

> 我原本的假设是「k=60 把名次差异压平了」——**错的**。换成 k=10 一点用都没有，
> 因为两路融合的排序本来就不靠 k 决定。**这条只有跑了网格才能知道**；
> 如果只跑一组参数、或者只调 k 不调候选数，就会误以为「是参数没调好」。

**（2）候选数从 10 加到 20 反而更差**（MRR 0.847 → 0.836）。同样有解释：
RRF 的重奖是「两路都命中」，所以**一对平庸的名次（比如 18 和 19）能压过
只在单路里排第 3 的正确片段**——候选池越深，这种「平庸共识」越多。

**（3）两个具体现象也都有出处：**

- `D01` 融合后从第 1 掉到第 2：`(向量1, BM25 2)` 与 `(向量2, BM25 1)` 的
  **名次和都是 3**，同分——谁在前由 id 排序决定，**不是证据决定的**。
- `D11` / `D15` 的自检仍然打「**0 个被两路同时命中**」：两路完全不相交，RRF 只是在交错拼接。

### 6.5 结论：**按事先立好的标准，这是结构性负收益**

参数网格里**没有任何一组**能追平单向量（hit@1 0.87）。所以：

> **在当前语料规模上，加一个弱关键词通道 + 等权 RRF 融合，是负收益。**

原因不是「RRF 不好」，而是 **RRF 的前提在我们这里不成立**：
它要求各路的**可信度相当**（因为它按名次等权相加）。而这里 BM25 的 hit@1 是 0.67、
向量是 0.87——**不等价的两路，等权融合就是把好的往差的方向拉。**

### 6.6 一个意外收获：确定性被真验过了

新代码的 `hybrid-c5-k60` 行是 `0.73 / 0.93 / 1.00 / 0.847 / 0.480`，
**和上一跑（旧代码、旧列结构）的 hybrid 行逐位相同**；`vector` / `bm25` 两行也完全一致。

**两次跑、而且是不同版本的代码，确定性指标逐位一致** —— 那两条「同分按 id 定序」的处理没白做。

### 6.7 下一步的方向（不是继续调参）

既然「等权融合」不成立，而关键词通道**确实**有它擅长的东西（精确编码、型号），
那么合理的下一步不是继续拧 RRF 的旋钮，而是**改变融合的前提**：

- **不做平均意义下的融合**，而是让关键词通道**在它该出场时出场**
  （比如查询里出现精确编码/型号时才加权关键词）——**「看情况用」而不是「一直混着用」**；
- 或者**放弃在检索层融合，把两路都交给重排**（迭代 17）——让重排去看「哪一段真的回答了问题」，
  而不是看「哪一段被两路同时提到」。

这两条都超出了「RRF 调参」的范围，**它们是关于「什么时候该信哪一路」的设计问题**。

### 6.8 一个必须承认的规模问题

19 个片段、6 份文档、15 道题。**BM25 的 IDF 在这个规模上极不稳定**——
一个 term 的 `df` 可能只有 2，这时候 IDF 基本是噪声。
而且 BM25 平均只返回 4.1 个片段（向量是 5.0），说明大量查询词在语料里根本不存在。

**所以这个负结果里有多少是「弱通道 + 等权融合」的机制问题、多少是「语料太小」，
本轮分不清。** 这是诚实的边界，不该被含糊过去。

## 七、局限

1. **只有 15 道 document 题，语料 19 个片段。** 这个规模下 BM25 的 IDF 统计很不稳
   （一个 term 的 df 可能只有 2）——**真实规模下 BM25 才真正发挥**。
2. **文档级指标，不是片段级。** 测不出「找对了文档但找错了那一段」。
3. **字符二元组的固有代价**：切出来的不是词，所以「同义词」这类问题它天然无解
   （那本来就是向量的活）。
4. **RRF 的 k=60 没调过。** 在我们的 19 片段规模上，名次差异本来就被压得很平，
   k 的影响可能很小——**但这是推测，没测**。
5. **两路都取 top-5 再融合**。取多少再融合本身是个参数（取 3 路 20 个候选再融合是常见做法），
   本轮固定 5 没扫。
